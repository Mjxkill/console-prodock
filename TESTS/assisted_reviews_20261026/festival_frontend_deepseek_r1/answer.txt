Revue statique uniquement : aucun outil, aucune exécution, aucun accès carte. Les numéros de ligne renvoient au paquet fourni.

**Hypothèse de travail indispensable** : `r->width`/`r->height` sont les dimensions half-res (400×240 et 640×360), car `board()` compare `w=2*r->width` à 800 puis choisit 960×480 pour l’autre mode (`festival.c:216`). Le paquet ne définit pas `r->width`. Si ce sont les dimensions natives, les pages UI de 1 MiB débordent : `1280×720=921 600` passe, mais `1600×960=1 536 000` et `2560×1440=3 686 400` dépassent `1<<20` (`festival.c:396`). À vérifier avant de conclure sur le double buffering UI.

## 1. Input jardin : restart non gardé, indexe `games[4]`

- **Faits** : `games` a `L3_TABLE_COUNT` éléments (`l3_festival.h:14`, `l3_table.h:8-9`, donc indices 0..3). En jardin (`kind==4`), seuls `m`, `e`, `w/a/s/d` retournent (`festival.c:77-80`). Les autres touches tombent sur le bloc restart (`festival.c:86-87`) :
  `unsigned k=f->kind; l3_table_init(&f->games[k],k,...);`
  avec `k==4`.
- **Contre-exemple** : entrer dans une table, terminer une partie, revenir au jardin par Tab, puis appuyer sur `R` ou `Entrée` : `f->view.status` peut être encore non nul, et/ou `c=='r'`, donc `l3_table_init(&games[4],4,...)` est appelé.
- **Statut** : chemin atteignable et index hors bornes **prouvé**. La corruption dépend de `l3_table_init` (non fourni) : s’il écrit avant de valider `kind`, corruption mémoire ; s’il valide d’abord, le chemin reste incohérent et réinitialise le jardin.
- **Correction minimale** :
  ```c
  if (f->kind < L3_TABLE_COUNT &&
      (c=='r' || c=='R' ||
       ((c==10 || c==13) && f->view.status))) { ... }
  ```
  et ajouter `return;` à la fin du bloc `if(f->kind==4)` pour les touches non traitées. Alternative : remettre `f->view.status=0` en entrant au jardin, mais la garde `kind<COUNT` reste nécessaire.
- **Test discriminant** : ajouter `assert(kind < L3_TABLE_COUNT)` en tête de `l3_table_init`, puis faire le scénario ci-dessus ; ou placer une canari après `games[3]` et vérifier qu’elle ne change pas.

## 2. Sortie du festival : géométrie 3D non invalidée

- **Faits** : `l3_festival_leave()` remet `active=0`, `assets=0`, les stamps, puis `reset_draw()` (`festival.c:34-36`). Il ne remet ni `geometry_ready` ni `mesh_count`. Or `garden()` ne reconstruit que si `!geometry_ready` (`festival.c:329-330`), et `garden_geometry()` réinitialise `mesh_count` seulement quand elle est appelée (`festival.c:291-323`).
- **Contre-exemple** : entrer au jardin, laisser `garden_geometry()` remplir `GEOMETRY` à 17,75 MiB, quitter le festival (Tab), jouer à LUMA normal qui réutilise de la mémoire GPU, puis revenir au jardin via `N` (`build.py:70-72`). `garden()` voit `geometry_ready==1` et dessine les anciens `meshes[]` sans re-upload.
- **Statut** : état conservé **prouvé**. La corruption visuelle dépend de la réutilisation effective de la région `GEOMETRY` par le jeu normal, non fournie.
- **Correction minimale** : dans `l3_festival_leave()` :
  ```c
  f->assets=0;
  f->geometry_ready=0;
  f->mesh_count=0;
  ```
- **Test discriminant** : instrumenter un compteur d’appels à `garden_geometry()` ; ou écrire un motif 0xAA dans `GEOMETRY` après `leave`, revenir au jardin et vérifier que la géométrie est reconstruite.

## 3. `bake_board()` modifie le fond GPU sans invalidation

- **Faits** : `art()` publie les assets puis appelle explicitement `gpu_v1_invalidate(&r->gpu)` (`festival.c:152-155`). `bake_board()` modifie `f->background` en CPU et le publie à `6u<<20` (`festival.c:195-209`) sans invalidation. Ensuite `board()` fait un `gpu_v1_copy` depuis cette zone (`festival.c:249`).
- **Contre-exemple** : quitter un autre jeu de table pour entrer dans Othello, ce qui déclenche `bake_board()` (`baked_kind != kind`, `festival.c:218`) ; le `copy` peut lire l’ancien fond si le cache GPU n’est pas invalidé.
- **Statut** : incohérence **prouvée** avec le chemin `art()`. La nécessité exacte de l’invalidation pour `gpu_v1_copy` est une **hypothèse** liée au cache GPU, non fourni.
- **Correction minimale** : après le `publish()` de `bake_board()` :
  ```c
  gpu_v1_invalidate(&r->gpu);
  ```
- **Test discriminant** : après `bake_board()`, forcer un `copy` puis relire/compare un pixel de la zone viewport, ou comparer avec un chemin sans cache. Si le résultat est identique, l’invalidation n’est pas nécessaire pour ce backend.

## 4. Solitaire : colonnes longues hors viewport

- **Faits** : la pile tableau utilise `gap=13` dès `count>15` (`festival.c:173-175`). Une carte fait 78 px de haut et commence à `y=106`. Pour `count=20`, bas = `106 + 19×13 + 78 = 431 > 400`. Or le dirty rectangle est borné à `y1=400` (`festival.c:245`) puis le scissor est appliqué (`festival.c:249`). Les cartes basses sont donc coupées/non redessinées.
- **Contre-exemple** : injecter un état Solitaire avec une colonne de 20 cartes ; la 20e carte dépasse 400 et n’est pas entièrement visible, alors que la logique de sélection autorise `row<51` (`festival.c:107`).
- **Statut** : **prouvé** par la géométrie et le clamp.
- **Correction minimale** : rendre le gap dynamique :
  ```c
  float gap = 17.0f;
  if (s->count[c] > 1) {
      float avail = 400.0f - 106.0f - 78.0f;
      gap = fminf(17.0f, avail / (float)(s->count[c] - 1));
  }
  ```
  ou ajouter un scroll. Il faut aussi vérifier que le dirty rectangle n’est pas borné à 400 si un décalage de rendu est introduit.
- **Test discriminant** : construire un état à 20 cartes dans une colonne et rendre en 800×480 et 1280×720 ; vérifier que la dernière carte est dans le scissor et visible.

## 5. Sauvegarde : garde de séparation seulement par `strcmp` exact

- **Faits** : `build.py:58` vérifie uniquement :
  `if(save_path&&!strcmp(save_path,festival_save))`.
  Si `save_path` est `NULL`, aucune comparaison n’est faite ; si deux chaînes différentes ou un lien matériel désignent le même fichier, la garde passe. Le chargement refuse les formats étrangers, ce qui protège un fichier V5 existant, mais ne remplace pas une comparaison d’identité.
- **Contre-exemple** : lancer sans `--save` mais avec `--festival-save <chemin V5 par défaut>` ; la garde est sautée. Si le fichier V5 n’existe pas, un fichier de progression est créé à cet emplacement. Avec `--save /a` et `--festival-save /a/../a`, les chaînes diffèrent alors que le fichier est identique.
- **Statut** : trou de garde **prouvé**. Le dommage réel dépend du chemin V5 par défaut, non fourni ; c’est une **preuve manquante**, pas une corruption certaine d’un fichier V5 existant.
- **Correction minimale** : canoniser les deux chemins (`realpath` pour l’existant), et comparer `st_dev`/`st_ino` après `stat` avec le chemin V5 par défaut ou effectif ; refuser aussi si `festival_save` est un lien matériel vers ce fichier.
- **Test discriminant** : hacher le fichier V5 avant/après un lancement utilisant deux écritures différentes du même chemin, ou un lien matériel ; attendre un refus sans écriture.

## Hypothèses et preuves manquantes à ne pas transformer en certitudes

- `r->width` half-res : non défini dans le paquet. Si natif, les pages UI de 1 MiB (`festival.c:396`) et les publications de fond (`festival.c:219`) doivent être recalculées.
- `l3_table_init` : l’implémentation n’est pas fournie ; le défaut n°1 est un appel hors contrat, la corruption n’est certaine que si l’écriture précède la validation de `kind`.
- `gpu_v1_invalidate` : la sémantique du cache GPU n’est pas fournie ; le défaut n°3 est une incohérence de chemin, pas une preuve de corruption.
- Chemin V5 par défaut : absent du paquet ; le défaut n°5 est une garde insuffisante, pas une preuve d’écrasement d’un fichier V5 existant.
- `l3_ui_text` : le nombre d’octets par pixel n’est pas fourni. `calloc(w,h)` et `publish(...,w*h)` suggèrent 8 bits/pixel ; si c’est faux, il y a un débordement UI même en half-res.
- `build.py:74` utilise `s.replace` sans `assert` de cardinalité, et `renderer.festival=festival` est placé avant `l3_presentation_bind` (`build.py:67`). Un double `l3_festival_step` ou une perte du pointeur sont possibles, mais non prouvables sans `main.c`/`l3_presentation_bind`.
- Les défauts connus exclus (scissor 720, ESC flèches Hangman) ne sont pas comptés.
