## Performance : ce qui est observable dans le code

Fait :
- `festival.c:261-264` publie des sections de 240 sommets/faces maximum ; `mesh_count` est borné à 24.
- `festival.c:267` flush quand `nv+3>240` ou `nf==240`.
- `festival.c:326-327` dessine tout `mesh_count` chaque image ; `festival.c:331-342` dessine ensuite 6 parties de héros.
- Aucun critère de distance, d’angle ou d’occlusion n’apparaît dans la boucle de rendu.

Hypothèse technique :
- Les 934 triangles statiques tiennent probablement dans 4 maillages de 240 faces. Le gain principal d’un culling serait donc surtout sur le ciel/horizon et les objets lointains, pas sur un découpage infini.
- L’absence d’occlusion est la vraie lacune perf conceptuelle : tout est redessiné même quand les relais et le bosquet occultent la fontaine. Mais ajouter un culling global sans bounds par objet demande metadata et risque CPU.
- La borne lointaine `100*65536` est probablement surdimensionnée pour un jardin de rayon effectif < 32 ; réduire délibérément la valeur améliorerait la précision de perspective si la représentation du G3D1 est réciproque. C’est une hypothèse, non une mesure.
- Le ciel R3 reste volontairement en rayon 2 (`handoff_r3.md`) pour la précision depth ; le monde Festival ne prouve pas qu’il suit la même discipline.

## Trois corrections minimales proposées (non appliquées)

### P1 — Refaire la composition du sol : masses et itinéraires, pas grille régulière

Impact attendu : le plus élevé visuellement ; réduit aussi les carreaux répétitifs.

Patch minimal sur `festival.c:282-288` : garder la base `grass0` comme masse unique, et ne poser des dalles que sur des axes de promenade et une couronne.

```c
/* Remplacer la condition actuelle par : */
for (int z = -14; z < 14; z += 2)
  for (int x = -14; x < 14; x += 2) {
    float a = (float)x + 1, b = (float)z + 1;
    if (fabsf(a) > 11 || fabsf(b) > 11) continue;
    int artery = fabsf(a) < 1.9f || fabsf(b) < 1.9f;          /* axes centraux */
    int promenade = fabsf(fabsf(a) - 8.5f) < 1.9f ||
                    fabsf(fabsf(b) - 8.5f) < 1.9f;              /* couronne */
    if (!artery && !promenade) continue;                            /* pelouse continue */
    unsigned r = artery ? 150 : 124;  /* stone1-ish / earth2-ish */
    unsigned g = artery ? 142 : 110;
    unsigned bcol = artery ? 124 : 92;
    quad3(&m, (L3Vec3){x+.04f,.01f,z+.04f}, ... r,g,bcol);
  }
```

Faits limitant :
- La couleur reste approximative ; aucune preuve que le tile index 1/2 a cette teinte.
- On ne sait pas si `.01f` est visible sans z-fighting selon la caméra.

Contre-exemple :
- Si les chemins sont trop étroits, le jardin paraîtra labyrinthique et lisible seulement depuis une capture haute ; la nouvelle caméra plus basse devra être testée.

### P2 — Grossir les masses verticales : relais et bosquet comme taches, non copies

Impact attendu : deuxième temps fort visuel et surtout réduction majeure des triangles.

2a) Relais, `festival.c:291-296` : garder la masse principale et la toiture, supprimer ou réduire les 4 poteaux lourds.

```c
/* Au lieu de la séquence complète, garder la masse et le toit : */
box(&m, x, 0, z, 2.8f, .2f, 2.8f, 195,180,142);           /* stone1-ish */
box(&m, x, .2f, z, 1.8f, .85f, 1.2f, c[0],c[1],c[2]);     /* teinte propre au site */
box(&m, x, 3.7f, z, 4.5f, .18f, 4.5f, c[0]*3/4,c[1]*3/4,c[2]*3/4);
/* option : seulement deux angles, plus fins */
for (int i = 0; i < 2; i++)
  box(&m, x + (i?1.05f:-1.05f), 0, z + (i?1.05f:-1.05f),
      .14f, 2.8f, .14f, 172,158,118);
```

2b) Bosquet, `festival.c:298-303` : remplacer 36 modules complets par 12 masses coniques irrégulières. Coût : environ 12 × 4 = 48 triangles au lieu de 504.

```c
for (unsigned i = 0; i < 12; i++) {
  float angle = i * 6.2831853f / 12 + sinf(i * 1.7f) * .35f;
  float radius = 23 + 5 * sinf(i * 2.3f) + (i % 3) * .9f;
  float x = sinf(angle) * radius, z = cosf(angle) * radius;
  float h = 7 + (i % 5);
  L3Vec3 top = {x, h, z};
  L3Vec3 a = {x-2,h*.3f,z-2}, b={x+2,h*.3f,z-2},
         c={x+2,h*.3f,z+2}, d={x-2,h*.3f,z+2};
  /* quatre facettes teintées bark5/leaf7; pas de cube-tronc pour arrière-plan */
  tri(&m,a,b,top,112,92,68);
  tri(&m,b,c,top,124,104,78);
  tri(&m,c,d,top,108,90,64);
  tri(&m,d,a,top,118,98,72);
}
```

Ce patch répond à la demande d’une forêt au fond sans multiplier les commandes : un seul maillage inchangé, moins de triangles, et les relais restent les éléments lisibles au premier plan.

Contre-exemple :
- Réduire le nombre de modules extérieurs peut rendre l’horizon vide ; il faut conserver des masses hautes même si le triangle count baisse. Les 12 propodes restent suffisamment larges (4 triangles × 4 m).
- La teinte “bark/leaf” n’est qu’une approximation locale ; si les textures chargées ont des contrastes différents, le patch seul ne produira pas l’effet voulu.

Impact attendu : lisibilité de profondeur et composition spatiale ; persistance de la réservation R3.

Patch minimal sur `festival.c:313-318` :

Ce patch ne déplace pas le ciel : `festival.c:320` copie déjà `sky_transform=transform` puis annule la translation, donc le changement de visée n’entraîne pas de translation erronée du fond.

Pour la transparence demandée, proposition minimale sans nouvelle commande par objet :
- Représenter l’eau comme un seul plan horizontal à `y=.015` dans le même maillage, teinté selon `water6`, plutôt qu’ajouter des quadruplés `gpu_v1_quad` par morceau d’eau.
- Ne passer à un alpha inférieur à 256 que si les flags et le moteur G3D1 prouvent l’ordre depth/alpha ; sinon garder l’eau opaque et la faire lire par contraste avec la pelouse.
- Pour la lune : réutiliser le ciel R3 déjà chargé (`festival.c:155`, `handoff_r3.json`) au lieu d’ajouter un objet séparé ; le passage `f->map` commute déjà le ton de fond (`festival.c:313`), ce qui est une base pour ambiance jour/nuit. Le paquet ne prouve pas que le tile R3 contient une ou plusieurs lunes.

Corps de culling optionnel, sans casser le dessin global :

```c

   au centre du maillage seulement si un champ bounds_radius existe.
   À défaut, ne pas ajouter ce patch sans metadata. */
```

Ce point resterait une vérification d’API, pas une promesse.

## Risques et contre-exemples à ces conseils

1. Composition trop raffinée peut échouer au débogage visuel : la caméra basse (P3) peut révéler que les relais à `y=3.7` masquent le horizon. La visée actuelle à `z-5` est indépendante du yaw (`festival.c:130` met à jour `f->yaw`, mais `target` n’utilise pas yaw). Si P3 n’est pas accompagné d’une cible cohérente, le joueur peut voir la scène latéralement désaxée.
2. Reduction du bosquet (P2) peut paraître artificielle si elle supprime trop de profondeur. Une alternative défendable serait de garder 18 masses, mais la variation de coût serait alors modeste.
3. Le pseudo-texturing par teinte ne fournit pas la texture elle-même. Si la GPU 3D ne transporte pas l’UV (`tri` ne remplit que la couleur), le patch ne change que la palette, pas le grain ni la relief.
4. L’eau translucent peut créer un faux problème d’ordre si le G3D1 compare depth et la surface est trop proche du sol (`.015`). L’eau opaque est plus sûre.
5. P1/P2 rendent les chemins plus lisibles en supprimant des carreaux, mais ils rendent aussi plus visible toute irrégularité de destination. Le patch doit être accompagné d’une vérification de navigation ADS.
6. Le culling par distance n’est pas à ajouter aveuglément : le coût dominant semble modeste en triangles, et les bornes de boîtes 240 faces peuvent masquer les micro-gains. Un patch de regroupement est plus justifié qu’un culling sophistiqué.

4. Vérifier la réserve root `festival.c:10-13` après publication du ciel ; tailles référencées : texture 262144, vertices 1792, faces 896.
5. Tester le mode `f->map` dans les deux ambiances et la visée basse pour repérer clipping des arbres.
6. Compter les draw calls avant/après pour éviter la dérive “pas de nouvelle commande par objet”.
7. Ne pas convertir les commandes en FPS ; se limiter au nombre de triangles et pixels supplémentaires, comme précisé dans la demande.

Conclusion opérationnelle : le premier geste utile est la réduction de la grille à des masses de circulation (P1). Le deuxième est l’allégement du bosquet (P2), car il supprime plus de la moitié des triangles statiques. Le troisième (P3) ne modifie quasiment pas le nombre de triangles, mais conditionne la perception de la profondeur et doit attendre la validation visuelle. Ne pas toucher à la réserve R3, au moteur des mini-jeux ni à la carte VRAM.
