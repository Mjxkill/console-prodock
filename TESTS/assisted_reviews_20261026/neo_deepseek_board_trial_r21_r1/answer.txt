## Périmètre

Revue statique du paquet fourni uniquement. Je n’ai exécuté aucun test, aucun script OpenOCD et aucune action matérielle. Les constats sont limités aux fichiers cités.

## Faits vérifiés

### 1. Adresses, tailles et non-recouvrement

`board_trial_r21.py:35` fixe :

- `COLOR=0x00800020`
- `SOURCE=0x00808000`
- `DEPTH=0x00810000`

`local_plan()` construit trois régions avec 32 octets de garde avant/après (`board_trial_r21.py:62-66`) :

- couleur : `0x00800000 .. 0x0080103f` inclus, payload utile à `COLOR`
- source : `0x00807fe0 .. 0x0080803f`, payload utile à `SOURCE`
- profondeur : `0x0080ffe0 .. 0x0081101f`, payload utile à `DEPTH`

L’assertion `board_trial_r21.py:68` vérifie bien le non-recouvrement. En revanche, elle ne vérifie pas explicitement que :

- `COLOR == regions['color'][0] + 32`
- `SOURCE == regions['source'][0] + 32`
- `DEPTH == regions['depth'][0] + 32`

Ces égalités sont vraies par construction, mais elles ne sont pas testées. Un décalage accidentel de région resterait possible sans être détecté.

### 2. Paquets COPY16 et CLEAR16

`board_trial_r21.py:38` :

```text
COPY16 = [29<<24, SOURCE, (16<<16)|1, 32, 0, 0, (16<<16)|1, 0]
```

Les bits `87:80` du mot 2 valent `(0x00100001 >> 16) & 0xff = 0x10`, ce qui correspond au contrat `contract.json:9`. Le test passe bien `width=16` au décodeur (`board_trial_r21.py:197`). Le mot 3 vaut `32`, ce qui est cohérent avec un payload de 16 pixels 16 bits, mais le code ne l’explique ni ne le vérifie.

`board_trial_r21.py:39` :

```text
CLEAR_COLOR16 = [28<<24, 1, 0x5aa5, 0x7bde, 0, (16<<16)|1, 0, 0]
```

Le masque `1` correspond à « couleur seule » d’après les libellés des cas voisins `z_cpu_probe_r19.py:24-27`. L’attendu associé est bien 32 octets de `0x5aa5` (`board_trial_r21.py:75`). La profondeur doit rester inchangée, ce qui est encodé par `expected[name]` mais pas explicitement testé comme invariant de masque.

Point important : ni COPY16 ni CLEAR16 ne contiennent d’adresse de destination explicite. Leur destination dépend de l’état laissé par `TARGET` (`board_trial_r21.py:36`) exécuté avant chaque cas (`board_trial_r21.py:190`). Aucune assertion ne prouve que la destination courante vaut effectivement `COLOR`.

### 3. Décodeur D*

Le mapping `decode_capture.py:15-20` correspond au contrat `contract.json:8-24` :

- `7:0` = largeur D
- `15:8` = largeur Q
- `16` = CE
- `17` = reset moteur
- `18` = COPY_START
- `19` = IDLE
- `20` = CHECK
- `21` = VALIDATE
- `22` = bad
- `23` = done

Le format 64 bits vérifie le magic `0xd` en `63:60`, le bit réservé 55, l’époque en 54, le masque d’événements en `59:56` et les deux échantillons 24 bits (`decode_capture.py:27-36`). Ce mapping est cohérent avec le contrat fourni.

En revanche, `decode_capture.py:41-56` ne fait que produire des `findings`. Le contrôleur ne les teste jamais. `board_trial_r21.py:197` décode le COPY16 avec une largeur attendue, mais aucune assertion ne refuse :

- `valid_samples != 3`
- `complete == 0`
- `armed == 1`
- `COPY_CAPTURE_INCOMPLETE`
- `COPY_INPUT_WIDTH_DIFFERS`
- `COPY_TRIGGER_NOT_PRESENT_IN_SAMPLE`
- `COPY_WIDTH_Q_DOES_NOT_MATCH_CAPTURED_D`

C’est un chemin de faux PASS logique : un log peut produire `diagnostic_complete=True` avec une capture D* inutilisable. Le résultat enregistre les findings, mais ne les transforme pas en verdict.

### 4. Ce que `parse_case()` vérifie réellement

`board_trial_r21.py:109-123` vérifie :

- présence de `CASE_OBSERVED`
- un seul bit `COMMAND_COMPLETE`
- 26 mots GPU avant/après
- un `NCP` de 6 mots, signature `0x4e435031`, statut `(word1 & 0x4f) == 12`
- cohérence du bit d’époque entre `ARM_EPOCH` et le statut
- décodage D* des mots 4/5

Il ne vérifie pas directement :

- que `COMMAND_COMPLETE=1` signifie succès fonctionnel, et non simple avancement de file ;
- que les deltas d’erreur sont nuls ;
- que les findings D* sont vides ou concluants ;
- que les données mémoire attendues sont présentes.

Ces vérifications sont déplacées dans `board_trial_r21.py:192-209`, avec une faiblesse importante : l’assertion mémoire n’est exécutée que si la commande est complétée **et** sans delta d’erreur (`board_trial_r21.py:208`).

## Risques de faux PASS ou de perte de preuve

### P1. Commande « complétée » avec erreurs : aucun contrôle du payload

`PACKET` considère une commande terminée dès que le compteur de file avance et que le bit busy retombe (`isolate_r19_clear.py:51-54`). Une commande rejetée rapidement peut donc produire `COMMAND_COMPLETE=1` avec des deltas d’erreur non nuls.

Or, dans ce cas :

- `board_trial_r21.py:207` vérifie seulement les gardes ;
- `board_trial_r21.py:208` saute l’assertion `expected_matches` ;
- le payload couleur peut avoir été partiellement écrit sans qu’aucune assertion ne le signale ;
- `row` contient bien `unchanged` et `differing_expected_bytes`, mais ces champs ne sont pas interprétés.

Conséquence : un rejet avec écriture partielle peut être enregistré comme simple « observation » alors qu’il viole l’hypothèse « opération rejetée = mémoire intacte ».

### P2. `diagnostic_complete` est inconditionnel

`board_trial_r21.py:212` fixe `diagnostic_complete=True` après la boucle, sans vérifier :

- que tous les cas ont été exécutés ;
- qu’un `outcome` explicite existe ;
- que les captures D* sont conclusives ;
- que les cas COPY16/CLEAR16 ne sont pas tous incomplets.

Un log synthétique avec deux captures `valid_samples=0` et `COPY_CAPTURE_INCOMPLETE` passerait cette étape si les commandes sont marquées complétées sans erreur et si les gardes sont intactes.

### P3. `TARGET` n’est pas prouvé sans écriture

`TARGET` utilise `COLOR` et `DEPTH` (`board_trial_r21.py:36`) et est exécuté avant chaque cas (`board_trial_r21.py:190`). Le contrôleur vérifie seulement :

- `target['completed']`
- deltas d’erreur nuls
- `memory_event_mask == 0` (`board_trial_r21.py:192-193`)

Il ne dumpe pas la couleur, la profondeur ni la source après `TARGET`. Or les attendus COPY/CLEAR sont construits à partir des seeds initiaux (`board_trial_r21.py:71-76`, `201`). Si `TARGET` écrit dans la région couleur ou profondeur, le test devient invalide et échouera probablement à `board_trial_r21.py:209`, mais le paquet ne fournit pas la preuve que ce n’est pas le cas.

C’est une preuve manquante, pas nécessairement un bug matériel.

### P4. Destination implicite non prouvée

COPY16 et CLEAR16 n’ont pas d’adresse de destination explicite. Le test infère que `TARGET` a configuré la destination à `COLOR`. Aucune lecture de registre GPU ni assertion de champ d’adresse ne le confirme. Le seul contrôle est indirect : comparaison des octets à `COLOR`. Si l’opération écrit ailleurs, le test échoue peut-être, mais il ne distingue pas « mauvaise destination » de « opération rejetée » ou « commande non exécutée ».

### P5. Stride/source non couverts

COPY16 contient `w3=32` (`board_trial_r21.py:38`) et la région source ne contient que 96 octets (`board_trial_r21.py:64`). Si `32` est un stride et que la copie lit plus d’une ligne, la source utile dépasse la région seedée. Le code ne vérifie ni le nombre de lignes, ni la couverture `height × stride`, ni que le payload attendu est bien contigu. Le contrat ne fournit pas cette sémantique.

C’est une hypothèse à lever par le contrat COPY ou par un test de seed discriminant, pas une conclusion matérielle.

## Correctifs minimaux proposés

### Correctif 1 — vérifier les offsets de région

Ajouter après `board_trial_r21.py:66` :

```python
assert COLOR == regions['color'][0] + 32
assert SOURCE == regions['source'][0] + 32
assert DEPTH == regions['depth'][0] + 32
assert len(regions['source'][1]) == 96
```

C’est minimal et teste directement les adresses réservées.

### Correctif 2 — prouver que TARGET ne modifie pas les seeds

Après la commande `TARGET` (`board_trial_r21.py:190`), dumper couleur, profondeur et source, puis comparer aux seeds avant de lancer COPY16/CLEAR16. Si `TARGET` est censé écrire, il faut alors construire les attendus à partir de son résultat, pas des seeds. Un simple dump de 3 régions et une comparaison suffisent.

### Correctif 3 — classer explicitement chaque cas

Ajouter une fonction pure :

```python
def classify(row):
    err = any(row['error_deltas'].values())
    if row['completed'] and not err:
        return 'completed_ok'
    if row['completed'] and err:
        return 'rejected'
    if not row['completed'] and not err:
        return 'stalled'
    return 'inconsistent'
```

Puis :

- `completed_ok` : conserver l’assertion `expected_matches` ;
- `rejected` : exiger au minimum `row['color']['unchanged']` et `row['depth']['unchanged']`, pour détecter une écriture partielle ;
- `stalled` : enregistrer `unchanged` et `differing_expected_bytes` sans conclure au succès ;
- `inconsistent` : échec explicite.

### Correctif 4 — rendre `diagnostic_complete` conditionnel

Remplacer `board_trial_r21.py:212` par une condition du type :

```python
assert len(result['cases']) == len(CASES)
result['diagnostic_complete'] = all(
    row.get('outcome') in ('completed_ok', 'rejected', 'stalled')
    for row in result['cases']
)
```

Et ajouter, pour COPY16, un champ `capture_conclusive` :

```python
row['capture_conclusive'] = (
    row['capture']['valid_samples'] == 3
    and row['capture']['complete']
    and not row['capture']['armed']
)
```

Ne pas assimiler `diagnostic_complete` à `capture_conclusive` : ce sont deux preuves différentes.

### Correctif 5 — lier le route review au helper D*

`route_review()` (`board_trial_r21.py:80-106`) vérifie le netlist, le bitstream et les `inputs`, mais `observer_paths_reviewed` n’est qu’un booléen (`board_trial_r21.py:101`). Il faut au minimum :

```python
contract_path = HERE / 'contract.json'
assert sha(contract_path) == review['contract_sha256']
contract = json.loads(contract_path.read_text())
helper = Path(contract['helper'])
helper = helper if helper.is_absolute() else ROOT / helper
assert sha(helper) == contract['helper_sha256']
```

Sans cela, rien ne prouve que le bitstream utilisé contient bien l’observateur D* exact du contrat.

## Tests discriminants avec logs synthétiques

### T1 — décodage nominal des bits COPY16

Construire un échantillon 24 bits :

```python
before = 0x10 | (1 << 16) | (1 << 18)   # D=16, CE, COPY_START
after = 0x10 << 8                        # Q=16
cap = ((0xd << 60) | (1 << 50) | (3 << 48)
       | (after << 24) | before)
d = decode(cap, 0, 16)
assert d['at_trigger']['width_d'] == 16
assert d['at_trigger']['copy_start'] is True
assert d['next_clock']['width_q'] == 16
assert d['findings'] == ['COPY_WIDTH_CAPTURE_CONSISTENT']
```

Ce test vérifie les frontières de bits 7:0, 15:8, 16, 18, 48:49 et 50.

### T2 — faux PASS d’une capture incomplète

Reprendre `cap` mais forcer `valid_samples=0` :

```python
incomplete = cap & ~(3 << 48)
d = decode(incomplete, 0, 16)
assert 'COPY_CAPTURE_INCOMPLETE' in d['findings']
```

Construire un log synthétique contenant `CASE_OBSERVED`, `COMMAND_COMPLETE 1`, 26 mots GPU, `ARM_EPOCH 0` et un `NCP` avec `incomplete`. Le `parse_case()` actuel ne lèvera pas d’exception. Le test doit échouer après le correctif 4 si `capture_conclusive` est exigé pour COPY16.

### T3 — commande complétée avec erreur et payload partiel

Log synthétique :

- `COMMAND_COMPLETE 1`
- `GPU_AFTER[3] = GPU_BEFORE[3] + 1`
- capture valide
- `row['color']['unchanged'] = False`

`classify()` doit retourner `rejected`. Le test doit vérifier que le contrôleur refuse un rejet avec payload modifié. Cela couvre P1.

### T4 — log sans `NCP` ou avec statut incomplet

Vérifier que :

- absence de `NCP` lève une erreur ;
- `NCP` avec `raw[0] != 0x4e435031` lève une erreur ;
- `raw[1] & 0x4f != 12` lève une erreur ;
- époque incohérente lève une erreur.

Ces tests sont déjà partiellement couverts par `board_trial_r21.py:118-120`, mais il faut les figer dans un test automatisé car le parseur est le point d’entrée de la preuve.

### T5 — attendus mémoire COPY16/CLEAR16

Extraire la construction des attendus dans une fonction pure testable, puis vérifier :

- COPY16 : `expected_color[32:64] == source_seed[32:64]`, source et profondeur inchangées ;
- CLEAR16 : `expected_color[32:64] == struct.pack('<H', 0x5aa5) * 16`, profondeur inchangée ;
- modifier un octet de `source_seed[32:64]` change l’attendu COPY16 ;
- modifier `COLOR` change l’emplacement du payload et doit être détecté par le correctif 1.

### T6 — route review synthétique

Avec un JSON de review minimal, vérifier que le contrôleur refuse :

- un `contract_sha256` absent ;
- un helper dont le SHA diffère de `contract.json` ;
- un netlist différent sans preuve d’équivalence ;
- une preuve d’équivalence dont `parent_netlist_sha256` ne correspond pas à `NETLIST_SHA`.

## Preuves manquantes

- `board_trial_r19.py`, `observe_r19_clear.py` et l’éventuel `decode_capture.py` C1 de `local_capture_20261026` ne sont pas fournis. Les hypothèses d’import de `board_trial_r21.py:20-25` ne peuvent donc pas être validées.
- La sémantique exacte de `TARGET`, de `w3=32` et de la destination implicite n’est pas fournie.
- Aucun résultat d’exécution R21 n’est fourni : `diagnostic_complete`, `capture_conclusive` et les invariants mémoire restent à démontrer.
- Le lien entre `NETLIST_SHA`, le helper `neo_capture_memory.v` et le bitstream n’est pas vérifié par le code.

## Conclusion

Le code fourni contient des gardes utiles sur les adresses, les seeds et les gardes mémoire, et le mapping D* est cohérent avec le contrat. Mais deux faux PASS logiques sont identifiables par inspection :

1. une capture D* incomplète peut être enregistrée avec `diagnostic_complete=True` sans assertion sur les findings ;
2. une commande complétée avec deltas d’erreur peut avoir modifié partiellement le payload sans que `unchanged` soit exigé.

Les correctifs 1 à 5 et les tests T1 à T6 sont minimaux et discriminants. Ils ne nécessitent ni révision FPGA ni nouvelle hypothèse de conception.
