Analyse **statique uniquement** : je n’ai exécuté aucun test, aucune action matérielle, aucune modification de fichier.

## 1. Verdict court

Oui, un cache HUD minimal peut être ajouté **dans `mini_ui.c` seul**, sans toucher au GPU, sans atlas, sans nouvelle couche, sans remplacer le cache double page existant.  
Mais les mesures PP2 ne permettent pas encore d’attribuer les 244,93 s de préparation du mode 1024 au raster CPU plutôt qu’au scan/upload : il faut d’abord instrumenter `raster_us`, `scan_us`, `upload_us`, puis seulement optimiser.

Le point important : **ne pas re-rasteriser tout le canevas UI à chaque changement de `stamp`**. Le patch proposé ci-dessous sépare :

- un **fond/panneaux/texte statique** mis en cache une fois par clé ;
- un **dessin dynamique** limité au plateau et aux valeurs HUD ;
- le cache double page existant `mini_stamp[2]` / `mini_canvas_stamp` reste intact ;
- la publication 32 bits existante reste la seule publication.

## 2. Faits, hypothèses, manques

### Faits établis par le packet

- Mode 1024 : `activities.json:117` `"Fusion 1024"`, `:118` 2 827 frames, `:119` `completion_fps` 9,633, `:136` `preparation_ms_per_frame` 86,6404.  
  Donc `2827 × 86,6404 ms ≈ 244 932 ms = 244,93 s`.  
  `2827 / 9,633 ≈ 293,46 s`, soit **83,46 %** de préparation. C’est cohérent avec le chiffre annoncé.
- Mode 1024 : `mini_ui_bytes_per_frame` = 12 539,9 octets (`activities.json:126-127`), soit 35 450 344 octets au total. Ce n’est pas un volume d’upload énorme en soi, mais **cela ne prouve pas** que le temps de scan/upload est négligeable.
- Mode 1024 : `commands_per_frame` = 0, `batches_per_frame` = 0 (`activities.json:128-129`), `submit_ms_per_frame` = 0 (`:137`), `max_layers` = 1 (`:132`). Le coût est donc côté préparation CPU, pas côté soumission GPU.
- Mode 1024 : `adviser_ms_per_frame` = 0,6818 (`activities.json:135`) → environ 1,93 s, soit 0,66 %. Ce n’est pas le poste dominant.
- Mode 5 « Maison des lueurs » : préparation 112,886 ms/frame (`activities.json:162`), 157 frames, `mini_ui_bytes_per_frame` 5 223,8 (`:152-153`), `submit_ms_per_frame` 40,04 (`:163`). Le HUD n’est pas le seul poste.
- Mode 7 « Vaisseau » : préparation 11,224 ms/frame (`activities.json:214`), `mini_ui_bytes_per_frame` 1 045,8 (`:204-205`), `max_layers` 4 (`:210`), `max_sprites` 22 (`:209`).
- Mode 8 « Tour 3D » : préparation 25,926 ms/frame (`activities.json:240`), `mini_ui_bytes_per_frame` 2 480,2 (`:230-231`).
- Mode 0 « Exploration 3D » : `mini_ui_bytes` = 0 (`activities.json:22-23`) alors que la préparation est 13,212 ms/frame (`:32`). Le cache HUD ne peut donc pas expliquer ce poste.
- Limites déclarées : les coûts par activité incluent les transitions, et `mini_ui_bytes` exclut le HUD monde et l’art statique initial (`activities.json:247-250`). Il n’y a pas de scène fixe contrôlée.

### Faits de code

- Le cache double page existe déjà : `mini_pixels`, `mini_shadow[2]`, `mini_stamp[2]`, `mini_canvas_stamp` (`luma3d_render.h:43`, `:49-50`). Il ne faut pas le reproposer.
- `l3_mini_ui_prepare` (`mini_ui.c:293-314`) fait actuellement :
  - `l3_arcade_view` puis `hash_view` ;
  - si `mini_canvas_stamp != stamp`, reconstruction complète :  
    `memcpy` du fond + `header` + `board` + `sidebar` + `footer` pour `k<4` (`mini_ui.c:307`), ou `shooter_hud` / `scene_hud` complet (`:308`) ;
  - puis `upload(&c,page,stamp)` (`:311`).
- `upload` (`mini_ui.c:282-292`) scanne toutes les lignes et compare les mots de 32 bits ; il publie seulement les mots différents. Il ne lit jamais la VRAM : il compare `mini_pixels` et `mini_shadow[page]`.
- `sidebar` (`mini_ui.c:198-221`), `shooter_hud` (`:225-246`) et `scene_hud` (`:247-265`) mélangent dans une même passe le statique et le dynamique.
- `hash_view` (`mini_ui.c:277-281`) est déjà sémantique pour la 3D : il n’hash pas des positions de grille MAZE. Je ne le modifie pas et je n’ajoute pas de hash de positions.
- La couche UI est choisie en fin de `l3_mini_ui_prepare` (`mini_ui.c:293-314`) : couche 0, ou couche 3 pour le shooter. Le patch ne touche pas à ce choix, n’ajoute aucune commande GPU et n’active pas les couches 12..15.

### Hypothèses, à vérifier par mesure

- Il est plausible que le mode 1024 passe l’essentiel de ses 86,6 ms/frame à reconstruire le fond, le plateau et la sidebar, car il n’y a ni commande ni submit. Mais ce n’est pas démontré : `l3_arcade_view`, `hash_view`, le scan de `upload` et le dessin des textes peuvent aussi contribuer.
- Le `memcpy` du fond 1280×720 n’est probablement pas dominant à lui seul, mais je ne le suppose pas. C’est précisément pourquoi `raster_us` doit inclure toute la préparation CPU hors upload, et pas seulement le `memcpy`.

### Manques de preuve

- Le packet ne contient pas `puzzle_art.c/h`, ni les métriques de glyphes, ni les valeurs RGB du fond. Je ne peux donc pas certifier des valeurs RGB exactes de pixels ; je peux certifier des **coordonnées et des zones**, et faire du rendu de référence A l’oracle des valeurs.
- Pas de capture framebuffer fournie. Une preuve A/B/A sur `mini_pixels` + `last_scene` prouve l’identité du canevas CPU et de la configuration de couche, pas nécessairement le pixel final affiché. Si le harnais ne sait pas capturer l’écran, il faut le dire explicitement.
- Pas de trace des commandes GPU par frame dans le packet. La preuve « GPU state conservé / max 64 commandes » doit être faite par comparaison de `last_scene`, `commands`, `batches`, `state_valid` et `state_cache`.

## 3. Cache proposé, exactement

### 3.1 Principe

Ajouter un **cache de chrome UI** : un canevas CPU plein format, non publié, qui contient uniquement :

- le fond immuable ;
- les panneaux (`panel`, `glass_panel`) ;
- les textes statiques hors zones dynamiques.

Ce cache ne remplace ni `mini_pixels`, ni `mini_shadow[0/1]`, ni la publication 32 bits. Ce n’est pas un troisième canevas affiché.

### 3.2 Clé de cache

```c
static unsigned ui_chrome_key_for(const Canvas *c,unsigned k,
                                  const L3MiniView *v,const L3Game *g)
{
    unsigned h=2166136261u;
    const uint32_t a[]={
        k,(unsigned)c->w,(unsigned)c->h,(unsigned)c->scale,(unsigned)c->wide,
        v->kind,(unsigned)v->width,(unsigned)v->height,v->status,
        g->activities.arcade.won,g->showcase_status
    };
    for(unsigned i=0;i<sizeof(a)/sizeof(*a);i++)h=(h^a[i])*16777619u;
    return h?h:1;
}
```

À exclure volontairement de la clé : `score`, `progress`, `lives`, `moves`, `target`, `cells`.  
Pour MAZE, la clé ne contient que `k`, `status`, `showcase_status` et la taille : pas de positions de grille.

### 3.3 Contenu exact du cache

Pour `k<4` :

- `memcpy(ui_chrome, puzzle_background_800/1280, c.w*c.h)` ;
- `header` complet : le tag dépend de `status`/`won`, tous deux dans la clé ;
- `sidebar(..., pass=1)` : **uniquement** `glass_panel` + le nom statique ;
- `footer` complet : dépend de `showcase_status`, dans la clé.

Le plateau n’est **pas** dans le cache : il change trop souvent.  
La partie basse de la sidebar n’est pas dans le cache en v1 : elle est redessinée dans l’ordre original après le plateau, ce qui évite tout problème d’ordre de dessin avec les valeurs dynamiques.

Pour le shooter :

- `shooter_hud(..., pass=1)` : `memset`, barres noires, séparateurs, titre, labels statiques `ÉQUIPAGE`, `SCORE`, `PROTECTION`, `VAGUE`, `CIBLES`, contrôles du bas ;
- pas de cœurs, score, bouclier, vague, kills, boss.

Pour `scene_hud` :

- `scene_hud(..., pass=2)` : `memset`, panneau haut, titre, panneau bas, statut/récompense/contrôles, ligne du bas ;
- pas d’`info`, pas de `lives`.

### 3.4 Découpage statique/dynamique

`sidebar` prend un paramètre `pass` :

- `pass=1` : `glass_panel` + nom, puis `return` ;
- `pass=2` : ne redessine ni le verre ni le nom ; reprend à partir de la valeur numérique, puis `meter`, score, ligne, statut/récompense/hint/touches, dans l’ordre original ;
- `pass=0` : comportement complet actuel, si un autre appel existe.

C’est volontaire : la partie basse de la sidebar est redessinée à chaque frame, mais **le coût du `glass_panel` et du fond est supprimé**. On ne met pas en cache un texte de sidebar qui pourrait recouvrir une valeur dynamique.

`shooter_hud` prend `pass` :

- `pass=1` : tout le statique ;
- `pass=2` : uniquement `state`, `lives`, score, bouclier/double, vague, kills, boss ;
- les labels statiques restent dans la base, les valeurs sont dessinées après, donc l’ordre label → valeur est conservé.

`scene_hud` prend `pass` :

- `pass=1` : `memset`, panneaux, titre, statut/récompense/contrôles, ligne du bas ;
- `pass=2` : uniquement `info` et `lives`.

### 3.5 Algorithme dans `l3_mini_ui_prepare`

```c
unsigned page=r->frame&1;
unsigned stamp=hash_view(&v,k,g->activities.arcade.won,
                         g->showcase_status,g->showcase_stage);
unsigned ckey=ui_chrome_key_for(&c,k,&v,g);

if(ui_chrome_key!=ckey){
    Canvas bc=c; bc.pixels=ui_chrome;
    ui_chrome_pass=1;
    if(k<4){
        memcpy(ui_chrome,c.w==800?puzzle_background_800:puzzle_background_1280,
               (size_t)c.w*c.h);
        header(&bc,k,v.status,g->activities.arcade.won&(1u<<k));
        sidebar(&bc,g,&v,c.w-unit(&c,244),1);
        footer(&bc,g);
    }else if(k==L3_ARCADE_SHOOTER){
        shooter_hud(&bc,g,&all.content.shooter,1);
    }else{
        scene_hud(&bc,g,&all,1);
    }
    ui_chrome_pass=0;
    ui_chrome_key=ckey;
    ui_chrome_builds++;

    /* La base a changé : les stamps de page ne sont plus une preuve
       suffisante si un champ de clé n'est pas dans hash_view. */
    r->mini_canvas_stamp=0;
    r->mini_stamp[0]=r->mini_stamp[1]=0;
}

if(r->mini_stamp[page]!=stamp){
    if(r->mini_canvas_stamp!=stamp){
        memcpy(r->mini_pixels,ui_chrome,(size_t)c.w*c.h);
        ui_chrome_pass=2;
        if(k<4){
            int sx=c.w-unit(&c,244);
            board(&c,&v,sx);
            sidebar(&c,g,&v,sx,2);
        }else if(k==L3_ARCADE_SHOOTER){
            shooter_hud(&c,g,&all.content.shooter,2);
        }else{
            scene_hud(&c,g,&all,2);
        }
        ui_chrome_pass=0;
        r->mini_canvas_stamp=stamp;
        r->mini_rasterizations++;
    }
    upload(&c,page,stamp);
}
```

Le `memcpy` depuis `ui_chrome` remplace le `memcpy` du fond + les panneaux + les textes statiques. En v1, c’est un **reset complet de la base** ; c’est simple et sûr. Les dirty rects ci-dessous ne servent que si les compteurs montrent que ce `memcpy` complet est lui-même significatif.

Important : on ne touche pas à la fin de `l3_mini_ui_prepare` (`mini_ui.c:293-314`) qui publie la couche 0 ou 3. Aucune commande GPU, aucune couche 12..15.

## 4. Dirty rects fiables

À utiliser seulement pour une restauration partielle depuis `ui_chrome`, **jamais** pour changer le format de publication 32 bits.

```c
typedef struct { int x,y,w,h; } UiRect;

static UiRect board_rect(const Canvas *c,const L3MiniView *v,int right)
{
    int top=unit(c,86), bottom=c->h-unit(c,54), area=right-unit(c,42);

              bw+2*rim+2*unit(c,3),

static UiRect sidebar_after_name_rect(const Canvas *c,int x)
```

Restauration :

```c
static void restore_rect(Canvas *c,UiRect r)
{
    int x0=max(r.x,0), x1=min(r.x+r.w,c->w);
    int y0=max(r.y,0), y1=min(r.y+r.h,c->h);
    for(int y=y0;y<y1;y++)
        memcpy(c->pixels+(size_t)y*c->w+x0,
               ui_chrome+(size_t)y*c->w+x0,
               (size_t)(x1-x0));

```

Règles :

- `board_rect` couvre le cadre, les vis, l’ombre et l’intérieur du plateau ;
- `sidebar_after_name_rect` couvre toute la zone après le nom, y compris les textes statiques de statut/hint/touches, car `pass=2` les redessine ;

- `scene_top_rect` couvre `info` et `lives`, tout en laissant le titre statique dans la base.

Ne pas utiliser ces rects pour restreindre l’upload dans le patch v1 : la publication delta 32 bits existante doit rester la seule publication. Si `scan_us` domine, on pourra plus tard limiter la boucle de comparaison existante à ces rects, sans changer le format.

## 5. Compteurs `raster_us`, `scan_us`, `upload_us`

### 5.1 `raster_us`

Ajouter autour de `l3_mini_ui_prepare`, de l’entrée jusqu’à avant `upload` :

```c
static uint64_t ui_raster_ns, ui_scan_ns, ui_upload_ns;
static uint64_t ui_now_ns(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC,&ts);
    return (uint64_t)ts.tv_sec*1000000000ull+(uint64_t)ts.tv_nsec;
}
```

Dans `l3_mini_ui_prepare` :

```c
uint64_t t_prep=ui_now_ns();
uint64_t s0=ui_scan_ns,u0=ui_upload_ns;
/* ... l3_arcade_view, hash_view, chrome, dynamique, upload ... */
uint64_t t_end=ui_now_ns();
ui_raster_ns += (t_end-t_prep)
              - ((ui_scan_ns-s0)+(ui_upload_ns-u0));
```

Ainsi `raster_us` inclut `l3_arcade_view`, `hash_view`, la reconstruction du chrome et le dessin dynamique, mais pas le scan ni l’écriture d’upload. C’est le seul moyen de voir si le temps restant est réellement du raster.

Si `raster_us` reste dominant, faire une seconde instrumentation temporaire `view_us` / `hash_us` / `board_us` / `sidebar_us` : le packet ne permet pas de savoir lequel domine.

### 5.2 `scan_us` et `upload_us`

Modifier `upload` (`mini_ui.c:282-292`) en deux passes par ligne : construction d’une petite liste de mots dirty, puis écriture. On garde exactement les mêmes écritures 32 bits et le même `mini_shadow`.

```c
static void upload(Canvas *c,unsigned page,unsigned stamp)
{
    L3Render *r=c->r;
    int force=!r->mini_stamp[page];
    unsigned bytes=0;

    for(int y=0;y<c->h;y++){
        size_t at=(size_t)y*c->w;
        const uint8_t *source=r->mini_pixels+at;
        uint8_t *shadow=r->mini_shadow[page]+at;
        uint16_t dirty[512];
        unsigned nd=0;
        uint64_t t0=ui_now_ns();

        if(force){
            for(int x=0;x<c->w;x+=4)dirty[nd++]=(uint16_t)x;
        }else{
            if(!memcmp(source,shadow,(size_t)c->w)){
                ui_scan_ns+=ui_now_ns()-t0;
                continue;
            }
            for(int x=0;x<c->w;x+=4){
                uint32_t a,b;
                memcpy(&a,source+x,4);
                memcpy(&b,shadow+x,4);
                if(a!=b)dirty[nd++]=(uint16_t)x;
            }
        }
        ui_scan_ns+=ui_now_ns()-t0;

        t0=ui_now_ns();
        for(unsigned i=0;i<nd;i++){
            int x=dirty[i];
            uint32_t a;
            memcpy(&a,source+x,4);
            *(volatile uint32_t *)(r->memory+MINI_BASE+page*MINI_PAGE+at+(unsigned)x)=a;
            memcpy(shadow+x,&a,4);
            bytes+=4;
        }
        ui_upload_ns+=ui_now_ns()-t0;
    }

    r->mini_stamp[page]=stamp;
    if(bytes){r->mini_uploads++;r->mini_bytes+=bytes;}
}
```

`dirty[512]` est sûr pour les tailles ouvertes : 1280/4 = 320 au maximum.

### 5.3 Sortie

Dans `l3_mini_ui_close` (`mini_ui.c:266`), imprimer une ligne exploitable :

```c
fprintf(stderr,
 "L3_UI_PROFILE raster_us=%llu scan_us=%llu upload_us=%llu "

```

Puis libérer `ui_chrome` et remettre les compteurs à zéro.  
Pour les activités successives du showcase, le harnais doit imprimer les deltas au changement de `kind` ; sinon les totaux mélangent les huit activités.

Aucun FPS ne doit être déduit de ces temps.

## 6. Preuve A/B/A à exiger

### Protocole

1. **A1** : binaire R6 non patché, même sauvegarde, même entrée enregistrée.
2. **B** : binaire avec le patch.
3. **A2** : recompilation depuis la même source R6, mêmes entrées.
4. Pour chaque scénario, capturer après un nombre fixe de frames :
   - `mini_pixels` page 0 et page 1 ;
   - `mini_shadow[0]`, `mini_shadow[1]` ;

   - `commands`, `batches`, `state_valid`, `state_cache` ;
   - si disponible, capture écran externe.

Assertion : `SHA256(A1) == SHA256(B) == SHA256(A2)` pour chaque capture.  
Si seule la capture CPU est disponible, la preuve est limitée au canevas CPU + configuration de couche ; il faut le déclarer.

- **Save/reward** : victoire 1024, sauvegarde, rechargement, comparaison du tag `SOUVENIR ACQUIS` et de la sidebar.
- **Showcase reward** : `showcase_status` 0 → 1 → 3, comparaison footer/scene_hud/shooter.
- **Maison**, **Shooter**, **Tour 3D** au repos.
- Vérifier `commands`, `batches` et couches identiques ; aucune couche 12..15 activée par le patch.

## 7. Quatre cas négatifs où un cache erroné donne des pixels différents

Ces tests sont des **mutations volontaires** de la clé ou de l’invalidation. Ils doivent échouer avec le cache erroné et passer avec le patch. Le harnais doit imprimer le premier pixel divergent `(x,y,attendu,obtenu)`.

| # | Cache erroné | Scénario | Zone/pixel divergent attendu |
|---|---|---|---|
| 1 | `k` absent de `ui_chrome_key` | 1024 page 0, puis Maison page 0, même taille 1280×720 | Le fond/panneau 1024 reste. La zone `board_rect` contient une tuile 1024 non nulle ; `scene_hud` fait `memset(...,0)` (`mini_ui.c:248`), donc la Maison correcte est noire dans cette zone. Si la grille 1024 est 4×4, le centre du plateau vaut `(458,384)` ; sinon utiliser `board_rect` pour trouver le premier pixel divergent. |
| 2 | `v.status` absent de la clé | 1024 `RUNNING` → `WON`, même `won` | Le tag d’en-tête et/ou le texte de statut de sidebar changent. Zone exacte : tag à `y=42`, `x = c->w - unit(c,28) - (text_width(f,tag)+unit(c,26)) + unit(c,13)` (`mini_ui.c:110-119`) ; sidebar statut à `(x=939, y=328)` pour 1280×720 (`sidebar`, `mini_ui.c:198-221`). Le pixel exact de premier écart est celui du glyphe différent, à relever par le rendu A. |
| 3 | `g->activities.arcade.won` absent de la clé | 1024 `RUNNING`, `won=0` → `won=1` | Le tag d’en-tête passe de `DÉFI FACULTATIF` à `SOUVENIR ACQUIS`. Même zone que le cas 2, `y=42`, `x` recalculé avec `text_width` du tag. Un cache erroné laisse l’ancien texte ; le test doit voir `memcmp != 0` dans cette zone. |
| 4 | `g->showcase_status` absent de la clé | 1024 `RUNNING`, `showcase_status=0` → `3` | Le footer change : `À votre rythme` ↔ `Visite en pause · E pour jouer` (`footer`, `mini_ui.c:103-109`). À 1280×720 : `y=675`, texte aligné à droite jusqu’à `x=1238` ; la divergence est dans les derniers glyphes à droite. Le cache erroné conserve l’ancien footer. |

Contrôle supplémentaire recommandé, même s’il n’est pas compté dans les quatre : forcer la parité de page 0/1 et vérifier que la page 0 ne reçoit jamais le contenu de la page 1. Le cache double page existant doit rester la seule autorité.

## 8. Limites et précautions

- Le cache `ui_chrome` est **file-static** dans `mini_ui.c`. C’est acceptable pour un seul `L3Render` par processus ; si le projet ouvre plusieurs rendus, il faudra le déplacer dans `L3Render`, mais ce n’est pas dans ce patch minimal.
- Le patch ne modifie ni les règles, ni les temps, ni les récompenses, ni les sauvegardes, ni les pixels d’art R6. Il ne touche ni aux glides GPU en cours, ni au fond RGB565, ni aux ombres ARGB4444, ni aux textes natifs GPU.
- Le patch ne duplique pas la publication indexée 32 bits : `upload` continue d’écrire les mêmes mots et de mettre à jour `mini_shadow`.
- Le patch ne lit jamais la VRAM.
- Le patch n’ajoute aucune commande GPU, aucune couche, et ne touche pas aux couches 12..15.
- Aucun FPS n’est prédit à partir de l’hôte. Les compteurs doivent être interprétés avec les limites `activities.json:247-250`.
- Sans `puzzle_art.c/h` et sans capture framebuffer, les valeurs RGB exactes des cas négatifs doivent être prises dans le rendu de référence A ; je ne les invente pas.
