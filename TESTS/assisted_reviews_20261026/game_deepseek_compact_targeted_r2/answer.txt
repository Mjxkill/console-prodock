## Verdict

Je ne trouve, dans le code fourni, **aucun contre-exemple d’état divergent pour la recherche merge elle-même** : la projection compacte reproduit bien `merge_index`, `merge_slide`, `merge_spawn`, `merge_has_move`, `merge_quality` et `merge_search` pour les champs qui influencent réellement une décision merge. En revanche, le **nouveau témoin `targeted.c` ne teste pas directement la décision compacte racine** ; il teste l’égalité des valeurs de recherche et la décision du moteur public. C’est le principal trou de preuve du packet, surtout pour la validation RV32.

---

## Faits vérifiables dans le packet

### 1. La projection merge semble exacte

- `compact_index` (`compact_proposal.h:41-47`) reproduit bien `merge_index` de `l3_minigames.c` :
  - `dir==0` : ligne `pos`, colonne `line` ;
  - `dir==1` : ligne `line`, colonne `3-pos` ;
  - `dir==2` : ligne `3-pos`, colonne `line` ;
  - `dir==3` : ligne `line`, colonne `pos`.
- `compact_slide` (`compact_proposal.h:49-79`) reprend le même ordre de compactage, la même fusion unique par tuile et le même `add_sat`.
- `compact_spawn` (`compact_proposal.h:95-113`) parcourt les cases dans le même ordre `y` puis `x`, consomme le même nombre d’appels RNG et choisit `2` avec la même probabilité `1/10`.
- `compact_has_move`, `compact_quality` et `compact_search` (`compact_proposal.h:81-93`, `135-190`, `192-209`) sont sémantiquement alignés avec leurs homologues du moteur.
- Les champs non copiés — `data[0]`, `data[1]`, `aux`, cases hors 4×4 — n’entrent pas dans `merge_move`, `merge_search` ou `merge_quality`. Ils interviennent seulement dans `l3_mini_validate` ou dans des invariants dérivés, pas dans le choix merge. L’affirmation « projection de recherche seulement » est donc cohérente.

### 2. Le nouveau témoin couvre bien seed0, les profondeurs et les fins

- `targeted.c:36` contient bien `seed=0`, ainsi que `0x80000000` et `0xffffffff`.
- `checked_advice` compare `merge_search(s,depth)` et `compact_search(&c,depth)` pour `depth=0..3` (`targeted.c:20-21`).
- Il vérifie aussi les quatre directions légales depuis l’état courant (`targeted.c:24-29`).
- Le retour terminal de `l3_mini_demo_input` est testé sans modification des sorties (`targeted.c:22-23`).
- Les 3 exécutions rapportent la même ligne, donc même ordre d’exécution, mêmes valeurs et même digest sur les 6004 états du témoin. C’est un résultat de reproductibilité, pas une preuve exhaustive.

### 3. Les anciens et nouveaux chiffres ne doivent pas être fusionnés

- `strict_result.json` décrit l’ancien `differential.c` : `states=64332`, `checks=6943110`, `wins=125`, `losses=3`, host seulement.
- Le nouveau `targeted_20261027_r1/result.json` décrit `states=6004`, `checks=675892`, `wins=12`, `losses=1`, avec host/ASAN/RV32.
- Ces deux campagnes sont complémentaires ; le packet ne doit pas laisser entendre que les 64 332 états ont été validés sur RV32.

## Limite principale : la décision compacte racine n’est pas testée dans le nouveau témoin

C’est le point contradictoire le plus concret.

Dans `targeted.c:24-29`, la valeur attendue est calculée avec le **moteur public** :

```c
int a=merge_search(&t,3), b=compact_search(&u,3);
assert(a==b);
if(a>best){best=a;expected=keys[d];...}
```

Puis `targeted.c:31-32` vérifie seulement :

```c
int ok=l3_mini_demo_input(s,&p,&h,&dt);
...
assert(p==expected&&h==0&&dt==0);
```

Autrement dit :

- `compact_search` est comparé à `merge_search` sur les fils ;
- `l3_mini_demo_input` est comparé à une sélection recalculée avec `merge_search` ;
- **aucune fonction compacte ne choisit la touche racine** et n’est comparée à `expected`.

Or la sélection compacte existe seulement dans `differential.c:14-22`, pas dans `compact_proposal.h`, et l’ancien `strict_result.json` est explicitement host-only. Donc la phrase de limite « QEMU validates RV32 decisions » est trop forte si elle vise la décision de l’adviser compact : le témoin RV32 valide les **valeurs** `compact_search` et la décision publique, pas le wrapper compact de choix racine.

Un bug dans le wrapper compact — ordre des directions, gestion des égalités, mapping `keys[d]`, filtre des coups sans changement — ne serait pas détecté par `targeted.c`.

---

## Contre-exemple de contrat encore non couvert : état terminal

`compact_move` (`compact_proposal.h:115-133`) ne teste pas `status`. `l3_mini_demo_input` du moteur, lui, retourne `0` si l’état n’est pas `L3_MINI_RUNNING`.

Conséquence : un `compact_advice` naïf construit comme `advice()` dans `differential.c:14-22`, sans garde terminal, peut renvoyer une touche sur un état `WON` non plein, alors que `l3_mini_demo_input` renvoie `0`.

Le nouveau témoin ne couvre pas ce cas :

- `targeted.c:22-23` retourne avant tout appel à une décision compacte pour les états terminaux ;
- les 12 états `WON` du témoin ne sont donc utilisés que pour vérifier le retour public `0` ;
- le packet ne journalise pas les plateaux terminaux, donc on ne peut pas confirmer ici qu’un des 12 `WON` possède une case vide et un coup compact possible. C’est une **hypothèse concrète à vérifier**, pas un fait du packet.

Si l’on veut un contre-exemple concret, le test discriminant est : prendre le premier état `WON` produit par le témoin, appeler un `compact_advice` sans garde, et vérifier s’il renvoie `0`. S’il renvoie autre chose, la divergence de contrat est démontrée.

## Patch minimal recommandé au banc

Ajouter dans `targeted.c` une sélection compacte racine explicite, avec la même politique terminale que le moteur :

```c
static unsigned compact_advice(const L3CompactMergeState *c)
{
    int best = INT_MIN;
    unsigned key = 0, d;

    if (c->status != L3_MINI_RUNNING)
        return 0;

    for (d = 0; d < 4; ++d) {
        L3CompactMergeState t = *c;
        int value;

        compact_move(&t, d);
        if (t.moves == c->moves)
            continue;

        value = compact_search(&t, 3);
        if (value > best) {
            best = value;
            key = keys[d];
        }
    }
    return key;
}
```

Puis dans `checked_advice`, après le calcul de `expected` :

```c
assert(compact_advice(&c) == expected);
checks++;
hash(compact_advice(&c));
```

Et dans la branche terminale :

```c
assert(compact_advice(&c) == 0);
checks++;
```

Ce patch est minimal et attaque précisément le trou : il teste la **décision compacte racine**, les égalités d’ordre, le mapping des touches et le contrat terminal, y compris sur RV32.

---

## Autres preuves manquantes, non génériques

1. **Égalités** : `targeted.c:59` vérifie seulement `ties != 0`, pas `ties == 993`. Le chiffre 993 est observé dans la sortie, pas encodé comme assertion. Ce n’est pas faux, mais ce n’est pas une preuve que la politique d’égalité compacte est identique ; le patch ci-dessus la testerait.
2. **Digest** : le digest FNV 32 bits est un témoin de reproductibilité, pas une preuve d’absence de divergence. Les assertions, pas le digest, portent la preuve.
3. **Score saturé** : `l3_mini_validate` accepte un score multiple de 4 proche de `UINT32_MAX` ; les états du témoin sont seulement atteignables par jeu normal. Un test construit depuis `l3_mini_init`, avec `meta[SCORE]=0xFFFFFFFCu`, puis un coup qui fusionne, vérifierait `compact_add_sat` sous RV32. Cela ne change pas la décision, mais ferme une limite de la revendication d’égalité complète.
4. **Wrapper terminal** : sans le patch `compact_advice` avec garde `status`, le test ne peut pas affirmer que la projection compacte respecte le contrat « retourne 0 si non-running ».

---

## Conclusion

- **Recherche merge** : pas de divergence concrète trouvée dans le code fourni ; la projection est fidèle pour les champs utiles.
- **Décision compacte racine** : non directement testée par le nouveau témoin `targeted.c`; elle reste couverte seulement par l’ancien `differential.c`, host, et par l’égalité des valeurs de recherche.
- **RV32** : les 6004 états prouvent la cohérence des valeurs de recherche et de l’advice public sur RV32, pas la sélection compacte racine.
- **Cas terminal** : contrat non couvert ; un wrapper compact naïf peut diverger sur un état `WON` non plein, mais le packet ne fournit pas le plateau permettant de l’affirmer.

Le test minimal à ajouter est `compact_advice()` avec garde terminale et assertion `compact_advice(&c) == expected`, exécuté dans les trois environnements.
