## Verdict

**Aucun contre-exemple imputable au correctif proposé n’est démontré par le paquet fourni.** Je ne l’ai pas simulé et je ne peux donc pas affirmer qu’il est testé. Sous le contrat implicite du RTL — `i_usb_txpktfin`, `i_usb_txpop`, `i_usb_txact` concernent l’endpoint `i_usb_endpt` du cycle — le correctif couvre bien le défaut EP1 initial, y compris le flush d’un cycle pendant EP0/EP2.

## Points vérifiés

1. **Priorité NBA index dynamique + bit 1**  
   `tx_pending[i_usb_endpt]` est affecté dans le bloc lignes 369-377, puis `tx_pending[1]` est affecté par le flush lignes 382-385 de `usb_fifo.v`. Pour `i_usb_endpt == 1`, la dernière affectation non bloquante l’emporte : EP1 est bien remis à 0. Pour `i_usb_endpt != 1`, il n’y a pas de conflit sur le bit 1. Même raisonnement pour `tx_saved_len[1]` ligne 384. Le flush gagne aussi sur la mise à jour de `ep1_sent` lignes 413-416.

2. **POP EP1 pendant le flush**  
   `usb_payload_pop` est neutralisé par `!ep1_flush_selected` ligne 343. Si `i_usb_endpt == 1`, aucun POP EP1 n’est présenté au `usb_tx_buf` EP1. En plus, `ep1_reset = i_reset | i_ep1_flush` ligne 390 remet la FIFO EP1 à zéro via les instanciations lignes 743 et 766. Le flush n’est donc pas seulement une suppression d’offre : la FIFO EP1 est bien purgée.

3. **Longueur / CORK**  
   Pendant un flush sélectionnant EP1, `s_usb_txlen` et `s_usb_txcork` sont forcés par priorité lignes 718-720, avant ACK/retire lignes 721-723. En sortie, `o_usb_txcork` et `o_usb_txlen` sont également forcés lignes 1387-1390. C’est cohérent : longueur nulle et CORK haut pendant le flush.  
   Point de détail : sur un front où l’endpoint quitte EP1 (`i_usb_endpt` devient 0 ou 2) alors que `i_ep1_flush` est encore haut, `ep1_flush_selected` est faux ; `o_usb_txlen` peut donc encore porter l’ancienne longueur EP1 pendant un cycle. Mais `tx_endpoint_ready` est faux, donc `o_usb_txcork` est haut ligne 1387. Ce n’est pas une offre valide si CORK est respecté ; c’est un point à couvrir par invariant, pas un contre-exemple démontré.

4. **Préservation EP2**  
   Le flush EP1 n’affecte que le bit 1 : ligne 383. Le bloc dynamique continue de mettre à jour `tx_pending[2]` / `tx_saved_len[2]` lignes 369-377. `ep1_flush_selected` est faux pour `i_usb_endpt == 2`, donc `usb_payload_pop` n’est pas masqué pour EP2 ligne 343. Enfin, le buffer EP1 est reset par `ep1_reset`, mais le buffer EP2 est reset par `i_reset` seul, ligne 787. Dans le périmètre du patch, EP2 n’est pas modifié.

5. **Redémarrage après flush**  
   Après le front de flush : `tx_pending[1] = 0`, `tx_saved_len[1] = 0`, FIFO EP1 vide, `ep1_sent = 0`, `ep1_offer = 0`. Les nouveaux octets ne peuvent apparaître que lorsque `usb_txlen[1]` redevient non nul, c’est-à-dire quand `ep1_txlen` contient réellement des octets lignes 422-424. Le chemin de longueur se recharge ensuite lignes 724-726. Un `tx_retire` résiduel, lignes 355-358 et 721, peut retarder le redémarrage de trois cycles après un ACK simultané, mais ne le bloque pas durablement.

## Preuve manquante / hypothèses à ne pas transformer en défaut du patch

- Le paquet ne prouve pas le contrat exact sur un **front de changement d’endpoint** avec `i_usb_txpktfin` ou `i_usb_txpop`. Le RTL utilise le nouvel `i_usb_endpt` pour `tx_pending` et l’ancien `s_endpt_sel` dans les buffers. Si le contrôleur autorise un ACK/POP appartenant à l’ancien endpoint sur ce front, il peut y avoir mauvaise attribution. Ce n’est pas introduit par le correctif et ce n’est pas démontré par les fichiers fournis.
- Un **ACK + POP simultanés sur EP2** restent priorités ACK dans le bloc dynamique lignes 370-377 : le nouveau paquet n’est pas réservé. C’est un comportement préexistant, visible aussi dans le diff `candidate.patch` lignes 27-55. Il ne faut pas l’attribuer au correctif EP1.
- Le test fourni `ep1_flush_review_tb.sv` maintient `flush` pendant 64 cycles lignes 40-41 et ne couvre ni le flush d’un cycle, ni ACK+POP simultanés, ni le changement d’endpoint au même front. Il est un témoin négatif, pas une preuve des cas demandés.

## Invariants de banc proposés, sans forçage interne

1. **I1 — flush EP0/EP2 puis retour EP1 sans nouvelle donnée** : après un flush d’un cycle avec `i_usb_endpt = 0` ou `2`, puis retour à `i_usb_endpt = 1`, on doit avoir `tx_pending[1] == 0`, `tx_saved_len[1] == 0`, et jamais `o_usb_txcork == 0` avec `o_usb_txlen != 0` tant qu’aucun nouvel octet EP1 n’a été présenté.

2. **I2 — flush EP1 avec ACK et POP simultanés** : sur un front où `i_usb_endpt == 1`, `i_usb_txact == 1`, `i_usb_txpktfin == 1`, `i_usb_txpop == 1`, `i_ep1_flush == 1`, vérifier sur ce front et le suivant : `o_usb_txlen == 0`, `o_usb_txcork == 1`, `tx_pending[1] == 0`, `tx_saved_len[1] == 0`, `ep1_sent == 0`, et aucun POP EP1 accepté.

3. **I3 — changement EP2 → EP1 au front de flush** : avec `s_endpt_sel` encore à 2 et `i_usb_endpt` passant à 1 sur le front de flush, après le front EP1 ne doit offrir ni longueur ni POP ; `o_usb_txcork` doit rester haut pendant le front de changement. Si aucun ACK/POP EP2 n’est présenté, `tx_pending[2]` et `tx_saved_len[2]` doivent rester inchangés.

4. **I4 — préservation EP2 sans ACK/POP** : partir d’un paquet EP2 en attente, sélectionner EP2, faire un flush EP1 d’un cycle avec `i_usb_txpktfin == 0` et `i_usb_txpop == 0`, puis vérifier que `tx_pending[2]`, `tx_saved_len[2]` et l’offre EP2 ne changent pas.

5. **I5 — redémarrage après flush** : après flush, écrire `N` nouveaux octets EP1 avec `i_ep1_tx_dval`, puis `i_ep1_tx_committed = N`. La première offre non-CORK doit avoir une longueur au plus égale au nombre d’octets réellement présents dans la FIFO EP1, jamais l’ancienne valeur 13. Au premier ACK, `ep1_sent` doit augmenter exactement de `tx_saved_len[1]`.

6. **I6 — cohérence CORK/longueur** : si `o_usb_txcork == 0`, alors `i_usb_endpt == s_endpt_sel` et `o_usb_txlen` doit correspondre à l’offre courante, jamais à un paquet EP1 flushé. Si `ep1_flush_selected == 1`, alors obligatoirement `o_usb_txcork == 1` et `o_usb_txlen == 0`.

Ces invariants peuvent être vérifiés en pilotant uniquement les ports et en observant les sorties et, si nécessaire, les registres internes du DUT, sans `force` sur `tx_pending`.
