Fait concret principal : le baseline est compilé sans `L3_MOTION_CANDIDATE`, donc `gpu_motion_probe.c` fait renvoyer `(Motion){0}` par `motion()` ; le candidate, avec la même commande et le même CRC d'état, publie 109 moves. Les deux logs indiquent le même CRC de sortie (`state_crc32=7162ad9c` puis `c5384401`), donc `moves=0` dans le baseline est un effet d'instrumentation, pas une preuve d'absence de mouvements. Indices de phases conservés et validés par le parser : entry = 0..1, rest = 2..13, moving = 14..373 ; le pire frame moving candidat est à l'index 27, bien dans [14,374), et le top rank 0 est le même index. Pour les lecteurs rectangle, `rect_valid()` impose déjà `offset < 2<<20`, `page<2`, dimensions et bytes cohérents ; rien, dans le paquet, prouve une violation.

Témoin : comparer `baseline` et `candidate` par phase ; leur `state_crc32` est égal (`7162ad9c` puis `c5384401`), tandis que `moves` passe de 0 à 109. Test minimal à retenir : pour chaque largeur et kind, asserter `before['state_crc32']==after['state_crc32']` pour les phases appairées, et ne comparer les compteurs Motion qu'avec le candidat activé. Les temps sont des temps hôte ; ils ne prouvent aucun FPS matériel et aucun comportement FPGA n'est modifié par le diagnostic.
