## Verdict

Deux points concrets ressortent du paquet :

1. **Régression de suffixe bufferisé, démontrable** : le `read(2)` de 1024 octets peut consommer des octets situés **après** le NUL terminal d’une trame `FIN`/`STOP`; ces octets sont ensuite perdus. C’est exactement le type de régression introduit par le passage de `read(1)` à une lecture bufferisée.
2. **Bug d’état** : un ACK de doublon valide ne remet pas `bad` à zéro, alors qu’il est traité comme une trame valide. Une séquence « 16 trames invalides + doublon valide + 1 invalide » termine en `BAD_LIMIT` au lieu de continuer.

Le cas **DATA + FIN dans le même buffer** ne m’a pas paru incorrect à la lecture : il est traité dans l’ordre, avec revalidation de deadline au NUL (`receiver.c:82`). Mais le paquet ne fournit pas le test correspondant, seulement le booléen `pipeline_duplicate_data_fin_passed`.

## 1. Suffixe après FIN/STOP : perte d’octets bufferisés

### Faits

- Le tampon d’entrée fait 1024 octets : `uint8_t incoming[1024]` (`receiver.c:69`).
- La lecture est faite jusqu’à 1024 octets : `read(0,incoming,sizeof(incoming))` (`receiver.c:75`).
- Les octets sont ensuite consommés un par un, et la trame terminale provoque un `break` (`receiver.c:87`).
- La sortie `done` ferme le fichier, éventuellement envoie `X`, puis quitte (`receiver.c:98-101`). Aucun reste `incoming[in_at..in_size)` n’est réinjecté ni traité.

Autrement dit, si une même lecture contient :

```text
[ NUL + base64(FIN) + NUL ][ octets suivants ]
```

le second groupe est déjà sorti du flux par le `read`, puis jeté au `break`.

### Preuve de la régression par rapport à l’ancien

`counts_r1/result.json` donne, pour 2048 octets utiles :

- ancien : `read0 = 3046`, `poll0 = 3046` ;
- bufferisé : `read0 = 5` avec `chunk=4096`, `read0 = 192` avec `chunk=16`.

Cela est cohérent avec un ancien lecteur à **un octet par lecture**, et un nouveau lecteur avec lecture anticipée. Je n’utilise pas les temps QEMU pour en tirer une vitesse.

### Contre-exemple minimal, sans carte

Utiliser un pipe ou une FIFO comme stdin du receiver, avec `total=0`, `new`, nonce arbitraire, CRC 0.

1. Écrire en **un seul `write(2)`** :
   ```text
   frame(nonce, op=2, seq=0, offset=0) + b"MARK"
   ```
   soit la trame FIN valide suivie de `MARK`.
2. Lire les réponses du receiver jusqu’à `X`.
3. Après sortie du receiver, lire ce qui reste dans le pipe/FIFO.

Attendu :

- **ancien receiver** : `MARK` reste disponible, car il s’arrête sur le NUL terminal sans lire au-delà ;
- **receiver bufferisé actuel** : `MARK` a été consommé, le receiver annonce `X` raison `0`, et le lecteur suivant ne voit plus rien.

Même test avec `b"id\n"` ou `b"\x03"` : la commande ou le caractère de contrôle qui suit la trame terminale est avalé. Ce n’est pas une corruption du fichier déjà commité, mais c’est une régression d’état du flux console. Sous `sender.py` nominal, aucun suffixe ne doit exister avant le RETURN (`Session.finish` puis `await_return` n’écrivent plus), donc les tests QEMU happy-path ne la voient pas.

### Patch minimal de diagnostic

Un vrai correctif de préservation n’est pas portable sur un flux non « peekable » : il faut soit revenir à `read(1)`, soit utiliser un transport avec `MSG_PEEK`, soit imposer contractuellement qu’aucun octet ne suit le FIN avant le RETURN.

Le patch minimal sûr est au moins de **ne pas annoncer silencieusement DONE/STOPPED si un suffixe a été lu** :

```c
/* op==3 */
if(in_at<in_size){result=IO;break;}
result=STOPPED;break;

/* op==2 */
if(in_at<in_size){result=IO;break;}
result=DONE;break;
```

Cela ne restitue pas le suffixe, mais rend la régression visible et testable. Pour le préserver réellement, il faut changer le mode d’I/O ou le contrat.

## 2. État : `bad` non remis à zéro sur ACK de doublon

### Faits

Chemin doublon :

```c
if(offset<committed&&len<=committed-offset){
    if(!reply('A',0)){result=IO;break;}
    deadline=now()+idle;
    continue;
}
```

(`receiver.c:89-90`)

Le compteur n’est remis à zéro que sur un nouveau bloc effectivement écrit :

```c
running_crc=...;committed+=len;nextseq++;bad=0;
```

(`receiver.c:93`), et le NACK fait `++bad>16` (`receiver.c:96`).

Un doublon valide est donc ACKé mais ne remet pas `bad` à zéro.

### Contre-exemple

Séquence dans une même session :

1. Envoyer une trame DATA valide bloc 0, offset 0, len 512 → ACK, `committed=512`, `bad=0`.
2. Envoyer 16 trames invalides NUL-terminées → 16 NACK, `bad=16` (le 16e ne dépasse pas `>16`).
3. Envoyer un doublon valide de la trame DATA bloc 0 → ACK, mais `bad` reste 16.
4. Envoyer une 17e trame invalide → `++bad` vaut 17, `>16` est vrai, arrêt `BAD_LIMIT`, sans NACK pour cette trame.

Attendu si un doublon ACKé est considéré comme une trame valide : après l’étape 3, `bad=0`, l’étape 4 doit produire un NACK et continuer.

### Patch

Une ligne :

```c
if(offset<committed&&len<=committed-offset){
    if(!reply('A',0)){result=IO;break;}
    bad=0;
    deadline=now()+idle;
    continue;
}
```

Test : envoyer les 16 trames invalides, le doublon, puis une invalide ; vérifier que la réponse est `N` et non `X` raison `8`.

Avec `sender.py`, le sender ne fait que 4 tentatives, donc ce chemin reste défensif. Il n’en est pas moins concret.

## 3. Deadline et arrêt : ce qui est prouvé, ce qui ne l’est pas

### Deadline

Le contrôle est fait avant décodage de chaque trame complète :

```c
uint64_t checked=now();
if(checked>=end_ms){result=TOTAL;break;}
if(checked>=deadline){result=IDLE;break;}
```

(`receiver.c:82`)

Mais l’écriture et la synchronisation viennent après :

```c
write(fd,...);          /* receiver.c:91 */
fdatasync(fd);          /* receiver.c:92 */
```

Il n’y a pas de revalidation de `now()` entre `82` et `91-92`, ni dans `reply()` qui a son propre budget de 1 s (`receiver.c:40`). Une trame décodée juste avant `end_ms` peut donc être commitée après `end_ms`. Si la spécification exige « aucun commit après la deadline totale », c’est un dépassement concret. Le paquet ne fournit pas cette spécification, donc je le classe comme point à trancher, pas comme régression prouvée.

Test discriminant possible sans vitesse physique : injecter un délai artificiel dans `fdatasync`/`write` via un petit `LD_PRELOAD`, avec `idle=total=100 ms`, envoyer une DATA juste avant la limite, et vérifier si `X` raison 0 est émis avec `committed` avancé après la limite. Sans ce test, il ne faut pas affirmer un bug.

### SIGINT/SIGTERM dans le buffer

`stopped` est vérifié en haut de boucle (`receiver.c:71`), mais pas entre les octets bufferisés ni juste avant l’écriture (`receiver.c:91`). Si le signal arrive après le contrôle de la ligne 71 et avant l’écriture, un bloc complet déjà lu peut être écrit, synchronisé et ACKé avant que la boucle ne sorte en `SIGNAL`. Ce n’est pas une corruption — le bloc est valide — mais c’est un dépassement du point d’arrêt, à couvrir par un test instrumenté. Patch conservateur :

```c
if(stopped){result=SIGNAL;break;}
```

juste avant l’écriture du bloc, et de préférence aussi dans la boucle d’écriture.

## 4. Preuves manquantes

- `speed_r1/result.json` ne contient que `pipeline_duplicate_data_fin_passed: true`, sans commande, sans trame, sans sortie `X`/offset. Ce booléen ne prouve pas le cas FIN + suffixe ni le cas deadline.
- `counts_r1/result.json` prouve seulement la granularité des lectures (`read0`) et des appels, pas le comportement après FIN, ni le signal, ni le dépassement de deadline.
- Aucun test fourni ne couvre : suffixe après FIN/STOP, `bad` après doublon, SIGINT pendant un buffer déjà rempli, deadline franchie pendant `fdatasync`.
- Aucune preuve matérielle ; je ne tire aucune conclusion de `qemu_seconds` ou des débits QEMU.

## Recommandation courte

1. Ajouter le test pipe/FIFO `FIN + MARK` ; il discrimine immédiatement l’ancien et le nouveau receiver.
2. Corriger `bad=0` dans le chemin doublon.
3. Décider explicitement la sémantique de deadline : contrôle à la frontière de trame, ou contrôle strict avant/après écriture avec rollback. Sans cette décision, le dépassement après `fdatasync` reste non prouvé.
