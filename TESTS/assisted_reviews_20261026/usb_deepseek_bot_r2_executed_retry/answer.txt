## Verdict

**Je ne vois pas de faux PASS démontré sur le symptôme précis `F01_STALE_DATA_AFTER_BOT`** : la production échoue bien après la purge EP0, et le candidat renvoie NAK au même endroit. Le correctif candidat est cohérent avec la différence observée.

**En revanche, le PASS candidat est sur-interprété** : il ne prouve pas la conformité CBW/CSW/DATA PID, et plusieurs choix du test peuvent masquer un défaut réel. Je relève au moins deux défauts concrets de test : le premier CBW F01 est émis en DATA1, et le CSW du lecteur vide est accepté en DATA0. Le test n’a pas d’oracle PID indépendant.

---

## Faits établis par le paquet

1. **Exécution candidate**  
   `RUN integration_candidate_r2` : `returncode=0`, `pass=true`, `inputs_unchanged=true`, summary `PASS USB disk...`. Les marqueurs F01 attendus sont présents :
   - `F01_CBW_PASS` deux fois,
   - `F01_AHB_PURGE_PASS`,
   - `F01_NO_STALE_EP1`,
   - `F01_BOT_PASS`.

2. **Exécution production/originale**  
   `RUN integration_original_r2` : `returncode=1`, `pass=false`, pas de summary, `F01_NO_STALE_EP1` et `F01_BOT_PASS` absents.  
   Le log original montre, après `F01_AHB_PURGE_PASS`, un paquet EP1 IN :
   `F01_STALE_DATA_AFTER_BOT pid=c3 len=16` à `tasks_r2.svh:576`.  
   `len=16` est la longueur UTMI totale : PID + 13 octets de données + 2 octets CRC. Le payload stale est donc **13 octets `0x55`**, pas 16 octets utiles.

3. **Mécanisme RTL invoqué**  
   Dans `candidate.patch`, le correctif essentiel est la remise à zéro de `tx_pending[1]` et `tx_saved_len[1]` sur tout `i_ep1_flush`, même si EP0/EP2 est sélectionné :
   - `candidate.patch:41-58`,
   - `usb_fifo.v:379-386`.  
   L’original ne le faisait que si `i_usb_endpt == 1` (`candidate.patch:41-49`). C’est exactement le cas « purge AHB pendant EP0 sélectionné ». Le correctif est donc plausible et non générique.

4. **Le test vérifie bien l’exactitude CBW et CSW dans F01**  
   - `f01_command` vérifie les 31 octets CBW lus par AHB, l’absence d’octet supplémentaire et l’état non halté : `tasks_r2.svh:285-315`.
   - `f01_status` construit et vérifie les 13 octets CSW, puis attend l’émission vide : `tasks_r2.svh:316-329`.
   - Le nouveau paquet de 17 octets et le CSW final sont vérifiés octet par octet : `tasks_r2.svh:578-587`.

5. **La purge sous EP0 est observée**  
   `f01_watch_flush` compte `msc_flush` et refuse tout `endpt_sel != 0` : `tasks_r2.svh:3-9`. Le marqueur `flush_ep0_cycles=100` prouve donc que `msc_flush` a bien été actif pendant EP0.  
   Cela ne prouve pas directement l’état interne EP1 ; la preuve finale est le NAK après purge.

## Défauts concrets et risques de faux PASS

### 1. Le premier CBW F01 est émis en DATA1, pas DATA0

Par lecture des affectations :

- `msc_out_pid` initialisé à `0xc3` (`tasks_r2.svh:161`), togglé à chaque OUT accepté (`tasks_r2.svh:187`).
- Remis à `0xc3` à `tasks_r2.svh:451`.
- Le dernier `empty_command(8'h00,...)` avant F01, à `tasks_r2.svh:532`, est accepté et bascule donc `msc_out_pid` de `0xc3` vers `0x4b`.
- Aucune remise à `0xc3` n’est faite avant `f01_command(13)` à `tasks_r2.svh:543`.

Donc, **d’après le code du banc**, le CBW F01 de 13 octets part avec `msc_out_pid = 0x4b` (DATA1). Le garde BOT ne contrôle pas le PID : `usb_msc_guard.v:46-52` ne vérifie que `rx_count` et la signature. Le test accepte donc un CBW non conforme au contrat BOT usuel « CBW = DATA0 ».

**Impact** : le PASS ne prouve pas la conformité DATA PID du CBW. Un DUT qui ignorerait totalement le PID CBW passerait.

**Patch minimal test** : forcer le PID CBW au début de `f01_command`, ou avant `tasks_r2.svh:543` / après le BOT reset :

```systemverilog
msc_out_pid = 8'hc3; // CBW DATA0
```

Il faut aussi le refaire après le BOT reset, avant le second CBW, pour modéliser un hôte qui repart proprement.

---

### 2. L’oracle du PID CSW est auto-référentiel, et le CSW vide est accepté en DATA0

`msc_in` compare le PID reçu à `msc_in_pid`, c’est-à-dire à la valeur courante du banc, et non à une constante BOT :

```systemverilog
if (response_len < 3 || response[0] != msc_in_pid)
    $fatal(...); // tasks_r2.svh:251-252
```

Or, dans le log candidate, on voit un CSW du lecteur vide en PID `c3` :

```text
TX at 4782000379000 ep1 len=16: c3 55 53 42 53 38 2a 42 2e 00 00 00 00 01 4d 9e
FIN ... len=13
```

C’est bien un CSW : `55 53 42 53`, tag, résidu, statut. Il est accepté parce que `msc_in_pid` vaut `c3` à ce moment-là. Si le contrat BOT exige un CSW en **DATA1 (`0x4b`)**, le test encode une attente non conforme et ne peut pas détecter un CSW DATA0.

Le CSW F01 final, lui, apparaît en `4b` dans le log candidate (`4829531811000 ... 4b 55 53 42 53 ...`), donc l’exactitude du CSW F01 n’est pas affectée. Mais le PASS global contient des CSW vides en DATA0.

**Patch minimal test** : dans `empty_status`, forcer l’attente CSW DATA1 avant `empty_packet(0,13)` :

```systemverilog
msc_in_pid = 8'h4b; // CSW DATA1
empty_packet(0, 13);
```

Et ajouter une assertion explicite `response[0] == 8'h4b` pour un CSW, indépendamment de l’état courant du banc.

---

### 3. `empty_packet` ignore complètement `lose_ack`

La tâche est déclarée avec `lose_ack`, mais ne l’utilise jamais :

```systemverilog
task automatic empty_packet(input bit lose_ack, input integer expected_len);
...
    msc_in(1, n); // tasks_r2.svh:220-231
```

Tous les appels `empty_packet(0, ...)` de `empty_status` perdent donc l’argument. Aucun CSW n’est testé avec ACK perdu et rejeu. Le commentaire `tasks_r2.svh:241-242` décrit ce cas, mais il n’est pas exécuté pour les CSW.

**Impact** : le rejeu d’un CSW sans ACK n’est pas couvert. Le garde ne passe à l’état suivant que sur `txpktfin` (`usb_msc_guard.v:68-79`), donc c’est un test discriminant important.

**Patch minimal test** :

```systemverilog
msc_in(lose_ack ? 1'b0 : 1'b1, n);
if (n < 0) ...
if (lose_ack) begin
    // rejeu obligatoire du même CSW, puis ACK
    msc_in(1'b1, n);
end
if (n != expected_len) ...
```

---

### 4. Le NAK F01 n’est pas vérifié immédiatement après la purge

Le test vérifie `F01_NO_STALE_EP1` seulement après :

- le BOT reset,
- le handback `ahb_write(0x14,0x20)`,
- une nouvelle demande de propriété `ahb_write(0x14,0x2)`,
- la remise à `-1` de `msc_in_pending` et à `0xc3` des PID.

Voir `tasks_r2.svh:550-576`. La vérification est donc faite après plusieurs transitions d’état.

Or, dans `usb_msc_port.v`, le handback volontaire retire `owner_u` et active `ureset` via `!owner_u` (`usb_msc_port.v:128-147`), ce qui remet à zéro les compteurs de staging `pushed_u`/`committed_u` (`usb_msc_port.v:329-331`). Le handback ne déclenche pas `ep_flush` s’il n’y a pas abandon (`usb_msc_port.v:142`), mais il modifie quand même l’état côté port. La phrase du test « Voluntary handback does not itself purge » (`tasks_r2.svh:569-570`) est donc trop absolue : il ne purge pas `tx_pending`, mais il remet d’autres états.

L’original échoue malgré ce handback, donc le candidat n’est pas sauvé uniquement par lui. Mais la preuve n’est pas minimale : le NAK pourrait être attribué à la purge, au BOT reset, ou au handback.

**Patch minimal test** : juste après la vérification de purge (`tasks_r2.svh:565`), avant les `control_nodata` de clear feature et avant `0x20` :

```systemverilog
old_response = responses;
token(8'h69, host_address, 1);
await_response(old_response);
if (response_len !== 1 || response[0] !== 8'h5a)
    $fatal(1, "F01 stale immediately after purge: pid=%02x len=%0d",
           response[0], response_len);
```

Puis refaire plusieurs polls espacés pour vérifier que le NAK est stable.

---

### 5. Le chemin `ep1_flush_selected` du correctif n’est pas testé

Le patch candidat ajoute une protection lorsque le flush arrive **alors qu’EP1 est sélectionné** :

- `usb_fifo.v:332-343` : `ep1_flush_selected`,
- `usb_fifo.v:718-726` : `s_usb_txlen`/`s_usb_txcork`,
- `usb_fifo.v:1387-1390` : `o_usb_txcork`/`o_usb_txlen`.

Mais le banc F01 interdit précisément ce cas :

```systemverilog
if (endpt_sel !== 4'd0)
    $fatal(1, "F01 purge moved away from EP0"); // tasks_r2.svh:6
```

Le PASS ne valide donc que le chemin « flush pendant EP0 », pas la nouvelle logique « flush pendant EP1 ». Ce n’est pas un faux PASS sur le symptôme F01, mais c’est une couverture incomplète du correctif.

**Test discriminant à ajouter** : purge AHB pendant une transaction EP1 sélectionnée, avec un paquet IN en attente et sans ACK, puis vérifier NAK/rejeu et non-régression EP2.

---

### 6. Autres limites concrètes

- **Aucun test de purge EP1 OUT** : le flush remet aussi le buffer RX EP1 (`usb_fifo.v:390`, `756-777`), mais F01 ne teste que le stale IN.
- **Aucun test d’un OUT host pending abandonné** : le cas « abandon host pending » n’est couvert que pour IN.
- **Pas de vérification du bit `lost` dans F01** : `ahb_read(32'h04,...)` est fait à `tasks_r2.svh:555`, mais seul `status & 0x300` est contrôlé. Le bit 7 (`lost`) n’est pas testé.
- **Pas de troisième CBW après le CSW final** : `f01_status` vérifie le CSW, mais pas que le garde est revenu à l’état CBW et accepte une nouvelle commande. `usb_msc_guard.v:77` le fait sur `txpktfin && txlen==13`, mais le test ne l’observe pas publiquement.
- **Une seule exécution, logs tronqués aux 60 dernières lignes** : pas de répétition, pas de trace des PID OUT, pas de trace de `tx_pending`/`s_usb_txlen`, pas de preuve interne EP1. La conclusion causale reste donc une inférence RTL + comparaison original/candidat, pas une mesure directe.

## Hypothèses / non prouvé

- **Hypothèse** : les 13 octets `0x55` du log original proviennent du paquet EP1 resté en attente ou de son buffer. Le paquet ne contient pas de trace de `tx_pending` ou du contenu du packet RAM ; l’origine exacte n’est donc pas prouvée. Le correctif candidat la rend muette, ce qui est cohérent, mais le paquet ne permet pas d’identifier formellement la source.
- **Hypothèse de conformité** : si le projet retient le contrat BOT standard « CBW DATA0 / CSW DATA1 », alors les points 1 et 2 sont des non-conformités de test, pas seulement des limites. Le test actuel ne permet pas de les distinguer.
- **Non prouvé** : le PASS candidat avec un vrai hôte USB, un vrai PHY ou un câble. `check_integration_r2.py:163-166` le limite explicitement à un hôte UTMI idéal et à une simulation numérique.

---

## Conclusion

Le candidat corrige vraisemblablement le défaut F01 réel : le clear de `tx_pending[1]`/`tx_saved_len[1]` sur `i_ep1_flush` hors EP1 est le mécanisme minimal qui manque à l’original, et le log candidate montre le NAK attendu là où l’original renvoie un paquet stale.

Mais **le PASS ne doit pas être présenté comme une preuve de conformité CBW/CSW/DATA PID**. En l’état :

- le premier CBW F01 est en DATA1 ;
- le CSW vide est accepté en DATA0 ;
- `empty_packet` n’exerce pas les ACK perdus ;
- le NAK F01 est vérifié après handback/re-request, pas immédiatement après la purge ;
- le chemin `ep1_flush_selected` du correctif n’est pas couvert.

Les patchs ci-dessus sont minimaux et permettent de transformer ce PASS « symptôme » en preuve plus discriminante, sans modifier le DUT.
