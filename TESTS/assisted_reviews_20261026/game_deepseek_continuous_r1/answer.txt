## Verdict

La correction est plausible sur le cœur arithmétique 17/33/100 ms : le report microseconde de `activities.c` absorbe correctement, sur le papier, les découpages 16+1 ms et 16+17 ms. En revanche, je ne valide pas les preuves « temps restant consommé » et « cancellation » telles quelles : le test fourni contient au moins un faux PASS certain et plusieurs angles morts précis.

Je n’ai exécuté aucun test ; l’analyse porte uniquement sur le packet.

## Faits vérifiables

- `play_timed` est bien limité aux jeux temporels (`kind>=4`) dans `showcase.c` ; les puzzles passent toujours par la branche avec `cooldown=kind<4?.4f:0`.
- `l3_showcase_step` plafonne `dt` à `1/60` avant tout traitement (`showcase.c`, début de `l3_showcase_step`).
- La conversion temps → moteur se fait dans `activities.c:34-39` :
  `us=lroundf(dt*1e6)+pending_us; ms=us/1000; pending_us=us%1000;`
  Le reliquat float est donc reporté en microsecondes.
- Pour 17 ms : 16 ms puis 1 ms. Pour 33 ms : 16 ms puis 17 ms. Pour 100 ms : six pas de 16/17 ms. Le report microseconde n’est pas le point faible principal.
- Le résultat fourni est dans `results_r5/result.json`, pas dans un répertoire `motion_continuous_r1/results`. Les hashes citent bien les sources du candidat, mais la provenance du fichier de résultat est à clarifier.

## Points de contre-revue

### 1. Faux PASS certain : la pause de 20 s n’est jamais soumise à `l3_showcase_step`

Dans `test_continuous.c`, bloc irrégulier, lignes 83-86 :

```c
double dt=frame==500?20:intervals[frame%6];
wall+=dt;if(dt>.25)dt=.25;accumulator+=dt;
...
while(accumulator>=1./60){l3_showcase_step(&irregular,&uneven,1.f/60);...}
...
if(frame==500){assert(ticks<=15);pauses++;}
```

Le `20.0` est immédiatement ramené à `0.25`, puis découpé en 15 appels de `1/60`. `l3_showcase_step` ne voit donc jamais un `dt` de 20 s. Le test vérifie son propre plafond `0.25`, pas le plafonnement interne `fminf(dt,1.f/60)`. Le message final `long_pause=20` est trompeur.

Témoin reproductible : à `frame==500`, appeler directement

```c
float before=irregular.elapsed;
l3_showcase_step(&irregular,&uneven,20.0f);
assert(irregular.elapsed-before <= 1.f/60 + 1e-6f);
```

Ici `l3_showcase_step` doit avancer d’un seul tick, pas de 15. Si le test actuel passe, il ne prouve rien sur la pause longue.

### 2. Reliquat réel au bord d’une commande : démarrage possible sur `ms=0` avec `pressed`

C’est le point le plus concret sur les 33 ms.

Séquence arithmétique, avec `dt=1/60` :

- tick n : `part=16.666… ms`, moteur reçoit `ms=16`, `pending_us=667`, `action_left=16.333… ms` ;
- tick n+1 : `part=16.333… ms`, `us=16333+667=17000`, moteur reçoit `ms=17`, `pending_us=0`, `action_left≈0` ;
- il reste `0.000333… s` dans le tick ;
- `play_timed` enchaîne alors sur `l3_arcade_demo_input`, pose la nouvelle commande et appelle `advance` avec `part=0.000333… s` ;
- dans `activities.c`, `us=lroundf(333.3)=333`, donc `ms=0` ; le moteur reçoit `pressed` avec `ms=0`, puis `s->action_pressed=0` est exécuté.

Extrait concerné : `showcase.c:80-88`, avec `s->action_pressed=0` après le premier `advance`; et `activities.c:34-39`.

Conséquence :

- si `l3_platform_step` traite l’appui indépendamment de `ms`, c’est probablement bénin ;
- si l’appui nécessite un pas moteur non nul pour être enregistré, la commande suivante — par exemple un saut de 33 ms — peut perdre frontalement son front `pressed`.

Le test ne peut pas le voir : son assertion de temps est globale au tick (`test_continuous.c:40-46`) et vérifie seulement `elapsed(after)-elapsed(before) ∈ [15,17]`. Sur le tick n+1, elle voit `+17` et passe, alors que la nouvelle commande vient d’être consommée à `ms=0`.

Preuve manquante : le code de `l3_platform_step` n’est pas dans le packet. Il faut soit l’instrumenter en test, soit ajouter un test différentiel :

1. partir du même état de plateforme ;
2. A : envoyer `pressed` avec `ms=0`, puis poursuivre ;
3. B : envoyer le même `pressed` avec `ms=1`, puis poursuivre ;
4. comparer position/vitesse/état après quelques ticks.

Si A ≠ B, le chemin `play_timed` n’est pas sûr.

Correctif minimal possible, à valider par ce test seulement : avant de démarrer une nouvelle commande, si `remaining < 0.001f`, consommer ce reliquat avec un input neutre (`advance(s,g,NULL,remaining)`) et sortir, plutôt que d’envoyer un `pressed` avec un pas sous-milliseconde. Je ne le recommande pas avant d’avoir la preuve différentielle, car le comportement exact de `ms=0` n’est pas fourni.

### 3. Reliquat terminal perdu, et test explicitement exempté

`play_timed` retourne immédiatement si le statut n’est plus `RUNNING` :

```c
if(v.status!=L3_MINI_RUNNING)return;
```

`showcase.c:79`. Le contrôle `if(remaining>.000001f)fail(...)` n’est alors pas atteint. Le commentaire « never silently lose time » est donc faux sur le tick exact de la victoire ou de la défaite : le reste du tick est abandonné silencieusement.

Le test exonère précisément ce cas :

```c
int timed=...before.status==L3_MINI_RUNNING;
...
if(timed && ... after.status==L3_MINI_RUNNING){
    assert(elapsed(after)>=elapsed(before)+15 && elapsed(after)<=elapsed(before)+17);
}
```

`test_continuous.c:40-46`. Si le jeu gagne au milieu du tick, le reliquat peut être perdu sans qu’aucune assertion ne le constate.

Ce n’est peut-être pas un blocage fonctionnel si la règle est « gel à la victoire ». Mais alors il faut le rendre explicite et retirer la revendication « temps restant consommé ». Sinon, il faut tracer ce reliquat terminal et le tester.

### 4. La cancellation n’est testée qu’au début de chaque stage

Le test de cancellation est exécuté ici :

```c
if(previous!=s.stage){
    L3Showcase copy=s; L3Game manual=g;
    l3_showcase_cancel(&copy,&manual);
    ...
}
```

`test_continuous.c:22-31`. Il intervient à l’entrée du stage, avant `play_timed`, avant `action_pending`, avant `release_inputs=0`. Il ne teste donc jamais une cancellation au milieu d’une commande temporelle, avec un reliquat d’action ou une activité arcade active.

Or `l3_showcase_cancel` ne remet pas `s->action_pending` à zéro et ne libère pas `g->activities.arcade.active` (`showcase.c:59-61`). Le test vérifie même que l’état arcade reste inchangé. C’est peut-être la politique voulue, mais elle n’est pas prouvée pour le cas « annulation pendant `play_timed` ».

Test minimal à ajouter : après l’entrée dans un stage temporel et après un tick où `s.action_pending==1`, copier `s/g`, annuler, appeler `l3_showcase_step`, puis vérifier :

- `copy.commands` et `copy.elapsed` ne bougent plus ;
- `halted.activities.arcade` est soit strictement inchangé, soit explicitement vidé selon la spec ;
- `release_inputs` ne reste pas dans un état ambigu.

### 5. Les 400 ms sont mesurés en temps simulé, pas en visibilité

L’assertion :

```c
assert(s.elapsed-last_command>=.399f);
```

`test_continuous.c:47-49`, ne vérifie pas qu’une présentation a eu lieu entre deux commandes de puzzle. Le code a bien `frames==event_frame` et `cooldown`, donc l’intention est là, mais le test ne mesure que `s.elapsed`, pas `s.frames`. Il ne prouve pas la « visibilité » à cadence de présentation faible.

Test discriminant minimal : mémoriser `last_command_frame` et vérifier que `s.frames > last_command_frame` au moins une fois après la fin de l’action, ou que le nombre de présentations entre deux commandes puzzle est ≥1.

## Preuves manquantes

- `l3_platform_step` / `l3_shooter_step` / `l3_simon_step` ne sont pas fournis : impossible de trancher le cas `pressed` avec `ms=0`.
- Aucune exécution réelle, aucun matériel : le packet le dit lui-même.
- Le résultat est sous `results_r5/result.json` ; la correspondance avec `motion_continuous_r1` doit être confirmée.
- Le test cadence 1/2/6/20 ne couvre pas les boucles et le scénario irrégulier : ce bloc est réservé à `cadence==10`. Le rapport global « all cadences » est donc plus large que la couverture réelle par cadence.

## Conclusion opérationnelle

Je ne bloque pas le principe du carry 17/33/100 ms : l’arithmétique microseconde de `activities.c` est cohérente sur les cas nominaux. Je bloque la validation des preuves :

1. corriger d’abord le test de pause 20 s ;
2. ajouter le test différentiel `ms=0` avec `pressed` pour la commande suivant un reliquat de 33 ms ;
3. rendre explicite ou tester le reliquat terminal ;
4. tester la cancellation au milieu de `play_timed`, pas seulement à l’entrée du stage.
