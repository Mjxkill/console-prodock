## Avis d’optimisation exacte pour `conseiller1024`

### 1. Faits relevés dans le code fourni

- `l3_mini_demo_input` est le conseiller déterministe. Pour `L3_MINI_MERGE1024`, il évalue les 4 directions puis appelle `merge_search(&t, 3)` :
  `source/.../l3_minigames.c`, branche `L3_MINI_MERGE1024` de `l3_mini_demo_input`.
- À chaque candidat, il fait `L3MiniState t = *s;` puis `merge_move(&t,d)`. `sizeof(L3MiniState)` est `992` octets sur l’ABI supportée, bien que le plateau merge ne comporte que `4 x 4` cellules logiques.
- `merge_search` fait récursivement `L3MiniState t = *s;` puis `merge_move` sur les 4 directions, jusqu’à `depth==0` ou état terminal.
- Le tirage est déterministe via `random32`, qui modifie `s->meta[RNG]`. Dans `merge_spawn`, l’ordre est important :
  1. premier `random32` pour la cellule libre ;
  2. second `random32` pour la valeur `2` ou `1` ;
  ainsi que `++data[0]` puis `++data[1]` si `v==2`.
- Le départage utilise strictement `>` dans `merge_search` et dans la boucle du conseiller ; l’ordre des directions `L3_MINI_UP, L3_MINI_RIGHT, L3_MINI_DOWN, L3_MINI_LEFT` compte donc pour les ex-æquo.
- La profondeur logique est : coup racine déjà joué, puis `merge_search(...,3)` explore jusqu’à 3 plis supplémentaires.
- `merge_quality` utilise déjà uniquement les 16 cellules logiques ; ce n’est pas un scan du padding.
- La validation externe (`l3_mini_validate`) reste intacte et transactionnelle pour encode/decode. Le moteur public n’est pas concerné par cette optimisation.
- Les mesures x86 `~0.030 s` pour 500 appels ne sont pas des mesures AE350. Le contexte indique AE350 à `4.3–4.9 FPS`, rendu GPU nul, `PRESENT` = `10–13 %` de l’intervalle.

### 2. Redondances identifiées

1. **Copie d’état 992 octets par nœud** alors que merge n’utilise pas :
   - `board` au-delà de 16 cellules logiques,
   - `aux`,
   - `ticks`, `phase`, `elapsed`,
   - `data` sauf `RNG` déjà dans `meta[RNG]` et le compteur de tuiles `2`,
   - le reste de `meta`.
2. **Copie répétée de l’état entier** à chaque profondeur, bien que l’état de recherche ne soit qu’un tuple compact : `RNG`, `score`, `moves`, `status`, nombre de `2`, plateau 16.
3. **Recalcul coûteux par nœud** d’une structure de 992 octets pour produire la même information que l’indicateur `moves`, nécessaire uniquement pour détecter les coups légaux (`merge_has_move`).
4. **Validation externe conservée à l’entrée** (`l3_mini_validate`), mais aucun recheck ne doit être ajouté ni retiré à l’intérieur de la recherche : il n’y a pas de coût superflu à supprimer côté moteur, seulement côté conseiller.
5. **Copies dans la branche merge du conseiller** : `L3MiniState t = *s` est inutile si l’on traduit l’état en état de recherche compact avant la boucle.

Ce qui ne doit pas changer :
- profondeur `3` après le coup racine ;
- règle `merge_slide` ;
- probabilité et ordre de RNG de `merge_spawn` ;
- départage strict `>` ;
- le fait que la recherche ne prune pas ; ajouter alpha-bêta ou élagage comporterait un risque de changement sémantique ou de complexité non nécessaire.

### 3. Optimisation proposée

Ajouter un état compact de recherche, purement statique, sans toucher à l’ABI publique :

```c
typedef struct {
    uint32_t rng;
    uint32_t score;
    uint32_t moves;
    uint32_t status;
    uint32_t twos;   /* correspond à data[1], nombre de tuiles valant 2 */
    uint8_t board[16];
} MergeSearchState;
```

L’état complet est réduit sans perte d’information pour cette heuristique parce qu’en état canonique `merge` :
- `data[0] == moves + 2` ;
- les tuiles du plateau sont uniquement dans les 4 premières lignes logiques ;
- toutes les autres valeurs sont invariantes ou dérivables.

On implémente des équivalents exacts de `merge_spawn`, `merge_slide`, `merge_has_move`, `merge_quality` et `merge_search` sur cet état compact. L’ordre des appels RNG est conservé byte pour byte. Le plateau compact utilise l’index logique `y*4+x`, avec un indexeur local équivalent à `merge_index` mais pour le plateau compact.

Point important : on ne modifie pas `merge_move`, `merge_slide`, `merge_has_move` ou la validation. Le moteur interactif et la sauvegarde restent strictement identiques.

### 4. Patch C minimal proposé

#### 4.1 Insérer avant les fonctions merge du conseiller

```c
typedef struct {
    uint32_t rng;
    uint32_t score;
    uint32_t moves;
    uint32_t status;
    uint32_t twos;
    uint8_t board[16];
} MergeSearchState;

static void merge_search_from_l3(MergeSearchState *out, const L3MiniState *s)
{
    unsigned i;

    out->rng = s->meta[RNG];
    out->score = s->meta[SCORE];
    out->moves = s->meta[MOVES];
    out->status = s->meta[ST];
    out->twos = s->data[1];
    for (i = 0u; i < 16u; ++i) out->board[i] = s->board[i];
}

static uint32_t merge_search_rng(MergeSearchState *s)
{
    uint32_t x = s->rng;

    x ^= x << 13;
    x ^= x >> 17;
    x ^= x << 5;
    s->rng = x;
    return x;
}

static unsigned merge_search_index(unsigned dir, unsigned line, unsigned pos)
{
    if (dir == 0u) return line + pos * 4u;
    if (dir == 1u) return (3u - pos) + line * 4u;
    if (dir == 2u) return line + (3u - pos) * 4u;
    return pos + line * 4u;
}
```

#### 4.2 Équivalent de `merge_spawn`

```c
static void merge_search_spawn(MergeSearchState *s)
{
    unsigned free_cells[16];
    unsigned n = 0u;
    unsigned q;
    uint8_t v;
    unsigned y, x;

    for (y = 0u; y < 4u; ++y) {
        for (x = 0u; x < 4u; ++x) {
            if (!s->board[y * 4u + x]) free_cells[n++] = y * 4u + x;
        }
    }
    if (!n) return;

    q = free_cells[merge_search_rng(s) % n];
    v = (uint8_t)((merge_search_rng(s) % 10u) == 0u ? 2u : 1u);
    s->board[q] = v;
    if (v == 2u) ++s->twos;
}
```

#### 4.3 Équivalent exact de `merge_slide`

```c
static int merge_search_slide(MergeSearchState *s, unsigned dir)
{
    unsigned line, pos;
    int changed = 0;

    for (line = 0u; line < 4u; ++line) {
        uint8_t packed[4] = {0, 0, 0, 0};
        uint8_t out[4] = {0, 0, 0, 0};
        unsigned n = 0u, k = 0u, i = 0u;

        for (pos = 0u; pos < 4u; ++pos) {
            uint8_t v = s->board[merge_search_index(dir, line, pos)];
            if (v) packed[n++] = v;
        }

        while (i < n) {
            uint8_t v = packed[i++];
            if (i < n && packed[i] == v) {
                ++i;
                ++v;
                s->score = add_sat(s->score, 1u << v);
            }
            out[k++] = v;
        }

        for (pos = 0u; pos < 4u; ++pos) {
            unsigned cell = merge_search_index(dir, line, pos);
            if (s->board[cell] != out[pos]) changed = 1;
            s->board[cell] = out[pos];
        }
    }
    return changed;
}
```

#### 4.4 Équivalents de `merge_has_move`, `merge_move` et `merge_quality`

```c
static int merge_search_has_move(const MergeSearchState *s)
{
    unsigned x, y;

    for (y = 0u; y < 4u; ++y) {
        for (x = 0u; x < 4u; ++x) {
            unsigned cell = y * 4u + x;
            unsigned v = s->board[cell];

            if (!v ||
                (x < 3u && s->board[cell + 1u] == v) ||
                (y < 3u && s->board[cell + 4u] == v)) {
                return 1;
            }
        }
    }
    return 0;
}

static int merge_search_apply(MergeSearchState *s, unsigned dir)
{
    unsigned i;

    if (!merge_search_slide(s, dir)) return 0;

    ++s->moves;
    merge_search_spawn(s);

    for (i = 0u; i < 16u; ++i) {
        if (s->board[i] == 10u) {
            s->status = L3_MINI_WON;
            return 1;
        }
    }
    if (!merge_search_has_move(s)) s->status = L3_MINI_LOST;
    return 1;
}

static int merge_search_quality(const MergeSearchState *s)
{
    unsigned x, y;
    int empty = 0, smooth = 0, mono = 0, max = 0, corner = 0;

    for (y = 0u; y < 4u; ++y) {
        for (x = 0u; x < 4u; ++x) {
            int v = s->board[y * 4u + x];
            int a, b;

            if (!v) ++empty;
            if (v > max) max = v;
            if ((x == 0u || x == 3u) && (y == 0u || y == 3u) && v > corner) corner = v;

            if (x < 3u) {
                a = s->board[y * 4u + x + 1u];
                if (v && a) {
                    b = v - a;
                    smooth -= (b < 0) ? -b : b;
                }
            }
            if (y < 3u) {
                a = s->board[(y + 1u) * 4u + x];
                if (v && a) {
                    b = v - a;
                    smooth -= (b < 0) ? -b : b;
                }
            }
        }
    }

    for (y = 0u; y < 4u; ++y) {
        int plus = 0, minus = 0;
        for (x = 0u; x < 3u; ++x) {
            int d = (int)s->board[y * 4u + x] -
                    (int)s->board[y * 4u + x + 1u];
            if (d > 0) plus += d;
            else minus -= d;
        }
        mono -= (plus < minus) ? plus : minus;
    }

    for (x = 0u; x < 4u; ++x) {
        int plus = 0, minus = 0;
        for (y = 0u; y < 3u; ++y) {
            int d = (int)s->board[y * 4u + x] -
                    (int)s->board[(y + 1u) * 4u + x];
            if (d > 0) plus += d;
            else minus -= d;
        }
        mono -= (plus < minus) ? plus : minus;
    }

    if (s->status == L3_MINI_WON) return 10000000;
    if (s->status == L3_MINI_LOST) return -10000000;
    return 1200 * empty + 220 * mono + 35 * smooth + 700 * max + 600 * corner;
}
```

#### 4.5 Recherche compacte conservant la profondeur et le départage

```c
static int merge_search_state(const MergeSearchState *s, unsigned depth)
{
    unsigned d;
    int best = INT_MIN;
    MergeSearchState t;

    if (!depth || s->status != L3_MINI_RUNNING)
        return merge_search_quality(s);

    for (d = 0u; d < 4u; ++d) {
        int value;

        t = *s;
        if (!merge_search_apply(&t, d)) continue;
        value = merge_search_state(&t, depth - 1u);
        if (value > best) best = value;
    }
    return (best == INT_MIN) ? merge_search_quality(s) : best;
}
```

### 5. Protocole différentiel déterministe

Le but est de prouver non pas une heuristique proche, mais **la même décision, le même départage et la même séquence RNG**.

#### 5.1 Deux références compilées

1. `oracle` : copie de `l3_minigames.c` avant optimisation, compilée avec renommage global des symboles, par exemple :
   `objcopy --prefix-symbols=old_ l3_minigames.o oracle_l3_minigames.o`
2. `candidate` : copie avec le patch.

Les deux sont compilées avec :
- `-std=c11 -O0 -g -fsanitize=address,undefined` pour host ;
- `-std=c11 -O2` puis `-O3` pour AE350 ;
- identiques pour les deux versions, sans modification des flags entre oracle et candidat.

Le harness appelle :
- `l3_mini_validate(state)` avant et après ;
- `l3_mini_encode` avant/après pour prouver l’octet-identité de l’état ;
- `l3_mini_demo_input(state, &pressed, &held, &dt)`.

#### 5.2 Corpus de positions

Construire un corpus deterministe et borné :

1. Balayage de seeds :
   - pour `seed` de `0` à `100000`, initialiser un jeu merge ;
   - jouer une suite de mouvements déterministes, par exemple toujours la décision de l’oracle sur l’état courant ;
   - capturer chaque état après `l3_mini_step` ;
   - ce balayage teste les états réellement accessibles avec le conseiller, y compris les victoires/défaites accessibles par decisions optimales.
2. Mutations adversariales :
   - pour chaque état canonique du balayage, muter une à plusieurs cellules du plateau `0..10`, la RNG, le score et les autres champs, puis ne garder que les états pour lesquels `l3_mini_validate(state) != 0` ;
   - inclure les positions presque pleines, les symétries, les paires adjacentes égales, les tuiles hautes dans chaque coin, et les états sans coup légal ;
   - inclure aussi des états invalides pour vérifier que les deux renvoient `0` et laissent l’état intact.
3. Séquences directes de promotion :
   - construire à la main des plateaux provoquant des fusions en cascade, pour exercer `merge_slide` sur chaque direction et sur les ordres de compactation.

#### 5.3 Assertions différentielles

Pour chaque état `S` :
- `validate_oracle(S) == validate_candidate(S)` ;
- si valide et état running :
  - `encode_oracle(S)` est identique avant et après ;
  - appel oracle puis candidat ;
  - `pressed`, `held`, `dt` sont identiques octet par octet ;
  - RNG/score/moves non mutés ;
- si non-valide ou état non-running :
  - retour `0` des deux ;
  - `S` inchangé selon empreinte d’encode.
- répéter chaque appel plusieurs fois et comparer : doit être deterministic pour un même état.
- pour détecter les divergences de RNG, instrumenter en mode debug côté oracle et candidat un compteur `rng_calls` dans `merge_spawn` et comparer les compteurs à chaque coup du conseiller : doit être identique, ainsi que la tuile éventuellement spawnée si l’on capture l’état simulé.

Cette dernière instrumentation doit rester hors production ou gardée derrière `#if MERGE_ADVISER_TRACE`, afin de ne pas changer la performance release.

#### 5.4 Tests structurels à ajouter

- `merge index table` : tester les 64 combinaisons `(dir,line,pos)` pour montrer que `merge_search_index` correspond exactement à la cellule originale `at(x,y)` pour les 4 premières lignes et colonnes.
- état de 16 cellules avec tous les exponents `0..10`, symétries, plateau plein.
- coup sans mouvement légal : retour no-op et quality racine.
- état déjà `WON` / `LOST` : retour qualité extrême et aucune mutation.
- tie synthétique : plateau où plusieurs directions donnent la même estimation, pour vérifier que c’est bien la première dans l’ordre `UP, RIGHT, DOWN, LEFT` qui l’emporte.
- CI minimal :
  - compile strict `-Wall -Wextra -Werror -pedantic -std=c11` ;
  - ASan/UBSan sur le harness de différence ;
  - vérification de non-régression de `encode/decode` autour des états testés.

### 6. MesureAE350 indispensable

La réduction de copies ne peut pas être validée uniquement sur x86. Protocole proposé :

1. Corpus fixe et stable :
   - utiliser les états capture les durant le balayage ;
   - appeler le conseiller `N` fois, par exemple `N = 500`, répété `M` fois ;
   - ne pas inclure le temps d’encode ni d’affichage dans la mesure du conseiller.
2. Environnement AE350 :
   - même outilchain et flags pour oracle et candidat ;
   - mesurer horloge CPU ou timer bare-metal, cycles si disponible, sinon microsecondes ;
   - désactiver ou rendre identique le reste de l’application ;
   - répéter à fréquence de jeu réelle : une décision environ toutes les `400 ms` selon le tutoriel/showcase, donc mesurer aussi la latence par appel et la jitter.
3. Métriques :
   - `p50`, `p99`, `max` par appel ;
   - gain en octets copiés par appel et par décision ;
   - gain cumulé sur une partie de 499 coups jusqu’à 1024 ;
   - impact sur la boucle de jeu : vérifier que la réduction adviser laisse le budget `PRESENT` intact et n’augmente pas les publications UI.
4. Budgets :
   - baseline x86 est `~0.030 s` pour 500 appels ;
   - sur AE350, la contrainte réelle est liée à la cadence `4.3–4.9 FPS` ;
   - la nouvelle optimisation doit être jugée sur sa réduction des copies, du cache et du coût récursif, pas sur une promesse de pourcentage non mesurée.
5. Si la différence n’est pas observable sur AE350 :
   - la réduction de 992 à quelques dizaines d’octets de copies par nœud reste pertinente pour cache/énergie ;
   - ne pas rajouter de complexité supplémentaire, pruning ou profondeur variable, car cela changerait la sémantique ou le risque de preuve.

### 7. Hypothèses explicites

- L’état transmis au conseiller est toujours canonique pour `L3_MINI_MERGE1024`, donc seules les 16 premières cellules logiques peuvent être non nulles hors validation explicite.
- `data[0] == moves + 2` en état valide ; la recherche n’a pas besoin de transporter ce champ.
- `meta[PHASE]`, `meta[TICKS]`, `board` hors plateau et `aux` n’influencent pas la décision merge, car `merge_slide`, `merge_spawn`, `merge_has_move`, `merge_quality` et les conditions de terminaison n’en dépendent pas.
- `random32` correspond exactement à la fonction privée fournie, avec le même xorshift et le même ordre d’opérations.
- La profondeur appelée `merge_search(&t,3)` signifie réellement trois plis supplémentaires après le coup racine ; on conserve exactement cette convention.
- Le changement est local au conseiller et au test harness ; il ne modifie pas la publication/UI, déjà optimisée à `91 %`.
- Aucune exécution réelle ni mesure n’a été effectuée ici ; les commandes données sont un protocole à exécuter dans le dépôt.

### 8. Conclusion

L’optimisation la plus défendable n’est pas de changer l’heuristique, de réduire la profondeur ou d’élaguer les branches, mais de remplacer les copies de `L3MiniState` de 992 octets par un état compact qui conserve exactement `RNG`, `score`, `moves`, `status`, nombre de tuiles `2`, plateau 16, puis de réimplémenter les mêmes règles et le même départage. La preuve doit être différentielle, seed par seed et mutation par mutation, avec contrôle des appels RNG et des octets de sauvegarde, puis une mesure réelle sur AE350 avant décision de merge.
