## Verdict

Je ne trouve pas, dans le paquet fourni, de défaut fonctionnel démontré sur les règles des moteurs ou sur l’exactitude du conseiller compact. Les contrats annoncés sont globalement cohérents avec les sources et les résultats rapportés. En revanche, il reste **deux défauts d’intégration concrets côté B** et **des trous de preuve ciblés côté A**. Je ne propose donc aucun changement de R6 ni de combinaison A+B active.

---

## 1. Faits vérifiables dans le paquet

### A. Temps continu `motion_continuous_r1`

- Dans `games/luma3d/candidates/motion_continuous_r1/src/showcase.c`, `play_timed()` :
  - boucle sur `remaining`, consulte `l3_arcade_view()` à chaque itération ;
  - appelle `l3_arcade_demo_input()` seulement quand `action_pending` est faux ;
  - refuse `!advised || ms>250` ;
  - consomme `part=fminf(remaining, action_left)` via `advance()` ;
  - décrémente `action_left` et `remaining` ;
  - échoue si un reliquat RUNNING reste après la boucle.
- Le même `play_timed()` ne consulte jamais `s->frames` : le temps des activités temporisées est donc bien indépendant de `l3_showcase_presented()`, conformément à la proposition A.
- Les états terminaux retournent avant le test de reliquat : c’est cohérent avec le commentaire « Terminal states intentionally freeze their own clock and discard the rest of this tick ».
- `l3_showcase_step()` plafonne `dt` à `1.f/60` :
  ```c
  dt=fminf(dt,1.f/60);
  ```
  Ce n’est pas un ordonnanceur : l’intégration doit fournir des ticks fixes de 1/60 s. Le test `IRREGULAR_MAIN_SCHEDULE_PASS` de `tests/test_continuous.c` simule cet accumulateur avec `while(accumulator>=1./60)`, mais **le vrai mainloop n’est pas dans le paquet**.
- `tests/test_continuous.c` vérifie notamment :
  - `zero_ms_fronts()` : comparaison état complet `0+1 ms` vs `1 ms` pour plateforme et shooter, huit graines ;
  - le delta d’activité temporisée entre 15 et 17 ms par tick de 1/60 ;
  - l’annulation en cours de commande sur les huit activités ;
  - `DIRECT_DT_GUARD_PASS` pour l’appel direct à 20 s ;
  - deux boucles et le rythme irrégulier.
- `results_r6/result.json` rapporte cinq cadences et les mêmes CRC `WON_STATE` pour les huit activités. En revanche, ce JSON ne contient **aucun enregistrement `asan_ubsan`, `rv32`, `elf_sha256` ou digest** comparable à `adviser_compact_r1/targeted_20261027_r3/result.json`. La phrase de `review_resolution.md` sur ASan/UBSan n’est donc pas vérifiable depuis ce seul JSON.

### B. Conseiller compact `adviser_compact_r1`

- `compact_proposal.h` définit une projection de 16 cases, `rng`, `score`, `moves`, `status`.
- `compact_move()` reproduit `slide`, `spawn`, `has_move`, la détection de victoire et la saturation du score via `compact_add_sat()`.
- `compact_adviser.h`, `compact_advice()` :
  - retourne `0` si `status != L3_MINI_RUNNING` ;
  - essaie les quatre directions dans l’ordre `d=0..3` ;
  - garde la première direction en cas d’égalité grâce à `if(value>best)` ;
  - ne modifie pas `s` (copies locales).
- `targeted.c` compare `merge_search()` et `compact_search()` aux profondeurs 0, 1, 2, 3, compare les états complets après `merge_move`/`compact_move`, vérifie les terminales sans mutation, les égalités, et un cas construit de saturation de score.
- `targeted_20261027_r3/result.json` rapporte :
  - `states=6004`, `checks=681917`, `ties=993`, `terminal=13`, `wins=12`, `losses=1` ;
  - même digest `df72c5e4` sur host, ASan/UBSan et RV32 ;
  - mais aussi `integrated:false`, `hardware:false`, et le test inclut directement `l3_minigames.c` :
    ```c
    #include "../../build/arcade_polish_20261026_r6/source/games/luma3d/minigames/l3_minigames.c"
    ```
    Ce n’est donc pas une preuve d’intégration au niveau lien avec l’objet R6 réel.

## 2. Défauts concrets retenus

### B1. Les en-têtes compacts ne sont pas autonomes et dépendent d’un symbole privé `keys`

Fichiers : `games/luma3d/candidates/adviser_compact_r1/compact_proposal.h`, `compact_adviser.h`.

Faits :

- `compact_proposal.h` n’a ni garde d’inclusion ni `#include <stdint.h>` / `<limits.h>`, alors qu’il utilise `uint8_t`, `uint32_t`, `UINT32_MAX`.
- `compact_adviser.h` n’a pas de garde, utilise `INT_MIN` sans `<limits.h>`, et surtout :
  ```c
  key=keys[d];
  ```
  `keys` n’est déclaré nulle part dans cet en-tête.
- Le test ne compile que parce que `targeted.c` inclut `l3_minigames.c` avant les deux en-têtes. Une intégration dans une autre unité de compilation, ou une double inclusion, casse la compilation.

C’est un défaut d’intégration concret, même si le comportement du conseiller est exact.

**Patch minimal proposé :**

```c
/* compact_proposal.h */
#ifndef L3_COMPACT_PROPOSAL_H
#define L3_COMPACT_PROPOSAL_H
#include <stdint.h>
#include <limits.h>
#include <stddef.h>
#include <string.h>

/* ... contenu existant ... */
#endif
```

```c
/* compact_adviser.h */
#ifndef L3_COMPACT_ADVISER_H
#define L3_COMPACT_ADVISER_H
#include <limits.h>
#include "compact_proposal.h"

static unsigned compact_advice(const L3CompactMergeState *s,
                               const unsigned keymap[4])
{
    unsigned key=0;
    int best=INT_MIN;
    if(s->status!=L3_MINI_RUNNING)return 0;
    for(unsigned d=0;d<4;d++){
        L3CompactMergeState next=*s;
        compact_move(&next,d);
        if(next.moves==s->moves)continue;
        int value=compact_search(&next,3);
        if(value>best){best=value;key=keymap[d];}
    }
    return key;
}
#endif
```

Appel correspondant dans `targeted.c` :

```c
unsigned compact_key=compact_advice(&c,keys);
```

Cela rend explicite l’ordre des directions et supprime la dépendance cachée à `keys`. Le patch ne change aucune règle de jeu.

**Test discriminant :**

- Test de compilation négatif : inclure deux fois `compact_proposal.h` et `compact_adviser.h` dans la même unité. Avant patch : redéfinitions. Après patch : compile.
- Test de compilation positif : appeler `compact_advice(&c, keys)` depuis une unité qui n’a pas de `keys` global. Avant patch : impossible. Après patch : possible.

### B2. La projection « 32 octets » n’est pas déterministe sur ses octets de padding

Fichier : `compact_proposal.h`.

`L3CompactMergeState` fait 32 octets sur ABI usuelle :

```c
uint8_t  board[16];   /* 16 */
uint32_t rng;         /* 16..19 */
uint32_t score;       /* 20..23 */
uint32_t moves;       /* 24..27 */
uint8_t  status;      /* 28 */
/* padding 29..31 */
```

`compact_from_l3()` écrit les champs mais pas le padding. Le test actuel ne compare jamais les 32 octets bruts. Ce n’est pas un défaut tant que la structure reste une projection interne, et `result.json` précise bien « not a save codec ». Mais si quelqu’un hashe, `memcmp` ou sérialise les 32 octets, le résultat dépend de padding non initialisé.

**Patch minimal :**

```c
static void compact_from_l3(const L3MiniState *s, L3CompactMergeState *c)
{
    memset(c, 0, sizeof *c);
    /* ... affectations existantes ... */
}
```

Et verrouiller le contrat :

```c
typedef char l3_compact_size_must_be_32[
    (sizeof(L3CompactMergeState)==32)?1:-1];
typedef char l3_compact_status_offset_28[
    (offsetof(L3CompactMergeState,status)==28)?1:-1];
```

**Test discriminant :**

```c
L3MiniState s;
L3CompactMergeState a,b;
assert(l3_mini_init(&s,L3_MINI_MERGE1024,1));
memset(&a,0xAA,sizeof a);
memset(&b,0x55,sizeof b);
compact_from_l3(&s,&a);
compact_from_l3(&s,&b);
assert(!memcmp(&a,&b,sizeof a));
```

Avant `memset(c,0,...)` dans `compact_from_l3`, ce test échoue sur le padding. Après, il passe. Cela ne fait pas de la projection un codec : si un codec est nécessaire, il faut encoder les champs explicitement, pas `memcpy` de la structure.

### A1. Point de contrat : un waypoint saute un tick de simulation

Fichier : `showcase.c`, branche de suivi de chemin dans `l3_showcase_step()` :

```c
if(d<.18f){s->point++;return;}
```

Ce retour ne consomme pas `dt` via `advance()`. `s->elapsed` et `s->stage_time` avancent, mais le jeu n’avance pas d’un tick. Pour les activités temporisées, ce n’est pas dans `play_timed()` et donc sans effet direct. Mais si le contrat « aucune perte de temps RUNNING » couvre tout le showcase, c’est une violation d’un tick par waypoint.

**Patch minimal conditionnel :**

```c
if(d<.18f){
    s->point++;
    advance(s,g,NULL,dt);
    return;
}
```

Ce patch préserve le temps mais peut modifier légèrement la trajectoire. Il ne faut l’appliquer qu’après un test qui compte les ticks de jeu ou qui compare une trajectoire de référence. Sans ce test, je le classe en point de contrat à trancher, pas en défaut bloquant.

## 3. Hypothèses et preuves manquantes

1. **Front sub-ms via l’adaptateur `l3_activity_step()`**  
   `zero_ms_fronts()` teste directement `l3_platform_step()` et `l3_shooter_step()` avec `0 ms`, pas le chemin `l3_activity_step()` qui convertit les secondes en millisecondes avec `pending_us`. La preuve existe donc au niveau moteur plateforme/shooter, pas au niveau adaptateur pour les huit activités, ni pour Simon aux frontières de phase.

2. **Commande temporisée de durée nulle**  
   Dans `play_timed()` :
   ```c
   s->action_left=ms?ms/1000.f:1.f/60;
   ```
   Si `l3_arcade_demo_input()` retourne `ms==0` pour une commande temporisée, elle est étirée à 1/60 s. Le commentaire parle pourtant d’un front à zéro ms et d’un reliquat reporté. Je ne peux pas conclure sans savoir si ce cas est réellement produit. **Pas de patch tant qu’un témoin ne l’a pas démontré.**

3. **Scheduling réel**  
   `l3_showcase_step()` plafonne `dt` à 1/60. Le test simule un accumulateur, mais le mainloop réel n’est pas fourni. Une intégration qui appellerait `l3_showcase_step()` une fois par image avec le temps mural perdrait du temps. C’est un contrat d’intégration, pas un défaut du code fourni.

4. **Intégration lien du conseiller compact**  
   `targeted.c` inclut `l3_minigames.c` directement. Il faut un test qui lie l’objet R6 et un adaptateur compact séparé, sans inclusion de `.c`, pour vérifier l’ABI, les symboles privés et l’absence de divergence de build. Le résultat actuel dit explicitement `integrated:false`.

5. **ASan/RV32 pour `motion_continuous_r1`**  
   `results_r6/result.json` ne contient pas les enregistrements ASan/UBSan/RV32. La revue ne peut pas vérifier la phrase de `review_resolution.md` à partir de ce JSON seul.

6. **Saturation de score**  
   Le test couvre un cas construit avec une seule fusion. Il manque un cas à plusieurs fusions dans le même mouvement, et un cas où le score est déjà `UINT32_MAX`. Le code `compact_add_sat()` est correct, mais la preuve reste partielle.

## 4. Plan d’intégration minimal

1. **Geler R6 et PP2.** Ne rien modifier dans `build/arcade_polish_20261026_r6`.
2. **Intégrer B d’abord, en privé.**
   - Garder `compact_proposal.h` / `compact_adviser.h` comme headers privés de l’unité moteur, ou ajouter un adaptateur privé.
   - Appliquer B1 (gardes, includes, `keymap`) et B2 (`memset`, assertions de taille).
   - Ne pas exposer la projection comme API publique ni comme codec.
   - Ajouter un test lien réel avec l’objet R6, sans inclure `l3_minigames.c`.
3. **Intégrer A ensuite, séparément.**
   - Le mainloop candidat doit appeler `l3_showcase_step(&s,&g,1.f/60.f)` dans une boucle d’accumulateur à 60 Hz.
   - `l3_showcase_presented(&s)` une fois par image rendue, pas une fois par tick.
   - Ne jamais appeler `l3_showcase_step()` avec le temps mural d’une image.
4. **Tests négatifs à exiger avant fusion :**
   - double inclusion des headers compacts ;
   - padding 0xAA/0x55 sur `L3CompactMergeState` ;
   - `compact_advice` avec `>=` au lieu de `>` : les 993 égalités doivent échouer ;
   - suppression d’un appel `compact_random32()` dans `compact_spawn()` : la comparaison d’état complet doit échouer ;
   - score proche de `UINT32_MAX` avec plusieurs fusions ;
   - front sub-ms via `l3_activity_step()` puis 1 ms, comparé à 1,4 ms ;
   - cadence réelle 10 Hz vs 60 Hz : mêmes CRC terminaux et pas de timeout ;
   - annulation au milieu d’une commande et après victoire avant `BACK`.
5. **Preuve reproductible :** ajouter au JSON de mouvement les enregistrements `host`, `asan_ubsan`, `rv32`, avec `elf_sha256` et la sortie exacte, comme pour `targeted_20261027_r3/result.json`.

Aucune conclusion FPS n’est tirée de ces éléments.
