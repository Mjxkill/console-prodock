## Verdict court

À la lecture seule du packet, je ne trouve pas de contre-exemple aux invariants de sûreté de `l3_mesh_cache_publish` dans le périmètre effectivement testé : bornes 26/28 MiB, allocation avant écriture, bitmap de validité par banque, reset, source non alignée et rejet du recouvrement sont cohérents.

En revanche, il existe un **contre-exemple réel au niveau du contrat du module** : le cache ne mémorise pas le couple `(gpu_memory, map_bytes)`. Réutiliser le même cache avec une autre mapping retourne succès sans écrire dans la nouvelle mapping.

Je distingue donc :
- **défaut de contrat du module** : rebind de mapping ;
- **limite de transaction** : `seal` publie sommets puis faces en deux appels non atomiques ;
- **limite de réouverture** : échec de `l3_mesh_cache_create()` dans `l3_render_open` laisse `active` armé ;
- **point non tranché** : ré-entrée dans le même mode après BACK, car le reset n’est fait que sur changement de mode.

Aucune source ni carte n’a été modifiée.

---

## Faits vérifiés

### 1. Validation avant allocation et avant écriture

`games/luma3d/candidates/maze_publish_cache_r1/src/mesh_cache.c:21-26` rejette avant toute allocation :

- `c == NULL`, `gpu_memory == NULL`, `source == NULL` ;
- désalignement destination `(dst & 3)` ;
- `offset` ou `bytes` non multiples de 32 ;
- `offset` hors `[BASE, BASE+2*BANK_BYTES)` ;
- dépassement de `map_bytes` ;
- dépassement de banque ;
- débordement de `dst+map_bytes` ou `src+bytes` ;
- recouvrement source/destination.

Le retour `if(!bytes)return 1;` est après cette validation (`mesh_cache.c:27`).

L’allocation est faite ensuite (`mesh_cache.c:30-35`), avant `stats.requested` (`:36`) et avant la boucle d’écriture (`:38-48`). Un échec de `realloc` retourne 0 sans écrire ni mettre à jour `capacity`, `shadow`, `valid`, `requested` ou `published`.

### 2. Bitmap de validité et doubles banques

- `valid[2][VALID_BYTES]` avec `VALID_BYTES = 1 MiB / 32 / 8 = 4096` (`mesh_cache.c:5,9`).
- `page = (offset-BASE)/BANK_BYTES`, `pos = (offset-BASE)%BANK_BYTES` (`:28`).
- `block = (pos+i)/BLOCK`, `byte = block/8`, `bit = 1U << (block%8)` (`:39`).
- La borne `bytes <= BANK_BYTES - pos` (`:24`) garantit `pos+i < BANK_BYTES`, donc `byte < 4096`.
- La capacité est suivie par banque (`capacity[2]`, `shadow[2]`), et `need = pos+bytes` (`:29`).
- La croissance se fait par doublement à partir de 128 KiB (`:31-32`), avec `need <= 1 MiB`, donc pas de débordement pratique de `cap`.

### 3. Reset et destruction

- `l3_mesh_cache_reset` ne fait que `memset(c->valid,0,sizeof c->valid)` (`mesh_cache.c:13`) ; il conserve `shadow` et `capacity`, ce qui est cohérent avec un cache réutilisable.
- `l3_mesh_cache_destroy` libère les deux shadows puis le cache (`:14`).
- Dans le chemin fourni, le cache est créé à l’ouverture (`games/luma3d/build/maze_publish_cache_20261027_r2/source/games/luma3d/src/render.c:155`) et détruit à la fermeture (`:481`).
- `l3_mesh_cache_reset` est appelé sur changement de mode (`render.c:308`).

### 4. Tests fournis

Le packet rapporte :

- 1600 cas, 6 invalides, 1 échec d’allocation, égalité mémoire complète (`tests/test_cache.c:19-55`, `tests/results_r2/result.json:19,38`) ;
- source non alignée (`test_cache.c:22`) ;
- reset puis republication (`test_cache.c:24,51-53`) ;
- traversée de frontière de banque rejetée (`test_cache.c:40`) ;
- recouvrement source/destination rejeté (`test_cache.c:42`) ;
- `map_bytes` trop court rejeté (`test_cache.c:43`) ;
- échec de `realloc` initial (`test_cache.c:47-48`) ;
- ASan/UBSan activés, LSan désactivé car ptrace non supporté (`result.json:31,47`).

Je ne prétends pas avoir exécuté ces tests : ce sont les résultats rapportés par le packet.

## Contre-exemple réel au niveau module : rebind de `gpu_memory`

### Code actuel

Le cache ne stocke ni `gpu_memory` ni `map_bytes`. La validité d’un bloc est donc associée uniquement à `(page, offset)`, pas à la destination physique.

Si on publie une première fois vers `a`, puis la même source vers `b` avec le même cache :

- la validation passe ;
- `need <= capacity` donc pas de `realloc` ;
- le bit `valid` est déjà à 1 ;
- `memcmp(old, source, 32) == 0` (`mesh_cache.c:43`) ;
- `continue` : aucune écriture vers `b` ;
- la fonction retourne 1 (`:49`).

### Test exécutable proposé

Fichier `test_rebind.c` à compiler avec `src/mesh_cache.c` :

```c
#include "l3_mesh_cache.h"
#include <assert.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

enum { MAP = 29U << 20, OFF = 26U << 20 };

int main(void) {
    unsigned char *a = malloc(MAP), *b = malloc(MAP);
    unsigned char src[32];
    assert(a && b);
    memset(a, 0xa5, MAP);
    memset(b, 0xa5, MAP);
    memset(src, 0x5a, sizeof src);

    L3MeshCache *c = l3_mesh_cache_create();
    assert(c);

    assert(l3_mesh_cache_publish(c, a, MAP, OFF, src, sizeof src));
    assert(!memcmp(a + OFF, src, sizeof src));

    /* Deuxième mapping, même cache : le code actuel retourne 1... */
    assert(l3_mesh_cache_publish(c, b, MAP, OFF, src, sizeof src));

    printf("b_written=%d\n", !memcmp(b + OFF, src, sizeof src));

    /* ...mais n'écrit pas dans b. Cette assertion échoue avec le code actuel. */
    assert(!memcmp(b + OFF, src, sizeof src));

    l3_mesh_cache_destroy(c);
    free(a);
    free(b);
    return 0;
}
```

Commande indicative, non exécutée ici :

```sh
cc -std=c11 -I games/luma3d/candidates/maze_publish_cache_r1/include \
   test_rebind.c \
   games/luma3d/candidates/maze_publish_cache_r1/src/mesh_cache.c \
   -o /tmp/test_rebind
```

### Portée exacte

Ce n’est pas une régression du chemin `render` fourni, car `render.c:155` crée un cache neuf et `:481` le détruit. Le test `test_cache.c` n’utilise qu’une seule `memory` (`test_cache.c:16,25`), donc ne couvre pas ce cas.

Mais si le module est destiné à être réutilisé après réouverture avec une nouvelle mapping sans `destroy/create`, le comportement est faux : succès retourné, aucune publication. C’est aussi le cas si un autre producteur écrit dans 26/27 MiB : le cache suppose l’exclusivité, mais ne le vérifie pas.

### Patch minimal

Ajouter une liaison au mapping et invalider le bitmap si elle change :

```c
struct L3MeshCache {
    unsigned char *shadow[2];
    size_t capacity[2];
    unsigned char valid[2][VALID_BYTES];
    uintptr_t gpu_base;
    size_t gpu_bytes;
    L3MeshCacheStats stats;
};
```

Dans `l3_mesh_cache_publish`, après `if(!bytes)return 1;` :

```c
if (c->gpu_base &&
    (c->gpu_base != dst || c->gpu_bytes != map_bytes))
    memset(c->valid, 0, sizeof c->valid);

c->gpu_base = dst;
c->gpu_bytes = map_bytes;
```

Cela conserve le chemin rapide quand la mapping est identique, et force la réécriture après rebind. Un test discriminant complémentaire doit vérifier que, sur la même mapping, la seconde publication de la même source ne change pas `published` (le cache saute bien), alors qu’après rebind elle écrit.

## Limite de transaction : `seal` n’est pas atomique

`games/luma3d/build/maze_publish_cache_20261027_r2/source/games/luma3d/src/maze_render.c:27-28` publie :

1. les sommets avec `l3_mesh_cache_publish(..., b->v, b->nv*32)` ;
2. les faces avec `l3_mesh_cache_publish(..., b->f, b->nf*32)`.

Chaque appel respecte bien « allocation avant écriture » pour lui-même. Mais si le premier appel réussit et que le second échoue sur `realloc`, les sommets sont déjà écrits dans la mémoire GPU et dans le shadow, les faces ne le sont pas, et `seal` retourne 0.

Test concret dans le banc existant, après le hook `test_cache.c:7-11` :

```c
static void test_partial_seal(void) {
    unsigned char *m = malloc(MAP), *r = malloc(MAP);
    unsigned char v[32] = {1}, f[32] = {2};
    memset(m, 0xa5, MAP);
    memcpy(r, m, MAP);
    L3MeshCache *c = l3_mesh_cache_create();

    /* alloue 128 KiB et écrit les sommets */
    assert(l3_mesh_cache_publish(c, m, MAP, 26U << 20, v, 32));

    /* force l'échec de l'allocation pour les faces */
    fail_realloc = 1;
    assert(!l3_mesh_cache_publish(c, m, MAP,
                                  (26U << 20) + 128U * 1024, f, 32));

    assert(!memcmp(m + (26U << 20), v, 32));          /* sommets écrits */
    assert(m[(26U << 20) + 128U * 1024] == 0xa5);     /* faces non écrites */
}
```

Ce n’est pas un défaut de `l3_mesh_cache_publish` pris isolément. C’est une limite si `seal` doit être transactionnel : il faudrait réserver les deux capacités avant la première écriture, ou publier sommets+faces en une seule opération.

## Limite de réouverture : `active` armé avant la création du cache

Dans `render.c` :

- `active=r;gpu_v1_init(...)` à `:153` ;
- `r->mesh_cache=l3_mesh_cache_create();if(!r->mesh_cache)return 0;` à `:155`.

Si `l3_mesh_cache_create()` échoue, la fonction retourne 0 sans remettre `active=NULL`. Le prochain `l3_render_open` échoue alors sur le contrôle « Only one GPU producer allowed » (`render.c:73`). C’est un problème de réouverture sous OOM, distinct du cache lui-même.

Correctif minimal possible : créer le cache avant `active=r`, ou sur ce chemin faire le nettoyage et `active=NULL`. Un test de fault injection sur `calloc` est nécessaire ; il n’est pas fourni dans le packet.

---

## Point non tranché : ré-entrée dans le même mode après BACK

`l3_mesh_cache_reset` n’est appelé que si `r->activity_mode != mode` (`render.c:308`). Le chemin monde, quand `g->activities.arcade.active == 0`, ne remet pas `r->activity_mode` à zéro et ne reset ni le cache ni `maze_static_count`.

Conséquence :
- les blocs dynamiques sont normalement corrigés par `memcmp`/écriture ;
- mais `maze_static_count` et les bits de validité ne sont pas réinitialisés lors d’une ré-entrée dans le **même** mode après BACK.

Le packet ne démontre pas de contre-exemple sur ce point : `tests/compare_render.c:23` contient `4` deux fois, mais pas consécutivement après un BACK, et chaque `k` recrée un `L3Game` (`:27`). Il manque un test « mode X → BACK → ré-entrée mode X avec géométrie statique différente ». Si la géométrie statique est immuable par mode, ce n’est pas un bug ; sinon, c’est un risque réel.

Je ne mélange pas ce point avec les numéros de mode : le défaut de rebind ci-dessus est indépendant de `kind`/`mode`.

---

## Ce que le packet ne prouve pas

- **Pas de test de croissance `realloc` après capacité non nulle** : le seul échec d’allocation testé est le premier, capacité 0 (`test_cache.c:46-48`). Le code paraît correct, mais ce cas n’est pas couvert par le test rapporté.
- **Pas de test de la banque 1 après allocation de la banque 0** : les 1600 cas alternent les pages, mais l’échec d’allocation n’est testé qu’une fois sur un cache neuf.
- **Pas de test de rebind de mapping** : c’est le contre-exemple ci-dessus.
- **Pas de test d’atomicité `seal`** : sommets/faces en deux appels.
- **Pas de test de ré-entrée même mode après BACK**.
- **Pas de preuve d’exclusivité des écritures 26/27 MiB** : le cache ne lit jamais la mémoire GPU pour vérifier ; il suppose que personne d’autre n’écrit dans ces banques. Le packet ne fournit pas l’inventaire exhaustif des écrivains.
- **LSan non exécuté** (`result.json:47`) : l’absence de fuite n’est pas prouvée par LSan.
- **Pas de carte** : `hardware:false`.

Enfin, je ne confonds pas les compteurs : `requested` compte les octets demandés (`mesh_cache.c:36`), `published` les blocs de 32 octets réellement écrits (`:47`), `compared` les blocs comparés (`:42`), et `allocated` la croissance cumulée de capacité (`:34`), non réduite par `reset`. Le « 256 KiB alloués » rapporté n’est donc pas une mesure d’octets évités ni une couverture des zones non écrites.

---

## Conclusion

- **Dans le périmètre testé**, je ne vois pas de dépassement de borne, d’écriture après échec d’allocation dans un même appel, ni d’erreur de bitmap par banque.
- **Contre-exemple réel au niveau module** : réutilisation du cache avec un autre `gpu_memory`/`map_bytes` ; succès retourné sans publication. Test `test_rebind.c` fourni.
- **Si le contrat est « un cache = une mapping »**, il faut le documenter et l’asserter ; le chemin `render` fourni respecte déjà ce contrat par `create`/`destroy`.
- **Si le module doit être réutilisable après réouverture**, le patch de liaison/invalidation ci-dessus est nécessaire.
- **Limites restantes** : atomicité de `seal`, réouverture sous OOM, ré-entrée même mode après BACK, et absence de preuve d’exclusivité des écritures 26/27 MiB.
