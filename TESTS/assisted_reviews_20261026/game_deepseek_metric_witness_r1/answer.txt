## Contre-exemples concrets à la normalisation

Les numéros de ligne ne sont pas fournis dans le paquet ; je cite les assertions exactes de `summarize_trial.py`, fonction `normalize_activity`.

### 1. `max_frame` incohérent avec `frame_sum` accepté

En partant de `parsed[0]` du mode 0 :

```python
bad = dict(parsed[0])
bad["max_frame"] = 100.0
```

`normalize_activity(bad)` passe les assertions actuelles :

- `measured = .703+.404+.505+.606 = 2.218 <= 2.420` ;
- `max_frame + 0.0001 >= frame_sum/frames` : `100 >= 0.02396` ;
- percentiles et compteurs inchangés, donc valides.

Pourtant un maximum de 100 s est impossible avec `frame_sum=2.420 s`. La normalisation produit `max_interval_ms=100000` sans erreur.

### 2. `over_1020ms` incohérent avec `max_frame` et les percentiles accepté

```python
bad = dict(parsed[0])
bad["over_1020ms"] = 101
bad["over_33ms"] = 101
```

Assertions actuelles :

- `0 <= 101 <= 101 <= 101` : passe ;
- `max_frame + 0.0001 >= mean` : `.420 >= .02396` : passe ;
- `p95=24`, `p99=24`, `p99_overflow=0` : passe.

Le rapport prétend donc que 101/101 frames dépassent 1 020 ms, tout en gardant `max_frame=420 ms` et `p99_upper=24 ms`. C’est impossible.

### 3. Borne de percentile incompatible avec `max_frame`

```python
bad = dict(parsed[0])
bad["p95_upper_ms"] = 1020
bad["p99_upper_ms"] = 1020
bad["max_frame"] = 0.024
```

`max_frame=0.024` satisfait juste `max_frame >= frame_sum/frames = .02396`. La normalisation accepte `p95_upper_ms=1020`, alors qu’une borne de tranche à 1 020 ms implique au moins une frame dans `[1016,1020)` ms, donc `max_frame >= 1.016 s`. Il n’y a aucune assertion croisant `max_frame` et les bornes p95/p99.

## Trois corrections minimales

### Correction 1 — Croiser `max_frame`, `over_*` et percentiles dans `normalize_activity`

Ajouter après les assertions existantes :

```python
    assert item["max_frame"] <= interval + 0.0001
    if item["over_1020ms"]:
        assert item["max_frame"] >= 1.02 - 1e-9
    if item["over_33ms"]:
        assert item["max_frame"] > 1.0/30.0 - 1e-9
    if item["over_1020ms"] * 100 > n * 5:
        assert item["p95_overflow"]
    if item["over_1020ms"] * 100 > n:
        assert item["p99_overflow"]
    if not item["p95_overflow"]:
        assert 1000 * item["max_frame"] + 4 + 1e-6 >= item["p95_upper_ms"]
    if not item["p99_overflow"]:
        assert 1000 * item["max_frame"] + 4 + 1e-6 >= item["p99_upper_ms"]
```

Tests discriminants à ajouter dans `test_metric_windows.py` :

- `max_frame = frame_sum + 1` doit lever ;
- `over_1020ms = frames`, `p99_overflow=0` doit lever ;
- `p95_upper_ms=1020`, `max_frame=0.024` doit lever.

Ces trois cas passent actuellement, donc ce sont de vrais contre-exemples, pas seulement des tests manquants.

### Correction 2 — Vérifier `max_sprites`, `max_layers`, `max_draws`

Dans `test_metric_windows.py`, la boucle :

```python
for name,j in [("simulation",2),...,("triangles",10)]:
    eq(d[name], sum(s[j] for s in ss))
```

n’inclut pas les trois maxima. Un accumulateur qui renverrait `max_layers=0` ou `max_sprites=0` pour le mode 7 passerait donc tous les tests actuels, alors que `producer.log` donne `max_sprites=24`, `max_layers=4`.

Ajouter :

```python
  eq(d["max_sprites"], max(s[11] for s in ss))
  eq(d["max_layers"], max(s[12] for s in ss))
  eq(d["max_draws"], max(2 if s[10] else 0 for s in ss))
```

C’est une correction de test, pas une optimisation de rendu.

### Correction 3 — Empêcher `summarize_trial.py` de promouvoir un résultat synthétique en hardware

Dans `summarize_trial.py`, le `main` fait :

```python
r=json.loads(a.result.read_text())
assert r['passed'] and r['tour']['completed']
...
out=dict(passed=True,hardware=True,...)
```

Le drapeau `hardware` du résultat source n’est jamais vérifié. Un JSON synthétique avec `passed=true`, `hardware=false` et un `tour.completed=true` serait publié avec `hardware=True`.

Patch minimal :

```python
r=json.loads(a.result.read_text())
assert r.get("hardware") is True, "rapport non matériel : pas de FPS hardware"
assert r["passed"] and r["tour"]["completed"]
...
out=dict(passed=True, hardware=r["hardware"], ...)
```

## Preuves manquantes / limites

- Les tests sont synthétiques : aucun FPS hardware, aucune exécution du jeu ni du rendu.
- Le sous-ensemble `adviser <= simulation` n’est vérifié qu’au niveau agrégé par mode ; aucun test ne prouve l’attribution par frame. Les échantillons fournis sont cohérents (`mode 7 : .501 <= .503`), mais ce n’est pas une preuve générale.
- Les transitions ne sont testées que vers les modes 0, 4, 7 et 8 ; aucun échantillon de transition vers 1, 2, 3, 5 ou 6.
- Les percentiles sont bien des bornes de tranches de 4 ms, pas des valeurs exactes. Le libellé `p95 ≤ 24` pour des frames à 20 ms est correct ; le risque identifié est qu’une borne incohérente soit acceptée par la normalisation.
