## Verdict court

Le cœur du calcul est sain sur plusieurs points : bins de 4 ms correctement bornés, sentinelle d’overflow cohérente, cumuls `bytes/commands/batches/triangles` en 64 bits, et balayage p95/p99 avec casts `uint64_t` avant multiplication. En revanche, l’audit met en évidence **quatre problèmes concrets d’attribution ou de valeur publiée**, plus plusieurs points de normalisation/sémantique qui rendent les chiffres faciles à mal interpréter. Aucun test n’a été exécuté ici et aucun gain FPS matériel n’est revendiqué.

Fichiers cités : `games/luma3d/candidates/arcade_polish_r1/src/main.c` (SHA `fd989e…b85f153`) et `games/luma3d/candidates/arcade_polish_r1/include/luma3d_render.h` (SHA `a4f458…e4371`). Le paquet ne contient pas de numéros de ligne ; les ancres ci-dessous sont des extraits/identifiants exacts.

## 1. Faits, hypothèses, preuves manquantes

**Faits observables dans le paquet**
- `activity_cost[9]` contient bien `bytes/commands/batches/triangles` en `unsigned long long`, et les deltas 32 bits y sont ajoutés.
- Le bin est calculé ainsi : `unsigned bin=frame>=1.02?255:(unsigned)(frame*250);` — 250 = 1000/4, donc bins de 4 ms, bin 255 = overflow ≥ 1020 ms.
- p95/p99 : `if(!p95&&(uint64_t)total*100>=(uint64_t)frames*95) p95=(bin+1)*4;` — comparaison en 64 bits, pas de débordement 32 bits dans cette expression.
- Le reset benchmark remet à zéro `activity_cost`, `geometry_cycles_total`, `measured_frame`, `report_frames`, `report_commands`, `measured_batches`, `measured_feed`, `measured_present`, puis `start=previous=report=last_frame_done=seconds()`.
- Le test CLI existant vérifie `cost.frames==count`, `cost.commands==result.commands`, `cost.batches==result.batches`, la forme des percentiles et `frame_sum>=max_frame`. Il ne vérifie ni `feed`, ni `present`, ni `bytes`, ni `max_layers`, ni la cohérence p95/p99/max.

**Hypothèses à confirmer avec `luma3d_render.c` / `prodock-uapi.h`**
- `renderer.mini_bytes` est cumulatif et peut être remis à zéro lors d’un changement de mode/page UI.
- `feed_seconds` et `present_seconds` mesurent des intervalles **disjoints** (sinon `preparation` est négatif).
- `renderer.triangles` est un compteur **par frame**, pas cumulatif.
- `renderer.last_scene.layers` a au moins 12 entrées et au moins 7 octets par entrée.
- `renderer.frame` s’incrémente exactement de 1 par frame.
- Les compteurs uapi `display.feed_us` etc. sont sur 32 bits et peuvent wrapper.

**Preuves manquantes**
- `luma3d_render.c` : sites d’incrément de `mini_bytes`, `hud_bytes`, `shooter_upload_bytes`, reset éventuel de `commands/draws/triangles`, localisation exacte des timers `feed/present`.
- `prodock-uapi.h` : dimension de `struct prodock_scene.layers`.
- Largeur réelle des compteurs kernel `cycles`, `feed_us`, `wait_us`, `cache_us`, `present_us`.
- Toute exécution matérielle.

## 2. Constats concrets et corrections minimales

### P1 — `ui_bytes` peut exploser à ~4,29 milliards si `mini_bytes` décroît

Ancre, bloc `if(mode_cost<9)` :

```c
activity_cost[mode_cost].bytes+=(uint32_t)(renderer.mini_bytes-bytes_before);
```

`renderer.mini_bytes` est `unsigned` (32 bits, y compris sur RV32). Si le renderer le remet à zéro ou le réinitialise lors d’un changement de mode, la soustraction non signée donne `0xFFFFxxxx` : `bytes` gagne ~4,29e9 d’un coup, puis `ui_bytes=%llu` publie une valeur absurde. Le cast `(uint32_t)` ne protège pas : il rend juste le modulo explicite.

La soustraction modulaire est correcte pour un **wrap** monotone, mais pas pour un **reset**. Sans compteur de génération, les deux cas sont indiscernables côté `main.c`.

**Correction minimale recommandée** : exposer un cumul 64 bits côté renderer.

Dans `luma3d_render.h`, ajouter par exemple :

```c
uint64_t mini_bytes_total;   /* cumul 64 bits, jamais remis à zéro */
```

Aux sites d’incrément de `mini_bytes` (non fournis dans le paquet), faire aussi :

```c
r->mini_bytes_total += (uint32_t)n;
```

Puis dans `main.c` :

```c
uint64_t mini_now = renderer.mini_bytes_total;
uint64_t mini_delta = mini_now - bytes_before;   /* monotone, sûr en 64 bits */
activity_cost[mode_cost].bytes += mini_delta;
bytes_before = mini_now;                          /* adapter le type de bytes_before */
```

À défaut, guard minimal mais moins propre :

```c
uint32_t mini_now = renderer.mini_bytes;
uint32_t mini_delta = (uint32_t)(mini_now - bytes_before);
if (mini_now < bytes_before) {           /* reset probable, wrap réel rare */
    mini_delta = 0;
    activity_cost[mode_cost].bytes_resets++;
}
activity_cost[mode_cost].bytes += mini_delta;
```

Cette seconde version perd le delta d’un wrap réel ; à ne retenir que si `mini_bytes` ne peut pas dépasser 2^32 pendant la fenêtre mesurée.

**Test discriminant** : injecter la séquence `mini_bytes = 1000, 2000, 0, 500` sur quatre frames mesurées. Attendu après correction : `ui_bytes = 2500` et `ui_bytes_resets = 1`. Le code actuel produit `1000 + 1000 + 4294968296 + 500`.

### P1 — `simulation` inclut la sauvegarde disque et le timeout showcase

Ancre :

```c
double sim_started=seconds(),adviser_started=tour.adviser_seconds;
...
else { ... l3_game_step(...); }
if(save_path&&((game.story.revision!=saved_revision&&now-last_save>=2)||now-last_save>=15)) {
    if(l3_progress_write(...)!=L3_PROGRESS_OK) { ... }
    ...
}
if(tour.status==1&&now-tour_started>3600) { ... }
double sim_elapsed=seconds()-sim_started,render_started=seconds();
```

`sim_elapsed` est arrêté **après** l’écriture de sauvegarde et le contrôle de timeout. Une écriture disque bloquante est donc attribuée à `simulation`, alors qu’elle n’a rien à voir avec la simulation. En interactif, cela peut produire un pic de `simulation` et fausser toute comparaison avec `preparation`.

**Correction minimale** : arrêter le chrono juste après le dispatch `l3_game_step`/`l3_showcase_step`, avant la sauvegarde.

```c
double sim_started=seconds(),adviser_started=tour.adviser_seconds;
...
/* fin du dispatch simulation */
double sim_done=seconds();

double save_started=0;
if(save_path&&...) { save_started=seconds(); ... }
double save_elapsed=save_started?seconds()-save_started:0;

double sim_elapsed=sim_done-sim_started, render_started=seconds();
```

Puis, si l’on veut une comptabilité complète, ajouter un champ `persistence` à `activity_cost` et l’alimenter avec `save_elapsed`. Sinon, la sauvegarde tombera dans le résidu non attribué de l’intervalle (voir P2).

**Note** : `double sim_elapsed=...,render_started=seconds();` a en outre un ordre d’évaluation non spécifié entre les deux initialisateurs. Séparer les déclarations est plus déterministe.

### P1 — Les rapports 5 s contaminent p95/p99/max/over_33ms

Ancre :

```c
if(!host&&(!benchmark||measured_frame)&&finished-report>=5) {
    printf("LUMA3D_PERF ...");
    ...
    if(ioctl(renderer.fd,PRODOCK_GEOMETRY_INFO,&gpu)||ioctl(renderer.display,PRODOCK_DISPLAY_INFO,&display)) ...
}
```

Ce bloc s’exécute **après** `last_frame_done=frame_done` et après l’enregistrement des compteurs. Son temps (deux ioctls + `printf`, potentiellement lent sur console série) est donc inclus dans l’intervalle completion-to-completion de la **frame suivante**, mais n’est attribué ni à `prepare`, ni à `feed`, ni à `present`. Il gonfle donc `max_frame`, `over_33ms`, `over_1020ms` et éventuellement p95/p99, sans apparaître dans la décomposition.

En benchmark, ce rapport périodique est redondant avec `LUMA3D_BENCHMARK_COUNTERS` et les lignes `LUMA3D_ACTIVITY_COST`.

**Correction minimale** : le supprimer en benchmark.

```c
if(!host&&!benchmark&&finished-report>=5) { ... }
```

Alternative si l’on tient à un rapport périodique : marquer la frame suivante comme « report frame » et l’exclure du histogramme/max, avec un compteur `excluded_report_frames` ; mais cela complique l’égalité `cost.frames==count` et les tests.

**Test discriminant** : avec une horloge factice et `L3_TEST_REPORT_COST_MS=200`, une frame de 100 ms suivie d’un rapport doit donner `max_frame≈0,100 s` après correction ; avant correction, le rapport injecte 200 ms dans l’intervalle suivant et `max_frame≈0,300 s`.

### P1 — Échec pendant le warmup : `frames=` peut être non nul alors qu’aucune mesure n’a commencé

Ancre :

```c
unsigned completed=renderer.frame-measured_frame;
if(benchmark&&(!measured_frame||completed!=frames))ok=0;
```

Si `l3_render_frame` échoue **avant** le reset benchmark, `measured_frame` reste à 0 et `completed=renderer.frame` vaut le nombre de frames de warmup déjà rendues. Le programme imprime alors `LUMA3D_RESULT frames=2` (par exemple) avec `ok=0`. C’est trompeur pour tout parseur qui interprète `frames` comme « frames mesurées ».

**Correction minimale** :

```c
unsigned completed=(benchmark&&!measured_frame)?0:renderer.frame-measured_frame;
```

**Test discriminant** : `L3_TEST_FAIL_SUBMIT=1` (échec au tout premier submit, donc pendant le warmup) → attendu : code retour 1, `LUMA3D_RESULT frames=0`, aucune ligne `LUMA3D_ACTIVITY_COST` avec `frames>0`. Le code actuel imprime probablement `frames=warmup`.

### P2 — Aucune normalisation par frame : les totaux inter-modes ne sont pas comparables

Ancre, ligne `LUMA3D_ACTIVITY_COST` : `simulation=%.6f adviser=%.6f preparation=%.6f submit=%.6f present=%.6f ...` puis `commands=%llu batches=%llu triangles=%llu`.

`simulation`, `preparation`, `submit`, `present`, `commands`, `batches`, `triangles`, `ui_bytes` sont des **sommes**. Deux modes avec des nombres de frames différents ne peuvent pas être comparés directement. Or `frames=%u` est présent, mais l’analyse de fluidité compare souvent des lignes sans renormaliser.

De plus, `adviser` est un **sous-ensemble** de `simulation`. Si un consommateur additionne les colonnes, il double-compte l’advice. Ce n’est pas un double comptage interne, mais un piège d’interprétation.

**Correction minimale, sans casser les clés existantes** :

```c
double inv=activity_cost[k].frames?1.0/activity_cost[k].frames:0.0;
double attributed=activity_cost[k].sim+activity_cost[k].prepare
                 +activity_cost[k].feed+activity_cost[k].present;
double unattributed=activity_cost[k].frame_sum-attributed;
printf("... frames=%u simulation=%.6f simulation_ms_per_frame=%.6f "
       "adviser_subset=%.6f adviser_ms_per_frame=%.6f "
       "preparation=%.6f preparation_ms_per_frame=%.6f "
       "submit=%.6f submit_ms_per_frame=%.6f "
       "present=%.6f present_ms_per_frame=%.6f "
       "frame_mean_ms=%.6f unattributed_ms=%.6f unattributed_negative=%d ...",
       ...,
       activity_cost[k].sim,
       activity_cost[k].sim*inv*1000.0,
       activity_cost[k].adviser,
       activity_cost[k].adviser*inv*1000.0,
       activity_cost[k].prepare,
       activity_cost[k].prepare*inv*1000.0,
       activity_cost[k].feed,
       activity_cost[k].feed*inv*1000.0,
       activity_cost[k].present,
       activity_cost[k].present*inv*1000.0,
       activity_cost[k].frame_sum*inv*1000.0,
       unattributed*1000.0,
       unattributed < -1e-9,
       ...);
```

Renommer ou documenter `adviser` comme `adviser_subset` ; ne jamais le sommer à `simulation`.

**Note unités** : `max_frame=%.6f` est en secondes, alors que `p95_upper_ms`/`p99_upper_ms` sont en millisecondes. Ajouter `max_frame_ms=%.3f` (ou renommer `max_frame_s`) évite les erreurs de lecture.

### P2 — `preparation` peut devenir négatif si `feed` et `present` se recouvrent

Ancre :

```c
activity_cost[mode_cost].prepare+=frame_done-render_started-feed_delta-present_delta;
```

Cette formule suppose que `feed_seconds` et `present_seconds` sont des sous-intervalles **disjoints** de `[render_started, frame_done]`. Si `present` englobe un `flush` (donc un `PRODOCK_SUBMIT` déjà mesuré dans `feed`), le submit est soustrait deux fois et `preparation` peut devenir négatif. Le code ne teste jamais `prepare>=0`.

**Correction de diagnostic minimale** :

```c
double prep=frame_done-render_started-feed_delta-present_delta;
if(prep<0&&prep>-1e-6)prep=0;          /* bruit d’horloge */
if(prep<0)activity_cost[mode_cost].negative_prepare++;
activity_cost[mode_cost].prepare+=prep;
```

Puis publier `negative_prepare`. La vraie correction dépend de `luma3d_render.c` : il faut garantir que les timers ne s’imbriquent pas, ou mesurer `present` hors du `flush`.

**Test discriminant** : injecter uniquement un coût sur `SUBMIT` et vérifier que `present` ne bouge pas ; puis uniquement sur `PRESENT` et vérifier que `feed` ne bouge pas. Enfin, vérifier `prepare>=0` et `sim+prepare+feed+present<=frame_interval`.

### P2 — `ui_bytes` ne mesure que `mini_bytes`, pas tous les octets UI publiés

Ancre : `renderer.mini_bytes` est utilisé, alors que le header expose aussi `hud_bytes`, `shooter_upload_bytes`, `mini_uploads`, `hud_uploads`. Le nom `ui_bytes` suggère un total UI ; ce n’est pas le cas.

**Correction minimale** : soit renommer `mini_ui_bytes`, soit additionner explicitement les deltas pertinents :

activity_cost[mode].bytes += delta64(renderer.mini_bytes_total, mini_before);
activity_cost[mode].bytes += delta64(renderer.hud_bytes_total, hud_before);
activity_cost[mode].bytes += delta64(renderer.shooter_upload_bytes_total, shooter_before);

Il faut d’abord vérifier la sémantique exacte de `mini_bytes`/`hud_bytes` dans `luma3d_render.c` (upload réel ou simple compteur logique, déduplication éventuelle).

### P2 — `max_layers` code en dur 12 : risque de lecture hors bornes

Ancre :

```c
unsigned layers=0;for(unsigned layer=0;layer<12;layer++)layers+=!!(renderer.last_scene.layers[layer][6]&1);
```

Si `struct prodock_scene.layers` a moins de 12 entrées, ou moins de 7 octets par entrée, c’est un accès hors bornes (UB). Le paquet ne fournit pas `prodock-uapi.h`.

**Correction minimale, si `layers` est un tableau** :

```c
#define L3_SCENE_LAYER_COUNT \
    (sizeof(((struct prodock_scene*)0)->layers)/sizeof(((struct prodock_scene*)0)->layers[0]))
...
for(unsigned layer=0;layer<L3_SCENE_LAYER_COUNT;layer++)
    layers+=!!(renderer.last_scene.layers[layer][6]&1);
```

Sinon, exposer une constante publique dans `prodock-uapi.h` et l’utiliser. À défaut, ajouter un test de compilation statique (`_Static_assert`) sur la dimension.

### P3 — `bin` : conversion `NaN` vers `unsigned` non définie

Ancre :

```c
double frame=frame_done-last_frame_done;
unsigned bin=frame>=1.02?255:(unsigned)(frame*250);
```

Si `frame` est `NaN` (horloge non initialisée, erreur `clock_gettime` non vérifiée), `frame>=1.02` est faux et `(unsigned)(NaN*250)` est un comportement indéfini. En pratique `CLOCK_MONOTONIC` ne devrait pas échouer, mais `seconds()` ne vérifie pas le retour de `clock_gettime`.

**Correction minimale** :

```c
unsigned bin;
if (!(frame < 1.02)) bin=255;          /* couvre NaN et >= 1.02 s */
else if (frame <= 0.0) bin=0;
else bin=(unsigned)(frame*250.0);
```

Et, si l’on veut être strict, faire retourner `NAN` ou `abort()` à `seconds()` en cas d’échec de `clock_gettime`.

### P3 — `over_33ms` ne correspond pas au seuil annoncé

Ancre : `if(frame>1.0/30)activity_cost[mode_cost].slow_frames++;` puis `over_33ms=%u`.

`1.0/30 = 33,333… ms`. Une frame de 33,2 ms n’est donc pas comptée, alors que le nom `over_33ms` suggère `> 33,0 ms`. Ce n’est pas un bug de calcul, mais une ambiguïté de contrat.

**Correction minimale** : soit utiliser `frame>0.033`, soit renommer la clé `over_33_33ms` / `over_30fps_budget`. Garder la constante dans une seule définition :

```c
#define L3_SLOW_FRAME_S (1.0/30.0)
if(frame>L3_SLOW_FRAME_S)activity_cost[mode_cost].slow_frames++;
```

### P3 — `triangles` : accumulation correcte seulement si le compteur est par frame

Ancre : `activity_cost[mode_cost].triangles+=renderer.triangles;`

Le header groupe `triangles` avec `commands, draws, instances, culled, uploaded`, et `LUMA3D_RESULT` imprime `triangles_last=renderer.triangles`, ce qui suggère fortement un compteur par frame remis à zéro dans `l3_render_frame`. Si c’est bien le cas, l’accumulation est correcte. Si `triangles` est en réalité cumulatif, la somme devient quadratique et n’a aucun sens (même si elle ne déborde pas en 64 bits avant longtemps).

**Vérification minimale** : dans le test CLI, comparer `cost.triangles` à la somme des triangles par page lue dans le flux `L3_TEST_STREAM`. Si `renderer.triangles` est cumulatif, ce test échouera immédiatement.

### Point RV32 important : les deltas 32 bits ne protègent pas contre un reset

`commands`, `batches`, `bytes` sont accumulés en `unsigned long long`, mais les **deltas** sont calculés en `unsigned` 32 bits. Pour un compteur monotone qui wrap, la soustraction modulaire est correcte tant qu’il y a moins d’un wrap entre deux lectures (toujours vrai ici). Le problème n’est donc pas le wrap, mais la **décroissance** (reset) : elle produit un delta proche de 2^32. C’est exactement le cas P1 sur `mini_bytes`. Pour `total_commands`/`total_flushes`, il faut vérifier qu’ils ne sont jamais remis à zéro ; s’ils peuvent l’être, appliquer le même guard ou passer ces compteurs en 64 bits.

## 3. Trois tests déterministes proposés

Les tests ci-dessous supposent un harnais `--cli` à fausses ioctls, comme dans `cli_contract`, mais avec une **horloge monotone factice** contrôlée par script. Sans horloge factice, les frontières 4 ms / 1020 ms ne sont pas déterministes. Aucun test n’a été exécuté ici.

### Test 1 — Attribution et absence de double comptage

But : vérifier que `feed`, `present`, `submit`, `prepare` et les deltas de compteurs se recollent exactement.

Harnais proposé :
- `L3_TEST_SUBMIT_COST_US=3000` : chaque `PRODOCK_SUBMIT` fait avancer l’horloge factice de 3 ms.
- `L3_TEST_PRESENT_COST_US=7000` : chaque `PRESENT` fait avancer l’horloge de 7 ms.
- `L3_TEST_CLOCK_ONLY_OPS=1` : aucune autre avance d’horloge.

Commande : `--benchmark --frames 20 --warmup 2`.

Assertions :
- `result.feed_seconds == measured_batches * 0.003` à 1e-9 près ;
- `result.present_seconds == 20 * 0.007` à 1e-9 près ;
- `sum(cost.feed sur les modes) == result.feed_seconds` et idem `present`, `commands`, `batches` ;
- `cost.simulation == 0` (pas de `l3_game_step` en benchmark) ;
- `cost.preparation >= -1e-9` ;
- `cost.adviser <= cost.simulation + 1e-9` ;
- `simulation_ms_per_frame == simulation/frames*1000` et idem pour les autres champs normalisés ;
- `unattributed_ms >= -1e-9`.

Ce test détecte : timers imbriqués, double soustraction, oubli de normalisation, et désaccord entre compteurs par mode et compteurs globaux.

### Test 2 — Histogramme, p95/p99, overflow et max

But : tester les frontières exactes sans dépendre du temps réel.

Harnais proposé : `L3_TEST_FRAME_INTERVALS_US="…"` consommé à chaque fin de frame, avec une horloge factice qui avance exactement de la valeur scriptée. Prévoir les valeurs de warmup en préfixe, ignorées après reset.

Cas à exécuter dans le même test :
1. 100 frames : 94 × 0,5 ms + 6 × 1500 ms → `p95_overflow=1`, `p99_overflow=1`, `p95_upper=0`, `p99_upper=0`, `over_33ms=6`, `over_1020ms=6`, `max_frame=1,5`.
2. 100 frames : 99 × 0,5 ms + 1 × 1500 ms → `p95_upper=4`, `p99_upper=4`, `p95_overflow=0`, `p99_overflow=0`, `over_1020ms=1`, `max_frame=1,5`. Ce cas teste le `>=` exact à 99 % : une implémentation avec `>` échouerait.
3. 100 frames à 3,999 ms → `p95_upper=4` ; 100 frames à 4,001 ms → `p95_upper=8`. Teste la frontière de bin.
4. 100 frames à 1019 ms → `p95_upper=1020`, `p95_overflow=0`, `over_1020ms=0` ; 100 frames à 1020 ms → `p95_overflow=1`, `p95_upper=0`, `over_1020ms=100`.
5. 100 frames à 33,2 ms → si le contrat est `over_33ms`, attendu `over_33ms=100` ; le code actuel avec `1/30` donnera `0`. Choix à figer par le patch (seuil 0,033 ou renommage).
6. Invariants systématiques : `p95_upper<=p99_upper` si aucun overflow ; `p95_overflow=1` implique `p99_overflow=1` ; `over_1020ms==0` si et seulement si `max_frame<1.02` ; `over_33ms==0` si et seulement si `max_frame<=seuil` ; `frame_sum` égal à la somme exacte des intervalles injectés ; `max_frame` égal au maximum injecté.

### Test 3 — Robustesse RV32, resets et warmup

Sous-cas dans un même test :
- **Reset de `mini_bytes`** : séquence mesurée `1000, 2000, 0, 500` → attendu `ui_bytes=2500`, `ui_bytes_resets=1`. Le code actuel doit produire ~4,29e9 et échouer.
- **Wrap de `mini_bytes`** : `0xFFFFFF00, 0x100, 0x200` → attendu deltas `0x200` puis `0x100`, total 768. Vérifie qu’une correction de type « si now<before alors 0 » ne casse pas le wrap.
- **Wrap de `total_commands`** : compteur initialisé à `0xFFFFFFF0`, incréments connus sur 20 frames → `cost.commands == result.commands == total incrémenté` modulo 2^32, et la somme 64 bits est exacte. Vérifie que le calcul modulaire n’est pas remplacé par un guard qui perd les commandes.
- **Échec au warmup** : `L3_TEST_FAIL_SUBMIT=1` → code retour 1, `frames=0` dans `LUMA3D_RESULT`, pas de ligne `ACTIVITY_COST` avec `frames>0`. Échoue avec le code actuel.
- **Rapport 5 s** : horloge factice, frames de 100 ms, `L3_TEST_REPORT_COST_MS=200` → après suppression du rapport périodique en benchmark, `max_frame≈0,100 s`, pas 0,300 s. Échoue avec le code actuel.

## 4. Ce qui semble correct et qu’il ne faut pas « corriger » à tort

- Le calcul de bin `frame*250` est cohérent avec des bins de 4 ms.
- La sentinelle p95/p99 (`1024` interne, `0` publié avec flag) est cohérente, à condition de documenter que le flag signifie « le percentile tombe dans le bin overflow », pas « il existe des frames > 1020 ms ».
- Les multiplications p95/p99 sont déjà castées en `uint64_t` : pas de débordement RV32 à cet endroit.
- La soustraction modulaire 32 bits de `total_commands`/`total_flushes` est correcte pour des compteurs monotones qui wrap, tant qu’ils ne sont pas remis à zéro.
- Le reset benchmark exclut correctement les frames de warmup des compteurs par activité, à condition que `renderer.frame==warmup` soit atteint exactement et que l’échec avant reset soit traité (P1).
- Le test CLI existant vérifie déjà `cost.commands==result.commands` et `cost.batches==result.batches` ; il faut conserver ces assertions et y ajouter les invariants ci-dessus.

Aucun de ces correctifs ne modifie le rendu ni le nombre de commandes GPU ; ils ne peuvent donc pas être présentés comme un gain FPS. Les tests proposés doivent rester sur fausses ioctls et horloge factice, avec `hardware_validation=False`.
