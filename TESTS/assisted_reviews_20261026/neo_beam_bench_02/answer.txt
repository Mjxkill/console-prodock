Contre-expertise ciblée sur le bench R19, sans modification RTL et sans accès matériel.

**Faits / hypothèses / preuves manquantes**
- Les faits proviennent uniquement de `tb_reviewed.sv`, du RTL fourni (`gpu_accel.v`, `gpu_v1.v`) et du log `simulation.log`. Hypothèse : l’ordre contractuel posedge + non-bloquant rend le garde `!v1_accepted` nécessaire et justifie le retard d’un cycle de l’ACK. Preuve manquante non fournie : capture complète des ondes n-cycle, mais la chronologie ci-dessous est dérivable du RTL.

## 1) Chronologie précise de 6 cycles — capture, attente, ACK différé

RTL réel (`gpu_accel.v`, bloc v1, extrait ~l.190-262) :

```verilog
v1_accepted <= v1_pending && ready;
...
if (v1_pending) begin
    if (ready) v1_pending <= 0;
end else if (extended_request && !v1_accepted) begin
    v1_pending <= 1;
end
...
if (!v1_pending) begin
    v1_tx_addr <= ...; v1_tx_data <= ...; v1_tx_mask <= ...; v1_tx_write <= ...;
end
```

Chronologie :

| Cycle | `extended_request` | `v1_pending` avant/après | `ready` DDR | `v1_accepted` | Observation |
|---|---:|---|---:|---:|---|
| 0 | 1 | 0 → 1 | 0/X | 0 | slot vide et `!v1_accepted` : armement + capture payload. |
| 1 | 1 | 1 → 1 | 0 | 0 | slot tenu ; payload ne se recapture pas. |
| 2 | 1 | 1 → 0 si `ready=1` | 1 | 0 | grant à ce cycle, mais l’ACK n’est pas encore visible (`v1_accepted` est enregistré). |
| 3 | 1 | 0 → reste 0 | 1/X | 1 | impulsion ACK enregistrée, différée d’un cycle ; `!v1_accepted` empêche la recapture. |
| 4 | 0 ou 1 | 0 | X | 0 | slot peut capturer seulement si engine redemande ; ici absence de re-armement spurieux. |
| 5 | 0 | 0 | X | 0 | transaction/slot drainés ; compteurs stables. |

Conséquences directement vérifiées :

1. **Compter un chargement sans `!v1_accepted` est faux.** Au cycle 3, `v1_pending` peut redevenir vide tandis que `extended_request` est encore actif et tandis que `v1_accepted` est encore à 1. La condition `!dut.v1_pending && dut.extended_request && !dut.v1_accepted` est donc correcte. La condition sans `!v1_accepted` compte un chargement phantom.
2. **`native_grants > returned_acks` en temps réel est faux.** Le grant (`v1_pending && br`) peut précéder l’ACK `v1_accepted` d’un cycle : au cycle 2, grant vu dans le compteur au posedge courant ; ACK seulement au cycle 3. Une assertion temps réel doit tolérer au plus `grants <= acks + 1`, ou n’être stricte qu’après drain complet.
3. **La payload est bien vérifiée sous blocage.** Le bloc `tb_reviewed.sv` conserve `old_pending`, puis après `#1`, si `old_pending` est vrai, compare l’ensemble `{v1_tx_write,v1_tx_addr,v1_tx_data,v1_tx_mask}` à `old_payload`. Donc tous les bits sont comparés à chaque front où le slot était réellement tenu. `held_checks=232` confirme que le contrôle n’est pas vacieux/muēt.

## 2) Scoreboard de conservation correct, avec annulations par reset

Ne pas garder l’invariant actuel `slot_loads != native_grants + 1` comme règle générale : le `+1` correspond ici au seul chargement annulé par reset (`clear(1,64,5,...)` puis `reset_all()`), pas à une propriété structurelle.

Instrumentation correcte dans `tb_reviewed.sv` (aucun changement RTL) :

```systemverilog
integer loads=0, grants=0, acks=0, cancelled_reset=0;

// Dans always @(posedge mc), avant/pendant la logique existante :
old_pending = dut.v1_pending;
...
if (!dut.mrst[1] && old_pending) cancelled_reset++;   // one-shot : slot tenu puis reset

if (dut.mrst[1]) begin
    if (!dut.v1_pending && dut.extended_request && !dut.v1_accepted) loads++;
    if (old_grant) grants++;      // grant DDR natif pendant slot tenu
    if (dut.v1_accepted) acks++;
    ...
end

// Live, tolérance d'un cycle d'ACK :
if (grants > acks + 1) $fatal(1, "ACK skew too large");

// Final, après fence/drain, pending=0 :
if (grants !== acks) $fatal(1, "ACK/grant mismatch grants=%0d acks=%0d", grants, acks);
if (loads !== grants + cancelled_reset)
    $fatal(1, "Conservation: loads=%0d grants=%0d cancelled=%0d", loads, grants, cancelled_reset);
```

Invariant attendu dans le scénario fourni : `14 loads = 13 grants + 1 cancelled_reset`, et `13 grants = 13 acks`.

## 3) Deux contrôles négatifs du banc, sans changer le RTL

1. **Comptage de slot sans garde ACK.** Variante instrumentale : remplacer  
   `!dut.v1_pending && dut.extended_request && !dut.v1_accepted`  
   par `!dut.v1_pending && dut.extended_request`.  
   Résultat attendu : surcharge des `loads` sur les fronts où `v1_accepted` est encore à 1 ; l’invariant final `loads === grants + cancelled_reset` doit échouer. Ce test prouve que `!v1_accepted` n’est pas décoratif.

2. **ACK strict en temps réel.** Variante instrumentale : remplacer la tolérance par  
   `if (native_grants > returned_acks) $fatal(...)` à chaque posedge.  
   Résultat attendu : faux échec sur le cas normal, lorsqu’un grant DDR est vu un cycle avant son ACK enregistré. Ce test prouve que l’assertion précédente était un faux positif lié au retard volontaire d’un cycle.
