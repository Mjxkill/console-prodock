# Plan minimal d'animation fluide par overlay natif

## 1. Position retenue

Je ne peux pas exécuter ni mesurer l'application ; les budgets ci-dessous sont calculés à partir des constantes et structures du packet. La solution retenue est hybride :

- **fond statique natif** conservé comme aujourd'hui sur les changements sémantiques ;
- **seules les pièces actives** sont détachées du fond et animées par des descripteurs de sprites de 32×32 ;
- **à l'arrêt**, on régénère une fois le fond complet, ce qui doit être octet-pour-octet identique à l'ancien rendu.

C'est la seule voie qui tient dans les limites fournies. Un mode "toute la grille en sprites 32×32" **dépasse** le budget pour 1024 sur Neo, voir §8.

## 3. Ce qu'on évite vraiment côté CPU

Aujourd'hui, tout changement sémantique redessine **tout** le canvas natif :

- Pro : 800 × 480 = **384 000 octets** par redraw + copie dans une page ;
- Neo : 1280 × 720 = **921 600 octets** par redraw + copie.

Ce n'est pas "toujours zéro CPU" aujourd'hui non plus : si le stamp est identique, `l3_mini_ui_prepare` ne redessine pas (`mini_canvas_stamp != stamp`) et `upload()` ne copie pas de mots. Ce que le plan évite en plus, c'est le coût des **états intermédiaires de déplacement** : pendant un glissement, chaque déplacement logique ou rafraîchissement déclencherait sinon ce redraw complet, alors qu'avec des sprites la mise à jour est :

- 64 descripteurs × 4 mots = 256 mots = **1 024 octets** au maximum ;
- en pratique un bloc actif = quelques tuiles seulement.

Les commits conservent exactement le coût actuel : un redraw complet du canvas + une copie page. Donc le gain est concentré sur les frames de mouvement, pas sur les COMMIT.

## 4. Décomposition recommandée

### 4.1 Couche de fond immuable (layer unique existant)

Conserver `layers[0]` ou `[3]` tel qu'aujourd'hui pour le fond complet :

- `L0` base = page VRAM choisie (`PRODOCK_GPU_BASE + MINI_BASE + page*MINI_PAGE`) ;
- dimension = canvas complet ;
- page native inchangée pendant les frames de déplacement.

Le fond inclut :

- `puzzle_background_*` ;
- bordures de plateau, puits, emplacements ;
- HUD mini, textes, compteurs, sidebar ;
- cellules non actives ;
- éventuellement toutes les tuiles inertes.

Ce fond est régénéré uniquement sur changement de stamp (semantic change), puis publié selon §6. Il reste donc immuable pendant le déplacement.

### 4.2 Sprites pour les seules pièces actives

Au départ d'un déplacement :

1. Identifier les cellules dont `flags & L3_MINI_FLAG_ACTIVE`.
2. Les **omettre du fond** régénéré au moment où on crée la session de déplacement. Le fond montre la case destination possible/vide, pas la pièce.
3. Pré-rasteriser la pièce dans un atlas temporaire de tuiles 32×32.
4. Référencer cet atlas par des descripteurs `sprites[0..n-1]`.
5. Pendant le déplacement, mettre à jour seulement `x,y` des descripteurs.

À la commit (dépôt) :

1. régénérer le fond complet avec la pièce inactive ;
2. retirer les sprites actifs ;
3. mettre à jour le stamp et publier la nouvelle page.

Cela conserve la logique inchangée : on ne modifie ni les structs `L3MiniView`, ni les règles, on change uniquement la présentation.

### 4.3 Tuiles procédurales à 32×32

`tile()` dessine une pièce de taille cellule `s`, avec ombre interne. Il faut la découper en tuiles de 32×32. Concrètement :

- allouer un buffer CPU temporaire `Wpiece × Hpiece` ;
- créer un `Canvas` pointant temporairement vers ce buffer ;
- dessiner `tile()`, `box()`, `circle()`, et le nombre avec `label()` dans ce buffer ;
- découper en carrés 32×32 alignés sur l'origine de la pièce ;
- uploader chaque slice non vide dans la zone d'actifs, alignée sur 32 octets ;
- remplir les pixels hors pièce par 0 (transparent).

Le nombre de tuiles par pièce est :

\[
n_x = \lceil C_x / 32 \rceil,\quad
n_y = \lceil C_y / 32 \rceil,\quad
n = n_x \times n_y
\]

où `C` est la taille de cellule déjà calculée par `board()`.

## 5. Budgets pires cas

### 5.1 Résolutions et couches

| Cible | Canvas natif | Octets fond | Pages 1 MiB utilisées |
|---|---:|---:|---:|
| Pro Dock | 800×480 | 384 000 | 22/23 MiB, chacune ≤ 1 048 576 |
| Neo | 1280×720 | 921 600 | 22/23 MiB, chacune ≤ 1 048 576 |

Capacité structurelle maximum :

- couches : 16 (`layers[16][8]`) ;
- sprites : 64 (`sprites[64][4]`) ;
- descripteurs couches : `16 × 8 = 128` mots = 512 octets ;
- descripteurs sprites : `64 × 4 = 256` mots = 1 024 octets ;
- overhead descripteurs pour le pire affiché simultanément : **1 536 octets**.

Notre plan utilise 1 à 3 couches et au plus quelques dizaines de sprites ; il ne touche ni au RTL ni au kernel, il utilise seulement le format de scène UAPI déjà exposé.

### 5.2 Tuiles 32×32 et VRAM

| Élément | Coût |
|---|---:|
| Une tuile 32×32 indexée | 1 024 octets |
| 64 tuiles pendant le déplacement | 65 536 octets |
| Fond actif en VRAM | 384 000 (Pro) ou 921 600 (Neo) dans une page native |
| Ombres CPU pour deux pages | 768 000 (Pro) ou 1 843 200 (Neo) octets RAM hôte |
| Fonts : fond statique, pas d'upload GPU dédié nécessaire | coût runtime 0 octet supplémentaire ; atlas GPU optionnel 4 096–65 536 octets non requis |
| Palette | indices 0..255; la plan utilise seulement 0 transparent et 32..127 pour l'art puzzle |

Conséquence directe : si l'on tient les 64 sprites max en réserve, il faut que **toutes les tuiles actives en mouvement tiennent ensemble dans 65 536 octets**. C'est le cas d'une pièce active, pas de toute la grille.

### 5.3 Tuiles par jeu et positions cellule

Tailles de cellule déjà calculées par `board()` :

- 1024 : 4×4. Sur Pro, ~85×85 px. Sur Neo, ~127×127 px.
- blocs : 8×14. Sur Pro, ~24×24 px. Sur Neo, ~36×36 px.
- shapes : dépend de la grille, typiquement entre blocs et 1024.

Tuiles 32×32 nécessaires par pièce :

| Jeu | Pro | Neo | Slices |
|---|---:|---:|---:|
| 1024, une tuile/ pièce | ceil(85/32)=3 | ceil(127/32)=4 | 9 / 16 |
| blocs, une cellule | 1 | ceil(36/32)=2 | 1 / 4 |
| blocs, tétrimino 4 cellules | 4 | 16 | 4 / 16 |

Fantômes de chute : 4 sprites supplémentaires au plus (un par cellule active), même coût.

## 6. Double buffer sans écrire la source active

Dans le code actuel, `page = r->frame & 1` et `mini_stamp[page]` sont supposés liés au rythme de présentation. Pour l'animation, je recommande de rendre cette hypothèse explicite plutôt que supposée :

1. Conserver `front_page` comme indice de la page présentée au dernier `PRESENT`.
2. Conserver les deux ombres `mini_shadow[0/1]` et stamps.
3. Sur changement de stamp :
   - dessiner dans `mini_pixels`, pas dans une page ;
   - choisir `back_page = 1 - front_page` ;
   - `upload()` vers `back_page` uniquement ;
   - mettre à jour la scène avec base `PRODOCK_GPU_BASE + MINI_BASE + back_page*MINI_PAGE` ;
   - publier ;
   - `front_page = back_page`.
4. Pendant le déplacement :
   - ne toucher ni à `mini_pixels`, ni aux ombres, ni aux pages ;
   - mettre à jour seulement `sprites[...]` ;
   - `layers_enabled` inchangé sur le fond ;
   - pas de page additional, pas de copie.
5. Si un déplacement se termine, traiter comme un commit : régénérer fond, choisir page inactive, uploader, présenter, puis effacer sprites actifs.

Condition de sécurité absolue : **toute écriture VRAM est interdite vers `front_page` tant qu'elle est référencée par la dernière scène présentée.** En absence de confirmation de fenchage dans le packet, il faut conserver le comportement synchrone du `SUBMIT`/`PRESENT` déjà utilisé ; aucune supposition de latence ou de FPS n'est nécessaire pour ce plan.

## 7. Égalité d'image aux repos

Exigence minimale de validation :

1. À tout état non animé (aucune tuile active, stamp changé), l'image composite doit être **identique octet par octet** au canvas produit par l'ancien code.
2. Les états avec `status != RUNNING` (pause, échec, réussite) sont traités comme des états de repos et doivent aussi correspondre.
3. Les fonds incluent les ombres décalées de `+3` produites par `tile()`; cette ombre doit être baked dans l'atlas et non recalculée par alpha.
4. Les textes sont produits par les mêmes appels `label()`/`wrapped()`, à la même position, dans le fond.
5. La différence n'est acceptée que pendant le mouvement, et doit disparaître à l'issue de la commande de dépôt.

Mécanisme de comparaison proposée :

- hachage du canvas généré pour chaque repos ;
- hachage de l'image effective/composée (ou capture de référence) pour le même état ;
- compteur `mini_rasterizations` : un repos après déplacement doit incrémenter exactement une fois ;
- compteur `mini_uploads` : idem, une page inactive ;
- `mini_bytes` : proche de 384 000 / 921 600 pour un repos, zéro pendant une suite de déplacements.

## 8. Tuilage 32×32 dépasse dans ces cas

Oui, le tuilage 32×32 dépasse le budget si on tente d'animer **toute la grille ou plusieurs pièces actives simultanées** :

| Cas | Slices | Budget 64 |
|---|---:|---:|
| 1024 une pièce Pro | 9 | OK |
| 1024 une pièce Neo | 16 | OK |
| blocs une pièce Pro | 4 | OK |
| blocs une pièce Neo | 16 | OK |
| 1024 **toute la grille** Pro | 16 tuiles × 9 = 144 | dépasse |
| 1024 **toute la grille** Neo | 16 × 16 = 256 | dépasse |
| 4 pièces actives Neo à 127 px | 64 | exactement à la limite, sans marge |

Donc le plan n'anime **jamais** toute une grille. Il n'y a aucune marge pour animer plusieurs grosses tuiles 1024 en même temps sur Neo. Si une phase future voulait le faire, il faudrait abandonner les sprites pour cette phase et redessiner le canvas complet par changement de stamp, comme aujourd'hui.

Règle recommandée : mode sprite uniquement si  
`sum over active pieces ceil(w/32)*ceil(h/32) <= 64 - réserve(8)`  
sinon, fallback fond complet. Réserve de 8 pour les HUD, ombres/fantômes ou futures pièces.

## 9. Effets que la quantification native empêche

La VRAM/indexation native impose des limites que le plan ne peut pas lever :

- **pas d'alpha par pixel** : la transparence est un index 0 dur ; les arrondis et ombres doivent être intégrés dans les tuiles, pas mélangés avec un fond ;
- **pas de sous-pixel** : même si on exprimait des offsets fractionnaires, la présentation native est une grille de pixels ; un mouvement inférieur à 1 px natif ne change rien ;
- **pas de filtrage bilinéaire** : un déplacement non multiple de la taille cellule produira des bords nets, pas une interpolation ;
- **pas de scaling arbitraire** : conformément à la contrainte du projet, une pièce ne peut pas être zoomée fluidement ; elle doit déjà être rasterisée à la taille finale ;
- **pas de blending de l'ombre** : l'ombre actuelle est une couleur solide décalée (`SHADOW`), pas une ombre alpha ; elle restera solide lors du déplacement ;
- **pas de correction de seams** : les slices 32×32 peuvent montrer des jonctions si les coordonnées d'origine ou les arrondis sont mal alignés ;
- **priorité fixe** par descripteur : l'ordre de composition ne peut pas être recomposé dynamiquement au-delà de l'ordre déclaré des sprites/couches ;
- **couleurs quantifiées** : digits et rammers restent dans l'ensemble 32..127 ; aucun effet colorimétrique continu n'est possible au moment du déplacement ;
- **pas d'accélération supposée** : le plan suppose seulement les capacités déclarées, pas un débit minimal ou une FPS garantie.

## 10. Modifications minimales suggérées dans `mini_ui.c`

Sans imposer un dépôt, la surface de changement conceptuelle est :

```c
/* board() : pour une pièce active en cours d'animation */
if (piece_is_active(cell)) {
    /* ne dessiner ni tile ni corner_selection ici */
    continue;
}

/* nouvelle primitive côté prepare() */
if (active_slice_count(...) > SOFT_BUDGET) {
    /* fallback : rendu complet canvas + page, comme actuellement */
}
```

Points d'insertion :

- `board()` : ajouter une omission des cellules `L3_MINI_FLAG_ACTIVE` quand on est en mode animation ;
- `l3_mini_ui_prepare` : détecter présence d'actifs et gérer le tampon d'atlas ;
- `upload()` : inchangé pour le fond ; les sprites n'ont pas besoin de `upload()` ;
- `l3_mini_ui_close` : libérer l'atlas temporaire et snapshots si ajoutés.

Dans `luma3d_render.h`, il faudrait seulement si on persiste l'atlas entre frames : un champ supplémentaire du type `uint8_t *mini_tile_atlas; unsigned mini_tile_atlas_bytes;` et peut-être `unsigned mini_front_page;`. Aucun changement des structures UAPI ni GPIO/RTL.

## 11. Tests discriminants proposés

1. **Fond synthétique A/B** : générer toutes les vues `L3MiniView` de repos par l'ancien code, puis par le fond-sans-actif + sprites commités, et comparer les hachages d'octets.
2. **Compteur `mini_rasterizations`** : une suite de `N` déplacements puis un dépôt doit donner exactement un rasterization supplémentaire par dépôt, pas par déplacement.
3. **Compteur `mini_bytes`** : déplacement seul doit donner 0 octet uploadé ; dépôt, une page inactive.
4. **Réserves de sprites** : stress sur Neo avec 1024 animé : 16 tuiles, puis ajouter un second actif pour vérifier le refus/fallback avant dépassement.
5. **positions entières** : demander un offset (0,5) dans le descripteur ; attendu visuellement inchangé, ce qui documente la quantification native ; les offsets admissibles sont les pixels entiers.
6. **front page** : pendant un upload de repos, vérifier par compteur que la base présentée avant l'upload n'est pas la base écrite.
7. **variant resolutions** : refaire 1-6 pour Pro et Neo, et pour `L3_MINI_BLOCKS`, `L3_MINI_MERGE1024`, `L3_MINI_SHAPES`.

## 12. Conclusion

La solution réalisable est : **fond statique complet, pièces actives détachées, tuiles 32×32 pour les seules pièces animées, validation octet-par-octet aux repos, fallback fond complet si le budget sprites est menacé.**

Elle évite le redraw complet du canvas indexé sur les déplacements, respecte l'immuabilité du fond, préserve les ombres et le HUD, n'échange aucune page active, et ne dépend d'aucune assumption de FPS ou de débit RTL. Le point de rupture est net : si l'on décompose toute la grille 1024 en tuiles 32×32, le nombre de slices dépasse largement 64 ; il faut donc n'animer que la pièce active.
