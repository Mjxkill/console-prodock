## Défauts concrets et correctifs minimaux

### D1 — Budget temporel incohérent : `idle_ms=100` et 32 Mio sont impossibles avec le pacing par défaut

**Faits.** Une trame pleine fait `44+512=556` octets utiles, soit `744` caractères Base64, plus deux NUL = **746 octets** (`sender.py:18-22`). Avec `chunk=16`, `pause=.002` (`sender.py:33,37,99-102`), cela donne :

- `ceil(746/16)=47` écritures ;
- `47 × 2 ms = 94 ms` de sommeil par bloc plein, hors écritures et hors traitement récepteur.

Or `idle_ms` minimal vaut **100 ms** (`sender.py:35`, `receiver.c:53`) : il ne reste que 6 ms pour 47 écritures. Le récepteur peut expirer en `IDLE` avant le NUL.

Pour 32 Mio : `32×1024×1024/512 = 65 536` blocs, soit `65 536×0,094 = 6 160 s` de pause. Le budget total par défaut est 1 800 s et le maximum accepté 3 600 s (`sender.py:35`, `receiver.c:53`). **32 Mio ne peuvent donc jamais être transférés avec les valeurs par défaut**, même avec `total_ms` maximal ; le maximum pratique est environ 18,7 Mio à 3 600 s.

**Correctif minimal.** Ajouter une validation au constructeur, par exemple après `self.started` (`sender.py:39`) :

```python
WIRE_MAX = 2 + 4*((44 + BLOCK + 2)//3)   # 746
self.deadline = self.started + total_ms/1000.0

parts = (WIRE_MAX + self.chunk - 1)//self.chunk
per_frame = parts*self.pause
if self.chunk <= 0 or self.pause < 0 or per_frame + 0.010 > self.idle_ms/1000.0:
    raise ValueError('idle_ms incompatible avec chunk/pause')

blocks = (len(self.data) + BLOCK - 1)//BLOCK
if blocks*per_frame > self.total_ms/1000.0:
    raise ValueError('total_ms incompatible avec le pacing')
```

Il faut ensuite soit réduire `pause`/augmenter `chunk`, soit relever les bornes. Sans mesure du lien réel, je ne fixe pas arbitrairement les nouvelles valeurs. Ce correctif transforme un échec silencieux en refus immédiat.

**Test discriminant.** Test unitaire sans I/O :
- `Session(io, '0'*32, b'\0'*(32<<20), idle_ms=5000, total_ms=1800000)` doit lever `ValueError` après patch ;
- `Session(..., b'\0'*512, idle_ms=100, total_ms=1800)` doit lever `ValueError` après patch.

### D2 — Le RETURN garanti n’est pas consommé sur les sorties terminales en échec

**Faits.** `finish` vérifie `self.terminal.reason` (`sender.py:135-137`) **avant** d’appeler `await_return` (`:138`). Si le récepteur a envoyé `X` avec raison 4 (I/O), `finish` lève immédiatement : la ligne `RX2_RETURN_...` peut rester dans `self.pending` ou dans l’I/O. Une nouvelle session peut alors soit la perdre, soit la retrouver comme sortie parasite.

Même problème dans `block` quand il voit un `X` (`sender.py:115`) et dans `begin` quand le premier message est un `X` (`:89`) : le processus est sorti, mais le RETURN n’est pas consommé.

**Correctif minimal.** Consommer le RETURN avant de propager toute erreur liée à un `X` :

```python
def _await_then_raise(self, exc):
    if not self.return_seen:
        try:
            self.await_return()
        except Uncertain:
            pass
    raise exc
```

Utilisation :
- dans `block`, remplacer `raise TransferError('receiver terminal reason '+str(r.reason))` par `self._await_then_raise(TransferError(...))` ;
- dans `finish`, déplacer `self.await_return()` avant le contrôle de `reason` ;
- dans `begin`, si `kind=='reply' and r.kind=='X'`, consommer avant de lever.

Pour `finish`, utiliser `self.await_return()` sans le timeout résiduel de `:138` : après un `X`, le shell a déjà tout ce qu’il faut pour imprimer le RETURN, mais le délai résiduel peut être quasi nul. Le timeout par défaut `idle+3 s` (`:144`) est borné et plus sûr.

**Test discriminant.** Faux I/O fournissant dans un même `read` :
`X ... reason=00000004\nRX2_RETURN_<nonce>:4\n`
Après l’exception de `finish`, vérifier que `return_seen` est vrai et `returncode==4`. Avec le code actuel, le RETURN peut rester non consommé.

### D3 — Inertie du shell : trois problèmes concrets

#### D3.1 — La chaîne autorisée `RX2_PROMPT> ` est inatteignable

`sender.py:64` lève `Uncertain('malformed reply')` pour toute ligne commençant par `RX2 `, **avant** l’exemption de `:65` :

```python
if line.startswith(b'RX2 '):raise Uncertain('malformed reply')
if self.ready and line and line not in (b'RX2_PROMPT> ',):
    raise Uncertain(...)
```

`RX2_PROMPT> ` commence par `RX2 ` : l’exemption ne peut jamais s’appliquer.

**Correctif :**

```python
if line == b'RX2_PROMPT> ':
    return None
if line.startswith(b'RX2 '):
    raise Uncertain('malformed reply')
if self.ready and line:
    raise Uncertain('unexpected receiver output '+repr(line[:100]))
```

**Test :** `_line(b'RX2_PROMPT> ')` avec `ready=True` doit retourner `None` ; actuellement lève.

#### D3.2 — Le wrapper shell n’est pas sûr sous `set -e`

`sender.py:47-49` génère :

```sh
receiver ...; rc=$?; printf '\nRX2_RETURN_...:%s\n' "$rc"
```

Si le shell est en `errexit` (`set -e`, fréquent en non-interactif), l’échec du récepteur termine le shell **avant** `rc=$?` et avant le `printf`. Le RETURN garanti disparaît. Le paquet ne prouve pas que le shell vérifié désactive `set -e`.

**Correctif minimal :**

```python
return (f"rc=0; {executable} {path} {self.nonce} {len(self.data)} {crc(self.data):08x} "
        f"{'resume' if resume else 'new'} {self.idle_ms} {self.total_ms} || rc=$?; "
        f"printf '\\nRX2_RETURN_{self.nonce}:%s\\n' \"$rc\"\n").encode()
```

La commande est alors dans une liste `||`, exemptée de `errexit`.

**Test :** stub exécutable qui sort avec code 1 ; exécuter la commande générée sous `dash -e` et `bash -e`. Attendu après patch : une seule ligne `RX2_RETURN_<nonce>:1`. Actuellement : aucune ligne.

#### D3.3 — Longueur de chemin non validée côté sender

`sender.py:44` accepte un chemin de longueur arbitraire ; `receiver.c:50` rejette `strlen(p)>220`. Un chemin de 221 caractères passe le sender, puis le récepteur retourne `ARGS` (5).

**Correctif :** ajouter `if len(path)>220: raise ValueError('target path length')` dans `command()`.

**Test :** chemin `/tmp/rx2-` + 214 caractères doit être refusé avant lancement.

### D4 — Boucles sans deadline absolue et ACK dupliqués

**Faits.** `event()` est un timeout **d’inactivité** (`sender.py:71-81`). Dans `block`, une réponse `A` avec `r.offset<=initial` fait `continue` (`:118`) ; la boucle ne vérifie jamais `time.monotonic()>=deadline`. Une succession d’ACK dupliqués, réels ou injectés, peut maintenir la boucle au-delà de la deadline et du budget total. Même problème dans `finish` (`:129-134`).

**Correctif minimal.** Ajouter une deadline de session et vérifier avant chaque `event` :

```python
# dans __init__
self.deadline = self.started + self.total_ms/1000.0

# dans block, au début de la boucle interne
now = time.monotonic()
limit = min(deadline, self.deadline)
if now >= limit:
    raise Uncertain('DATA deadline')
kind, r = self.event(limit - now)

# dans finish
while not self.terminal:
    now = time.monotonic()
    limit = min(deadline, self.deadline)
    if now >= limit:
        raise Uncertain('FIN deadline')
    kind, r = self.event(limit - now)
```

Et dans `send`, avant chaque `io.write` :

```python
if time.monotonic() >= self.deadline:
    raise Uncertain('session deadline')
```

**Test :** faux `io` renvoyant indéfiniment `A offset=initial-512` ; `block` doit lever après la deadline, pas boucler. Avec le patch de D5.1, il lèvera immédiatement.

### D5 — ACK dupliqué : acceptation trop large et keepalive récepteur

#### D5.1 — Côté sender, `r.offset<=initial` est trop permissif

`sender.py:118` accepte tout ACK dont l’offset est antérieur ou égal à `initial`. Dans le protocole normal, un ACK dupliqué utile porte `offset==initial` (dernier offset commité). Un ACK plus ancien signale un désaccord ou une injection et ne doit pas faire attendre jusqu’à la deadline.

**Correctif :**

```python
if r.kind=='A' and r.offset==initial and r.reason==0:
    continue
```

**Test :** séquence simulée `[A offset=initial-512, A offset=end]` ; avant patch le second ACK est accepté, après patch le premier lève `Uncertain('unexpected acknowledgement')`.

#### D5.2 — Côté récepteur, tout vieux bloc renouvelle l’idle

`receiver.c:80` répond ACK pour tout `offset<committed` et exécute `deadline=now()+idle`. Un rejeu répété d’un vieux bloc peut donc maintenir le récepteur vivant jusqu’au budget total, retardant le RETURN. Le contenu n’est pas réécrit, donc pas de corruption, mais c’est un keepalive non prévu.

**Correctif minimal :** ne renouveler la deadline que pour le bloc immédiatement précédent :

```c
int last = (offset + len == committed);
if(!reply('A',0)){result=IO;break;}
if(last) deadline=now()+idle;
continue;
```

**Test :** après `committed=1024`, rejouer le bloc 0 toutes les 50 ms avec `idle=200 ms` ; après patch le récepteur doit sortir à la deadline initiale, pas rester vivant.

### D6 — `waitfd` et HUP stdin : boucle active jusqu’à la deadline

**Faits.** `waitfd` retourne 0 si `poll` signale `POLLHUP`/`POLLERR` sans l’événement demandé (`receiver.c:32`). Dans la boucle principale, `if(!waitfd(...)) continue;` (`:70`) refait immédiatement un `poll` sur un fd en HUP : consommation CPU jusqu’à `idle`/`total`.

**Correctif minimal.** Rendre `waitfd` tri-état : `1` prêt, `0` timeout/stop, `-1` erreur fatale. Attention : les appelants actuels utilisent `if(!waitfd(...))`, donc `-1` serait interprété comme succès. Il faut adapter :

```c
/* sendall */
int w=waitfd(1,POLLOUT,deadline,0);
if(w!=1)return 0;

/* boucle principale */
int w=waitfd(0,POLLIN,until,1);
if(w<0){result=IO;break;}
if(!w)continue;
```

Dans `waitfd`, retourner `-1` si `revents & (POLLERR|POLLHUP|POLLNVAL)` sans l’événement demandé, et sur `poll<0 && errno!=EINTR`.

**Test :** fermer l’extrémité écriture du pipe stdin après le `R` ; attendu après patch : sortie `IO` (4) rapide et RETURN, pas de spin jusqu’à `idle`.

### D7 — Rollback ENOSPC : `ftruncate` ignoré

**Faits.** En cas d’échec de `write` (`receiver.c:82`) ou de `fdatasync` (`:83`), le code fait `(void)ftruncate(fd,committed)` puis signale `IO`. Le résultat du rollback n’est ni vérifié ni reflété dans la réponse. Si `ftruncate` échoue, l’état du fichier n’est pas celui annoncé. Le CRC de préfixe côté sender (`sender.py:85`) limite fortement le risque de reprise sur un bloc partiel, mais le récepteur ne fournit aucune preuve que le rollback a réussi.

**Correctif minimal.**

```c
static int rollback(int fd,uint32_t n){
  if(ftruncate(fd,(off_t)n))return 0;
  struct stat st;
  if(fstat(fd,&st)||!S_ISREG(st.st_mode)||st.st_size!=(off_t)n)return 0;
  return 1;
}
static int syncfd(int fd,int data){
  int r;
  do{r=data?fdatasync(fd):fsync(fd);}while(r&&errno==EINTR&&!stopped);
  return r;
}
```

Puis :

```c
if(w<=0){
  if(!rollback(fd,committed))result=RESUME; else result=IO;
  goto done;
}
if(syncfd(fd,1)){
  if(!rollback(fd,committed))result=RESUME; else result=IO;
  break;
}
```

Un code distinct (par exemple `ROLLBACK=9`) serait préférable à `IO` pour que l’appelant sache que la taille du fichier n’a pas pu être restaurée. Il faut alors inclure `r.reason` dans les erreurs sender.

**Test avec shim `LD_PRELOAD` :** `write` réussit N octets puis renvoie `ENOSPC`; option `ftruncate` renvoie `EIO`. Vérifier :
- aucun ACK pour le bloc ;
- taille du fichier == `committed` quand le rollback réussit ;
- réponse `X` non-success ;
- reprise : `R` offset == `committed`, préfixe CRC cohérent ;
- avec `ftruncate` en échec, code distinct ou au moins pas de succès silencieux.

### D8 — NACK et budget idle

`receiver.c:86-87` répond `N` sans renouveler `deadline`, alors que les ACK le font (`:80`, `:85`). Si l’écriture du NACK prend du temps (jusqu’à 1 s, `:39`) avec `idle=100 ms`, le récepteur peut sortir immédiatement après le NACK ; le sender, lui, retente explicitement sur ce NACK.

**Correctif minimal :** après un NACK envoyé avec succès, faire `deadline=now()+idle;` avant de reboucler. `bad>16` et le budget total bornent déjà l’abus.

**Test :** forcer un `reply('N')` lent (pipe sortie presque plein) avec `idle=100 ms`, envoyer une trame corrompue, puis la retransmission : elle doit être acceptée, pas arriver après la sortie du récepteur.

## Cas malformed/truncated header : pas de défaut concret trouvé

La lecture ne montre pas de dépassement ni de lecture hors paquet :

- `bytes<HEADER` est testé avant les `memcmp` (`receiver.c:75`) ;
- `len>BLOCK` et `bytes!=HEADER+len` sont testés avant le CRC payload (`:77`) ;
- `decode` rejette `n=0`, `n%4`, `n>744`, les caractères invalides et les bits de padding non nuls (`:43-49`) ;
- le buffer `packet` fait 560 octets pour 558 octets décodés maximum (`:67`).

**Tests discriminants à exécuter :**
1. Base64 de 43 octets + NUL → `N` raison 1, `committed/running_crc/nextseq` inchangés, aucune écriture.
2. En-tête 44 octets avec magie fausse, puis CRC faux → `N`, aucune écriture.
3. `len=512` annoncé mais payload absent → `N`, aucune écriture.
4. 744 caractères valides + 1 caractère + NUL → `oversized`, `N`, aucune écriture.
5. Trame tronquée sans NUL puis silence → `IDLE` (X raison 2) à `idle`, aucune écriture.
6. NUL isolé → ignoré (`receiver.c:73`), pas de NACK ; ce n’est pas une trame.

## Reprise, points de contrôle et retries : comportement fail-closed à confirmer

- La reprise vérifie `st_size`, l’alignement bloc et le CRC de préfixe via `_checkpoint` (`receiver.c:63-65`, `sender.py:83-85`). Si le fichier contient un bloc partiel ou incohérent, le `R` est rejeté par le sender. C’est sûr mais peut laisser le récepteur vivant jusqu’à `idle`.
- `block` ne réessaie que sur `N` avec `r.offset==initial` et `reason==1` (`sender.py:119`). Un NACK cohérent mais avec `offset<initial` (récepteur en retard) tombe dans `Uncertain('unexpected acknowledgement')` (`:121`) : pas de resynchronisation automatique, pas d’écriture. C’est un choix fail-closed acceptable.
- Un ACK ou un NACK perdu termine la session : le sender ne retransmet pas sur silence (`sender.py:81`, `:121`). C’est conforme au commentaire, mais la fiabilité du lien n’est pas prouvée dans le paquet.
- `_checkpoint` recalcule `crc(data[:offset])` à chaque réponse (`sender.py:85`). Pour 65 536 blocs, cela représente environ **1,1 To** de CRC/copies cumulés. Ce n’est pas une corruption, mais un risque de dépassement du budget total sur 32 Mio, à mesurer. Un cache incrémental serait à envisager si le benchmark confirme.

**Tests :**
- NACK avec `offset=0` alors que `initial=512` → doit lever sans retenter ni écrire.
- Perte simulée d’un NACK → attendre le RETURN, vérifier `IDLE`, ne pas envoyer de nouvelle trame.
- Reprise après un bloc complet non ACKé : le `R` doit reporter `offset=committed+len` et le préfixe CRC doit décider si la reprise est acceptée.

## Contrat I/O borné : preuve manquante

`sender.py:97-102` affirme que `io.write` doit avoir un timeout fini, mais le module ne l’impose pas. `event` suppose également que `io.read(timeout)` retourne dans le délai. Si l’implémentation appelante ne le garantit pas, les deadlines du protocole ne servent à rien. Aucun adaptateur `poll/select` n’est fourni dans le paquet ; c’est une preuve manquante, pas un correctif interne aux deux fichiers.

Côté récepteur, `write`/`fdatasync` sur fichier peuvent rester en D-state ; le paquet l’admet pour SIGKILL. Aucune garantie logicielle ne peut couvrir ce cas.

## Point résiduel : `safe_path` et symlinks intermédiaires

`safe_path` accepte des `/` après le préfixe (`receiver.c:50`) et l’ouverture utilise `O_NOFOLLOW` seulement sur le dernier composant (`:62`). Un répertoire intermédiaire `/tmp/rx2-x` qui est un symlink peut donc faire sortir de `/tmp`. Si les sous-répertoires ne sont pas nécessaires, le correctif minimal est de rejeter tout `/` après `p+9`. Sinon, il faut une ouverture composant par composant ou `openat2` avec `RESOLVE_NO_SYMLINKS`, ce qui dépasse le correctif minimal. À tester avec un symlink intermédiaire.
