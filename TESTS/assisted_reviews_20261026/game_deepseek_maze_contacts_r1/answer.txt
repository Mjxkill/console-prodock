## Contre-exemples concrets

### C1 — Un `COLLECT` avant un contact dans le même appel provoque un faux fallback

Trace minimale, toutes cellules ouvertes dans la carte fournie (`minigames/l3_minigames.c:310-314`) :

```text
t=0     héros H=(3,5), fantôme G0=(5,5), G1=(11,9)
event0  COLLECT à (4,5), acteurs H=(4,5), G0=(5,5), G1=(11,9)
event1  DEATH   à (5,5), acteurs H=(5,5), G0=(5,5), G1=(11,9)
        respawns H=(1,1), G0=(6,5), G1=(11,9)
```

Le chemin `H: (3,5)->(4,5)->(5,5)` est orthogonal et légal. Pourtant :

- `maze_motion.c:122` et `:132` **sautent** les événements `COLLECT` ;
- l’événement `DEATH` appelle ensuite `observed_move` avec `H` directement de `(3,5)` à `(5,5)` (`maze_motion.c:133`) ;
- la distance de Manhattan vaut `512`, donc `observed_move` retourne 0 (`maze_motion.c:73`) ;
- `observe_events` part en fallback (`:146-147`), donc le héros est téléporté immédiatement vers l’état final et le report du respawn/des vies est perdu.

C’est un faux fallback : l’information de mouvement est présente dans le `COLLECT`, mais elle est ignorée. Le moteur émet bien `maze_eat` puis `maze_contact` dans le même tick (`l3_minigames.c:414`), et `maze_eat` émet un événement `COLLECT` (`:343`).

**Correctif minimal** : valider et traiter `e->actor_x/y` pour **tous** les événements, y compris `COLLECT`, avant de faire le `continue` des contacts. En pseudo-diff dans `observe_events` :

```c
/* validation */
if(!open_cell(v,e->x*256u+128,e->y*256u+128))return 0;
for(unsigned i=0;i<3;i++)
    if(!open_cell(v,e->actor_x[i]*256u+128,e->actor_y[i]*256u+128))return 0;
if(e->kind!=L3_MAZE_COLLECT)
    for(unsigned i=0;i<3;i++)
        if(!open_cell(v,e->respawn_x[i]*256u+128,e->respawn_y[i]*256u+128))return 0;

/* traitement */
for(unsigned i=0;i<3;i++)
    if(!observed_move(&work,v,i,e->actor_x[i]*256u+128,
                              e->actor_y[i]*256u+128,now))goto fallback;
if(e->kind==L3_MAZE_COLLECT)continue;
```

### C2 — Deux `POWER` sur le même fantôme : le warp zéro du premier contact fait échouer le second

Trace minimale :

```text
t=0     H=(4,5), G0=(5,5), G1=(11,9)
event0  POWER à (5,5) ; respawn G0=(6,5)
event1  POWER à (6,5) ; H et G0 sont en (6,5), respawn G0=(6,5)
final   H=(6,5), G0=(6,5), G1=(11,9)
```

Le premier événement exécute `contact_warp` et ajoute un segment de durée nulle `{due1,due1, (5,5), (6,5)}` (`maze_motion.c:113`). Le second événement, après le déplacement du héros `(5,5)->(6,5)`, appelle `contact_arrival` sur G0. La boucle rencontre ce segment avec `s->end==s->start` et retourne 0 (`maze_motion.c:88`) ; tout l’appel part en fallback (`:138`, `:146-147`).

Conséquence visuelle : à `t=0.05`, avant `due1=0.117`, G0 est déjà affiché en `(6,5)` au lieu de rester en `(5,5)` jusqu’à l’arrivée du héros. Le chemin `(6,5)->(6,5)` est pourtant reconstructible et légal.

C’est cohérent avec le moteur : après un `POWER`, le fantôme est remis sur `(6,5)` (`l3_minigames.c:358-360`) ; si le héros atteint ensuite cette cellule, un second contact est possible. La trace API autorise plusieurs événements dans un même pas (`l3_mini_trace.h:5-7`). La reachability exacte dépend du découpage `dt_ms`/ticks, absent du packet : c’est une **hypothèse moteur à confirmer**, mais la trace est valide pour l’API.

**Correctif minimal** : ne pas reconstruire une queue déjà arrivée. Dans `contact_arrival`, après le cas `due<=now` :

```c
if(t->count){
    const L3MazeSegment *last =
        &t->segments[(t->head+t->count-1)%L3_MAZE_SEGMENTS];
    int prior_zero=0;
    for(unsigned n=0;n<t->count;n++){
        const L3MazeSegment *s=&t->segments[(t->head+n)%L3_MAZE_SEGMENTS];
        if(s->end>now && s->start==s->end){prior_zero=1;break;}
    }
    if(prior_zero && last->end<=due) return 1; /* déjà au contact au plus tard à due */
}
```

Ce correctif évite de perdre le warp zéro antérieur quand le second contact est postérieur. Il faut un test de non-régression avec un fantôme **encore en mouvement** pour vérifier que le retiming existant n’est pas modifié.

Accessoirement, `contact_warp` ajoute un segment zéro même si `(px,py)==(x,y)` (`maze_motion.c:111-113`). Il vaut mieux ne l’ajouter que si la position change :

```c
if(px!=(unsigned)x||py!=(unsigned)y){
    if(next.count==L3_MAZE_SEGMENTS)return 0;
    next.segments[next.count++] =
        (L3MazeSegment){due,due,(uint16_t)px,(uint16_t)py,(uint16_t)x,(uint16_t)y};
}else if(next.count==0){
    next.settled_x=(uint16_t)px;next.settled_y=(uint16_t)py;
}
```

## Chemins traversant un mur

Je n’ai pas trouvé de contre-exemple de traversée de mur dans le code fourni :

- les déplacements normaux sont limités à Manhattan 256 et destination ouverte (`maze_motion.c:29-30`, `:73`) ;
- les warps sont des segments de durée nulle (`:113`) ;
- `sample` traite `time>=s->end` comme un saut, sans interpolation (`:47`).

Réserve : `contact_warp` peut clipper un segment à `due` et poser un `x1,y1` interpolé hors centre de cellule (`maze_motion.c:108`). Ce n’est pas une traversée de mur visuelle, car le saut final est zéro-durée, mais tout futur code qui réutiliserait ce point comme extrémité de chemin doit rester prudent.

## Preuves manquantes / hypothèses

- Le packet ne contient pas `l3_mini_step_trace`, `finish`, ni la définition complète de `L3MiniActors`/`L3MiniView`. Impossible de prouver la suite exacte des ticks et la reachability moteur des traces C1/C2 avec un `dt_ms` donné.
- Le packet ne montre pas si `finish(L3_MINI_LOST)` change `after->kind`. Si la vue n’est plus `L3_MINI_MAZE`, `presentation.c:13-19` remet `maze_motion`/`maze_events` à zéro et le report du dernier cœur est contourné. C’est une **hypothèse à lever** avec un test `LOST`.
- Le test fourni ne couvre pas le dernier cœur, les collectes avant contact, les contacts sur cellule de respawn, ni un restart aléatoire.

En résumé : le code transactionnel est propre sur les entrées publiques, les segments normaux ne traversent pas de mur, mais deux cas concrets de contacts multi-événements provoquent un fallback évitable et donc une réapparition/respawn visuel immédiat au lieu d’être aligné sur l’arrivée interpolée du héros.
