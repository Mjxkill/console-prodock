## Verdict court

**Fait calculé :** pour le packet COPY16 fourni, `descriptor_bad = 3'b000`. Si `u_copy.packet_0` contient réellement ces 256 bits, la logique RTL de validation **ne rejette pas**. Le rejet board n’est donc pas expliqué par l’arithmétique du descripteur.

**Fait d’observation :** `done2 + rejected+1 + source/color/depth inchangés` est compatible avec **deux** branches :
1. V1 rejette **avant** `COPY_START` : `29: state<=target_valid ? COPY_START : BAD` (`gpu_v1.v:428`), donc pas de `u_copy` du tout.
2. `u_copy` tourne, `copy_done=1`, mais `copy_bad=1` (`gpu_v1.v:437`), par exemple parce que `packet_0=0` → `descriptor_bad=3'b011`.

L’observation board seule **ne prouve pas** que `u_copy` a été lancé. La CE routée `n7630_6` est un point suspect, mais elle n’est pas encore une cause mesurée.

## 1. Calcul des 3 bits `descriptor_bad` avec les valeurs fournies

Packet COPY :
`[1d000000, 00808000, 00100001, 00000020, 0, 0, 00100001, 0]`

Donc, dans `gpu_copy565.v` :

| mot | valeur |
|---|---:|
| `w0 = packet[31:0]` | `0x1d000000` |
| `w1 = packet[63:32]` | `0x00808000` |
| `w2 = packet[95:64]` | `0x00100001` |
| `w3 = packet[127:96]` | `0x00000020` |
| `w4 = packet[159:128]` | `0` |
| `w5 = packet[191:160]` | `0` |
| `w6 = packet[223:192]` | `0x00100001` |
| `w7 = packet[255:224]` | `0` |

TARGET déjà accepté : `dst_base = color_base = 0x00800020`, `dst_stride = 0x0100`, `dst_height = 0x0010`.

```text
src_end = w1 + w3[15:0]*w2[15:0]
        = 0x00808000 + 0x20*1
        = 0x00808020

dst_end = dst_base + dst_stride*dst_height
        = 0x00800020 + 0x0100*0x0010
        = 0x00801020

overlap = (w1 < dst_end) && (dst_base < src_end)
        = (0x00808000 < 0x00801020) && (0x00800020 < 0x00808020)
        = 0 && 1
        = 0
```

Bits, d’après le bloc `CHECK` de `gpu_copy565.v` :

```text
descriptor_bad[0] =
  w1[31:30]!=0          -> 0
  || w1[4:0]!=0         -> 0
  || w2[31:16]==0       -> 0x0010 != 0 -> 0
  || w2[31:16]>1024     -> 0
  = 0

descriptor_bad[1] =
  w2[15:0]==0           -> 1 != 0 -> 0
  || w2[15:0]>512       -> 0
  || w3[31:16]!=0       -> 0
  || w3[4:0]!=0         -> 0
  || w3[15:0] < ({1'b0,w2[31:16]}<<1)
       -> 32 < (16<<1)=32 -> 0
  = 0

descriptor_bad[2] =
  src_end > 33'h040000000 -> 0
  || w7!=0                -> 0
  || (overlap && ...)     -> 0
  = 0
```

**Résultat : `descriptor_bad = 3'b000`.**

Pour TARGET, les mots fournis satisfont aussi `target_bad=0` : `width=128`, `height=16`, bases alignées, `color_stride=z_stride=256`, `color_end=0x00801020`, `z_end=0x00811000`, pas de chevauchement color/Z. La ligne `gpu_v1.v:442` pose donc logiquement `target_valid=1`, et `gpu_v1.v:428` devrait aller en `COPY_START`. C’est une déduction RTL, pas une mesure netlist.

## 2. CE `n7630_6` INIT `0x4000` et `packet_0` initialisé à zéro

Le rapport de route fournit :

- `l_31_s10` : LUT4, entrées `state_0[1], state_0[0], state_0[2], state_0[3]`, init `16'h0001` → sortie `l_31_18 = (state[3:0]==0)`.
- `n7630_s2` : LUT4, entrées `state_0[4]`, `gpu_debug_state[50]`, `u_pixels/state[41]`, `l_31_18`, init `16'h4000`.
- `packet_255_s0` et `packet_32_s0` : DFFRE, `CE = n7630_6`, `RESET = GND`, init `1'b0`.
- `descriptor_bad_*_s0` : DFFRE, `CE = n5984_12`, reset séparé, init `0`.

Avec la convention usuelle Gowin/Verilog, `0x4000` correspond à un **seul minterm** : `I3=1, I2=1, I1=1, I0=0`. Donc, sous cette convention :

```text
n7630_6 = l_31_18
        & gpu_debug_state[50]
        & u_pixels/state[41]
        & !u_copy/state[4]
        = (u_copy.state==IDLE)
        & gpu_debug_state[50]
        & u_pixels/state[41]
```

Deux conséquences factuelles :

1. **Ce n’est pas une CE `IDLE && start` simple.** Une fonction `IDLE && start` à deux entrées utiles aurait 4 minterms dans une LUT4, pas 1. La CE routée est strictement plus restrictive : elle exige **deux termes supplémentaires**.
2. Si `gpu_debug_state[50]` ou `u_pixels/state[41]` n’est pas actif pendant l’unique cycle `IDLE/start`, `n7630_6=0`, et `packet_0` reste à sa valeur d’initialisation, `0`, car son `RESET` est `GND` et le reset du module ne remet pas `packet` à zéro.

**Hypothèse à tester, pas cause affirmée :** si `gpu_debug_state[50]` et `u_pixels/state[41]` sont deux bits d’un même état one-hot, ils ne peuvent pas être simultanément à 1, et la CE est identiquement 0. Dans ce cas, **aucune capture COPY ne se fait**, pas seulement la première. La simulation mappée doit trancher.

### Rejet attendu si la première capture manque

Après reload, `packet_0=0` :

```text
w1=w2=w3=w4=w5=w6=w7=0
src_end=0
overlap = (0 < dst_end) && (dst_base < 0) = 1 && 0 = 0

descriptor_bad[0] = (w2[31:16]==0) = 1
descriptor_bad[1] = (w2[15:0]==0)  = 1
descriptor_bad[2] = 0
```

**Rejet attendu : `descriptor_bad = 3'b011`.**

Chemin RTL correspondant :

- `gpu_copy565` : `CHECK` → `VALIDATE` → `bad<=1` → `FINISH` → `done<=1`. Aucun passage par `ROW/READ0/WRITE`, donc `copy_valid=0`, `copy_write=0`.
- `gpu_v1` : `COPY_WAIT` voit `copy_done && copy_bad` → `BAD` (`gpu_v1.v:437`) → `rejected+1` → `FINISH` → `done=1`.

Donc : **`done` total = 2**, **`rejected=1`**, **aucune requête COPY**. C’est exactement le symptôme board. C’est une **cohérence**, pas une preuve.

Nuance : `gpu_v1.v:437` pose aussi `cache_invalidate<=1` avant d’aller en `BAD`. Ce n’est pas une écriture color/depth, mais si la métrique « mémoire non touchée » inclut le cache, il faut le préciser.

## 3. Distinguer cause logique, faute de capture, faute de FSM

| Branche | Signature à observer en simulation mappée | Statut sur ce packet |
|---|---|---|
| **Cause logique** : `descriptor_bad` faux alors que `packet_0` est intact | `packet_0 == COPY16` **et** `descriptor_bad != 3'b000` à `VALIDATE` | **Ruled out par calcul** pour le packet fourni : `3'b000`. À confirmer en netlist (pas de bug d’arithmétique mappée). |
| **Faute de capture** : `u_copy` reçoit zéro/partiel | `packet_0 != COPY16` à `VALIDATE`, typiquement `0` ; `copy_done=1`, `copy_bad=1` ; `descriptor_bad=3'b011` | **Très cohérent** avec la CE `n7630_6`, mais non prouvé sans sonde `packet_0`/`n7630_6`. |
| **Faute de FSM V1** : la commande 29 ne va pas jusqu’à `COPY_START` | `target_valid=0` à `gpu_v1.v:428`, ou pas de `COPY_WAIT`/`copy_done` ; rejet par `BAD` sans `u_copy` | **Alternative non éliminée par l’observation board.** `done2 + rejected+1` est aussi produit par `gpu_v1.v:428`. |

Point important : le CE des `descriptor_bad` est `n5984_12`, distinct de la CE packet `n7630_6`. Si ce CE échouait, `descriptor_bad` resterait à 0 et on aurait un **faux accept**, pas un rejet. Donc, **si `u_copy` a réellement tourné**, le rejet vient bien d’un descripteur jugé invalide, pas d’une non-capture des bits `descriptor_bad`.

Mais l’observation board ne dit pas si `COPY_START`/`COPY_WAIT`/`copy_done` ont eu lieu. C’est la première discrimination à faire.

## 4. Petit tableau de cas discriminants

| Cas | `u_copy.packet_0` effectif | `descriptor_bad` attendu | Sortie `u_copy` | V1 | Mémoire |
|---|---|---:|---|---|---|
| **COPY16 intact fourni** | `00000000_00100001_..._1d000000` | `3'b000` | `done=1, bad=0` | `FINISH` accepté | lectures/écritures COPY attendues |
| **Première capture perdue** | `0` | `3'b011` | `done=1, bad=1` | `BAD`, `rejected+1` | aucune requête COPY |
| **Seul `w0` capturé** | `{w0=1d000000, reste 0}` | `3'b011` | `done=1, bad=1` | `BAD` | aucune |
| **COPY16 mais `w2[31:16]=0`** | `w2=0x00000001` | `3'b001` | `done=1, bad=1` | `BAD` | aucune |
| **COPY16 mais `w7=1`** | `w7=0x00000001` | `3'b100` | `done=1, bad=1` | `BAD` | aucune |

Le cas « seul `w0` capturé » montre que `descriptor_bad` **ne distingue pas** `packet=0` de `packet={opcode seul}` : les deux donnent `3'b011`. D’où la nécessité de sonder `packet_0` directement.

Test complémentaire décisif : envoyer **deux COPY consécutifs** après reload. Si le deuxième est accepté, la CE n’est pas systématiquement morte (problème de première capture/timing). Si le deuxième est aussi rejeté avec `packet_0=0`, la CE est probablement systématiquement inactive (décodage FSM/CE).

## 5. Une seule assertion de capture forte

À mettre dans le **TB de simulation mappée exacte**, pas dans le RTL commun/frozen, sans forcer le producteur :

```systemverilog
// TB mappé exact R19 uniquement. Adapter les noms hiérarchiques au netlist :
// le rapport de route expose u_copy/packet_0[255:0] et la CE n7630_6.
property p_copy_capture_exact;
  @(posedge gpu_clk) disable iff (!rstn)
    (u_accel.u_v1.u_pixels.u_copy.start &&
     u_accel.u_v1.u_pixels.u_copy.state == 5'd0) // IDLE
    |=> (u_accel.u_v1.u_pixels.u_copy.packet_0 ==
         256'h0000_0000_0010_0001_0000_0000_0000_0000_0000_0020_0010_0001_0080_8000_1d00_0000);
endproperty

assert property (p_copy_capture_exact);
```

Cette assertion est discriminante :

- Elle **échoue** si la CE ne s’est pas armée ou si la capture est partielle : `packet_0` reste à `0` ou est incomplet.
- Elle **passe** si `u_copy.packet_0` reçoit bien les 256 bits attendus. Dans ce cas, la capture n’est pas la cause, et il faut regarder `descriptor_bad` à `VALIDATE` et la branche FSM `target_valid`.
- Elle ne dépend d’aucun force sur `command` ni sur `packet` : elle compare l’état interne du netlist à la commande réellement émise.

Si elle échoue, un moniteur séparé (pas une assertion) doit imprimer au cycle du start : `u_copy.state`, `n7630_6`, `gpu_debug_state[50]`, `u_pixels/state[41]`, `u_copy.packet_0`. C’est ce qui localisera le terme manquant de la CE.

## 6. Preuves manquantes / prochaine étape

Faits manquants à obtenir, sans nouvelle PnR ni modification source :

1. **Simulation mappée exacte du netlist R19**, avec les mêmes init, le même reload, TARGET puis COPY. Le bench RTL fourni (`reads=2 writes=2`) ne valide pas `n7630_6` ; il ne peut pas exonérer la CE routée.
2. Sonder si `COPY_START` et `COPY_WAIT` sont atteints, et si `copy_done` pulse réellement. Sinon, le rejet est `gpu_v1.v:428` (FSM/`target_valid`), pas une capture.
3. Sonder `u_copy.packet_0` à `VALIDATE` et `n7630_6` au cycle `IDLE/start`.
4. Retrouver la définition de `gpu_debug_state[50]` et `u_pixels/state[41]`. Sans cela, l’équation de CE reste une hypothèse de décodage.
5. Clarifier la divergence de comptage : la prose dit « 1 read+1 write », le log RTL fourni dit `reads=2 writes=2`. Il faut savoir ce que le compteur inclut avant d’en faire une preuve de trafic mémoire.
6. Vérifier la définition exacte de « mémoire non touchée » : `gpu_v1.v:437` arme `cache_invalidate` même sur `copy_bad`.

Aucune cause physique n’est affirmée ici. La prochaine preuve doit être la **simulation mappée exacte** avec l’assertion ci-dessus, pas un force du producteur ni une nouvelle capture board.
