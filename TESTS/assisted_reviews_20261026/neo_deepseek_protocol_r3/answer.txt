**Réponse courte** : sur ce RTL exact, le slot `v1_pending`/`v1_accepted` ne perd ni ne duplique une requête **unique** sous backpressure, *si* le producteur respecte un protocole « une transaction à la fois » et retire VALID au premier front utile après avoir vu `v1_accepted`. Le RTL seul ne garantit pas ces conditions : la garde n’est que d’un cycle. En particulier, une VALID maintenue un cycle de trop peut dupliquer, et une nouvelle requête présentée dans le cycle du pulse `v1_accepted` peut être perdue.

## Faits RTL

- Le slot est un registre unique, pas un FIFO : `v1_pending` est mis à 1 si `extended_request && !v1_accepted`, maintenu tant que `ready=0`, et remis à 0 dès `v1_pending && ready` — [S10] lignes 220-225.
- Le payload est figé pendant `v1_pending=1` : le bloc de capture n’écrit que si `!v1_pending` — [S10] lignes 231-238.
- `v1_valid = v1_pending` — [S10] ligne 239.
- Le producteur v1 voit `ready = v1_accepted && v1_select` — [S10] ligne 247. `v1_accepted` est enregistré, donc le producteur voit l’acceptation **un cycle après** l’acceptation réelle par l’arbitre.
- L’arbitre n’émet `m_en` que si `b_valid && b_ready` ; pour une écriture, `b_ready` exige aussi `m_wr_ready` — [S13] lignes 82-93. `take_blitter` est remis à 0 sur acceptation — [S13] ligne 110.
- `scan_valid`, `take_blitter`, `m_ready` et `m_wr_ready` peuvent maintenir `b_ready=0` : c’est le backpressure considéré.
- Les fonctions combinatoires `native_issue`, `native_valid next`, `pending next`, `accepted next` ont été comparées exhaustivement au RTL et concordent, hors reset et sémantique FF documentée — fait 7 du paquet. Cela exclut une erreur booléenne dans ces équations, pas un problème de protocole producteur ni de capture de payload.

## Déductions et séquences

### 1. Backpressure pur : pas de perte

Si `ready=0`, alors `v1_pending` reste à 1, `v1_tx_addr/data/mask/write` restent figés, et `b_valid=1` attend. Aucune acceptation n’est possible tant que `b_ready=0`. Quand `b_ready` repasse à 1, une seule acceptation a lieu, `v1_pending` retombe à 0, et `v1_accepted` monte au cycle suivant. **Pas de perte ni de duplication dans ce cas.**

### 2. Duplication conditionnelle concrète

Soit `P` une requête, `ready` haut au cycle N :

| cycle | `v1_pending` | `v1_accepted` | `extended_request` | effet |
|---|---:|---:|---:|---|
| N | 1 | 0 | 1 (`P`) | l’arbitre accepte à ce front ; `v1_pending→0`, `v1_accepted→1` |
| N+1 | 0 | 1 | 1 (`P`) | capture bloquée par `!v1_accepted` ; payload réécrit avec `P` |
| N+2 | 0 | 0 | 1 (`P`) | `v1_pending→1` de nouveau, payload `P` rechargé |
| N+3 | 1 | 0 | 1 (`P`) | `b_valid=1`, une seconde acceptation DDR est possible |

C’est une **duplication de la même requête** si le producteur maintient VALID plus d’un cycle après avoir vu `v1_accepted`. Le RTL ne l’empêche pas : la garde `!v1_accepted` ne couvre qu’un cycle — [S10] lignes 220-225.

### 3. Perte conditionnelle concrète

Si le producteur peut présenter une **nouvelle** requête `Q` au cycle N+1, pendant que `v1_accepted=1` :

- `extended_request=Q` ;
- `v1_pending=0` ;
- la capture est inhibée par `!v1_accepted` — [S10] ligne 224 ;
- `v1_valid=0` — [S10] ligne 239 ;
- l’arbitre ne voit pas `b_valid` et n’émet aucun `m_en` — [S13] lignes 82-93 ;
- si le producteur interprète `v1_accepted` comme READY pour `Q` et retire `Q` au front N+1, `Q` est perdue.

Ce cas est exclu par le protocole « une transaction à la fois » : le producteur ne peut pas remplacer `P` par `Q` avant d’avoir observé READY pour `P`, c’est-à-dire au plus tôt au front N+1. Mais c’est une **hypothèse non encodée dans ce RTL**, pas une garantie matérielle.

## Hypothèses nécessaires au progrès

1. **H1 — stabilité** : le producteur maintient `v1_request`, adresse, données, masque et write stables tant que `v1_accepted && v1_select` n’a pas été observé.
2. **H2 — retrait** : le producteur retire VALID au premier front qui échantillonne `v1_accepted` haut, et ne présente pas une autre transaction dans ce même cycle.
3. **H3 — exclusivité** : `ext_active`, `v1_select` et `legacy_valid` sont cohérents pendant toute la durée de `v1_pending`. Sinon `valid=legacy_valid||v1_valid` avec des mux `ext_active` peut mélanger l’adresse legacy et le payload v1 — [S10] lignes 252-256. Cette exclusivité n’est pas démontrée dans le paquet.
4. **H4 — progression de l’arbitre** : `b_ready` finit par monter, c’est-à-dire que `scan_valid` ne bloque pas indéfiniment, que `take_blitter` finit par être accordé et que `m_ready`/`m_wr_ready` finissent par être hauts — [S13] lignes 82, 86, 110-111. Le RTL ne fournit pas de preuve de fairness, seulement une priorité scanout.
5. **H5 — connexion** : le `ready` de [S10] ligne 18 est exactement `b_ready` de [S13] ligne 83, sans qualification supplémentaire. Cette connexion n’est pas visible dans les extraits fournis.

## Cinq conclusions actionnables

1. **Ne pas conclure à une perte ou duplication inconditionnelle** : pour une requête unique, avec H1+H2 et la connexion H5, le slot est sûr sous backpressure. La chaîne `pending → valid → b_valid && b_ready → accepted` ne produit qu’une acceptation, puis `pending=0` et `take_blitter=0` empêchent une seconde acceptation immédiate — [S10] 220-239 ; [S13] 82-94, 110.

2. **Corriger ou documenter H2 avant de qualifier le protocole** : le RTL duplique si VALID reste haut plus d’un cycle après `v1_accepted`. Le contre-exemple N/N+1/N+2 ci-dessus est reproductible en simulation avec un producteur qui maintient VALID deux cycles. Si le FSM pixel ne garantit pas le retrait immédiat, ajouter une garde de drainage :
   ```verilog
   reg v1_drain;
   always @(posedge mem_clk)
     if (!mrst[1]) v1_drain <= 0;
     else if (v1_pending && ready) v1_drain <= 1;
     else if (v1_drain && !extended_request) v1_drain <= 0;
   ```
   puis conditionner la capture à `!v1_accepted && !v1_drain`. Cela supprime la duplication par VALID trop longue, au prix d’un cycle de latence.

3. **Ne pas revendiquer le back-to-back** : si le producteur peut présenter une nouvelle requête dans le cycle du pulse `v1_accepted`, le RTL la perd. Pour un vrai back-to-back, il faut un skid buffer deux entrées ou un `ready` producteur qualifié par « slot vide » ; le simple ajout de `v1_drain` ne restaure pas cette requête. C’est une limite de protocole, pas une erreur booléenne.

4. **Test discriminatoire minimal, sans nouveau PnR** : simuler ou forcer, autour de `gpu_accel`, trois séquences : (a) VALID tenu puis retiré au front après `v1_accepted` → doit produire un seul `b_valid && b_ready` et aucun re-`pending` ; (b) VALID tenu un cycle de plus → doit produire un second `pending` (confirme la duplication) ; (c) nouvelle requête au cycle `v1_accepted=1` → doit montrer `v1_valid=0` et aucune acceptation (confirme la perte). Observer `v1_pending`, `v1_accepted`, `extended_request`, `b_valid`, `b_ready`, `v1_tx_addr/data`. Aucun de ces signaux n’est exposé par les sondes R19 actuelles — fait 5.

5. **Preuve manquante à exiger avant toute conclusion matérielle** : le FSM pixel exact et la chronologie de retrait de VALID ne sont pas dans le paquet ; les comparaisons exhaustives du fait 7 valident les équations `pending next`/`accepted next` mais pas le respect de H1/H2 par le producteur, ni la capture payload, ni le timing routé. R20/R20r1 n’a fourni aucun bitstream ni observation — fait 6. Il faut soit une simulation cycle-accurate avec le FSM pixel réel, soit une sonde observant `extended_request`/`v1_pending`/`b_ready`/`v1_accepted`, avant d’attribuer le stall CLEAR à ce slot.
