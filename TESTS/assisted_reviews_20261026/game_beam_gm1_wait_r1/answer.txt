# Audit complémentaire GM1 — attente native, volumes rendus, commandes/batches/triangles/overdraw

## 1. Verdict exécutif

**Facts :** le vrai tour complet GM1 est passé sur Pro Dock G22r0, avec conservation des pixels/art/logique/save et `1079` commandes légales (`FULL TOUR COSTS`, `scope` complet). Les FPS sont des FPS d’intervalle de complétion, pas promesses : exploration `10.647`, circuits, blocs, formes, fusion1024 `21.613`, **maison `11.828`**, Simon `25.700`, shooter `43.400`, tours `19.724` (`FULL TOUR COSTS`).

**Hypothèse proposée (une seule piste) :** réduire le nombre de soumissions `SUBMIT` par image en fusionnant géométrie et présentation/UI dans une **seule soumission par image** dans les modes qui font aujourd’hui `flush(géométrie)` puis `flush(UI/présentation)`, sans changer l’ordre des commandes, ohne-tout buffer ou caméra (`games/luma3d/.../src/render.c:307-310`, `render.c:452`, `render.c:318`).

**Hypothèse rejetée pour cette piste :** fond couleur+Z statique pour la maison. Elle n’est pas retenue car, dans les conditions réelles de la maison (actors, granulés et anneaux dynamiques mobiles chaque image, page de profondeur unique et partagée, pages couleur alternées), préserver exactement occlusion et pixels exigerait soit un effacement/restauration de profondeur déjà présente, soit une copie couleur+Z documentée, non prouvée par les sources fournies. La prouver demanderait du RTL ou une extension pilote dédiée.

**Important :** la cause GPU « fillrate natif » n’est **pas prouvée**. `wait_us` est une mesure d’attente de complétion du FIFO, pas un compteur de fragments/textures (`FULL TOUR COSTS`, `COUNTER SCOPE`). Aucun contre de texel/fragment/overdraw n’est revendiqué (`FULL TOUR COSTS`: « No fragment/texture-miss counter is claimed to exist »).

### 2.3 Plafonds possibles, non promis

Pour la maison contrôlée candidate :
- `submit` seul = `40,280 ms/image` → plafond image si submit seul comptait : `24,8 FPS`.
- `préparation` seule = `22,877 ms/image` → plafond `43,7 FPS`.
- image réelle candidate = `81,637 ms` → `12,22 FPS`.
- somme des composantes driver visibles `feed_us + wait_us + cache_us = 35,316 ms/image`, laissant `submit - somme = 4,964 ms/image` inexpliqué dans le paquet (`40,280 - 35,316`).

**Conclusion de budget :** une seule optimisation logicielle ne peut pas promettre plus que la suppression d’une composante mesurée. Le levier le plus défendable, pour l’instant, est la réduction des passes/soumissions inutiles, pas un FPS cible.

## 3. Distinction des classes de coût

| classe | où elle apparaît | ce que mesurent les sources | ce qu’il ne faut pas faire |
|---|---|---|---|
| logique/adviser/simulation | `simulation`, adviser inclus dans simulation | vrai tour exploration 8,774 ms/image ; maison 6,050 ms/image | optimiser moteur sans preuve d’hotspot |
| préparation CPU | `preparation`, `mesh_publish`, rebuilds | maison contrôlée candidate 22,877 ms/image ; vrai tour maison 26,730 ms/image | attribuer indûment au raster natif |
| SUBMIT pilote | `submit`, `L3Render.feed_seconds` → `PRODOCK_SUBMIT` | candidate maison 40,280 ms/image avec feed 0,754 + wait 33,156 + cache 1,406 ms | dire « tout submit = attente GPU » |
| attente native | `wait_us` dans `prodock-gpu.c` | `readl_poll_timeout` jusqu’à complétion attendue | appeler ça fillrate |
| publication/versionning | `feed`, `wmb`, `(void)readl(memory)`, cache sync | `prodock-gpu.c:151-172` | réduire barrières sans preuve |
| PRESENT | `present`, display wait | candidate maison 14,223 ms/image ; vrai tour 12,263 ms/image | transformer l’affichage en source de FPS |
| géométrie (cycle modulo 32) | compteurs `vertices`, `triangles`, `culled` | candidate maison 687,6 triangles/image ; exploration 1799,8 triangles/image | déduire un total cycles réel d’un modulo 32 |
| rasters/pixels UI | `L3Render.mini_*`, counters legacy | vrai tour maison raster 6,04 ms/image et compare/publish 5,73 ms/image | doubler dans préparation |

**Fait :** dans `games/luma3d/build-kernel/.../drivers/prodock/prodock-gpu.c:127-188`, `submit` fait, dans cet ordre :
1. validation de tout le batch (`136-140`);
2. test de signature géométrie si `geometry >= PRODOCK_GEOM_MATRIX` (`141-144`);
3. test d’erreurs (`145`);
4. `prodock_cache_sync()` chronométré dans `p->cache_ns` (`147-150`);
5. barrière `wmb()` et lecture MMIO (`151-152`);
6. alimentation FIFO mot à mot avec poll si FIFO plein (`163-168`) ;
7. `mb()` et `feed_ns` (`171-172`);
8. `readl_poll_timeout` jusqu’à complet (`174`);
9. `usleep_range(10,20)` (`177`);
10. `wait_ns` (`178`);
11. erreurs puis second `prodock_cache_sync()` (`179-183`).

Donc `wait_us` inclut l’exécution complète du lot, y compris tout l’overdraw/culling possible ; mais aucune mesure fragment/texel n’est exposée (`FULL TOUR COSTS` l’affirme).

## 4. Piste logicielle minimale recommandée

**Fichier** : `games/luma3d/build/maze_events_20261027_r4/source/games/luma3d/src/render.c`.

État actuel :

    if(!(mode==L3_MINI_MAZE+1?l3_maze_render(r,g):l3_arcade_3d_render(r,g)))return 0;

...
if(mode==L3_ARCADE_SHOOTER+1&&!l3_shooter_render(r,g,&scene))return 0;

Patch minimal :
- supprimer le `flush(r)` immédiatement après rendu 3D de maze/platform (`render.c:309`) ;
- conserver le test `if(r->failed)return 0;` après le rendu ;
- laisser `l3_mini_ui_prepare` émettre ensuite ses commandes dans le même lot ;
- conserver le `flush(r)` avant `PRODOCK_PRESENT` (`render.c:318`) comme seule clôture GPU de l’image.

Effet attendu : une soumission driver au lieu de deux pour les images maze/platform avec UI. L’ordre des commandes reste identique : géométrie d’abord, puis présentation. Le FIFO ne voit qu’une seule séquence.

**Point B — exploration**, autour de `render.c:321-457` :

État actuel :
- dessin du monde (`render.c:359-436`) ;
- `flush(r); if(r->failed)return 0;` à `render.c:452` ;
- `l3_hud_prepare(r,g,&scene)` (`render.c:454`) ;

Patch minimal :
- supprimer le `flush(r)` de `render.c:452` ;
- laisser le `flush(r)` implicite/finale des préparations et le `PRODOCK_PRESENT` clôturer.

Effet attendu : une seule soumission pour géométrie monde + HUD.

**Précautions de mémoire et publication :**
- `emit()` appelle déjà `flush()` si `r->batch.count==PRODOCK_BATCH_MAX` (`render.c:55`). Donc le patch ne peut pas faire déborder le lot ; si le maximum est atteint, un flush automatique conserve l’ordre.
- Aucun buffer de mesh n’est modifié par ce patch. Les pages `maze_dynamic[page]` restent alternées par frame ; le `flush` final de l’image sert toujours de barrière de complétion avant que la génération future d’un frame ultérieur réutilise l’autre page.
- Aucune écriture CPU de VRAM n’est ajoutée. Les shadows VRAM ne sont pas lues pour comparaison.
- Pas de modification FPGA/kernel/driver. Seul le nombre d’appels `PRODOCK_SUBMIT` côté client app C change.

### 4.2 Bornage du gain, pas promesse

Pour la maison contrôlée candidate :
- coût d’une soumission inexpliqué mesuré : `4,964 ms/image` ;
- le gain maximal théorique si tout ce résidu était évité par une soumission unique est donc `≤ 4,964 ms/image`, soit un passage possible de `81,637 ms` à `76,673 ms` dans ce cas parfait, mais uniquement si aucun autre effet caché n’en absorbe une partie ;
- le composant GPU pur (`wait_us`) de `33,156 ms/image` n’est pas attaqué par ce patch.

Pour l’exploration :
- le paquet ne fournit pas `feed_us/wait_us/cache_us` par mode en vrai tour ; il ne faut donc pas prétendre un gain numérique pour l’exploration. Le gain doit être mesuré séparément en mode borné avec compteurs pilote.

### 4.3 Ce que le patch ne prétend pas faire

- Il ne réduit pas le nombre de commandes ni de triangles.
- Il ne change pas les recettes de culling, de tri, de textures, de fogging.
- Il ne change pas `r->triangles`, `r->draws`, `r->commands` attendus (le compteur `commands` reste identique dans la même séquence).
- Il ne prouve pas le fillrate GPU. Il cible l’ordonnancement public et le coût fixe par soumission, qui est justement séparé par les compteurs.

## 5. Étude et décision sur « fond couleur+Z statique »

### 5.1 Conditions exactes où une telle approche serait acceptable

Il faudrait toutes les conditions suivantes :
1. caméra 3D bit-identique chaque image : matrice, near/far, projection, taillefocale. Dans `l3_maze_render`, l’œil et la cible sont dérivés de `v.width/v.height` (`eye={v.width,42,v.height+9}`, `target={v.width,0,v.height}`), donc ils sont en principe stables pour une grille fixe.
2. éclairage, matériau et texture stables : `light`, `material`, `texture` sont repositionnés mais leurs paramètres sont constants dans `l3_maze_render`.
3. mailles statiques complètes et immuablespour le niveau : `r->maze_static_count` déjà calculé une fois et réutilisé.
4. pas d’affinement LOD dépendant de la distance caméra qui changerait le volume statique. Dans l’exploration, ce mécanisme existe pour les instances world (`distance>a->lods[j].distance`) ; pour la maison maze, les murs sont générés une fois.
5. cible d’affichage et scissor identiques.
6. maîtrise parfaite de la profondeur : chaque pixel dynamique doit être testé contre le fond statique correct, et la profondeur dynamique précédente ne doit pas corrompre la nouvelle image.
7. possibilité technique de restaurer couleur et profondeur statiques dans la page courante sans lecture VRAM interdite.

### 5.2 Pourquoi on la rejette pour cette piste

**Cause de rejet : préservation de l’occlusion.**
- La maison contient des éléments dynamiques chaque image : granulés, power pellets, courier, fantômes et éventuellement anneau guide mobile (`candidate_maze_render.c:geometry()` et `l3_maze_render()`).  
- La profondeur n’est pas doublement tamponnée : la cible utilise `page (frame&1)` pour la couleur, mais la profondeur reste `PRODOCK_GPU_BASE+2*r->page_bytes` (`l3_maze_render`, `t=... +2*r->page_bytes`).  
- Si on garde les fonds statiques sans réIRON les dynamiques, la profondeur dynamique de la frame précédente reste dans la page unique de profondeur. Un acteur nouveau peut alors être rejeté à tort par un acteur ancien devenu hors écran, ou au contraire laisser une couleur fantôme là où aucun nouvel élément n’est dessiné.  
- Effacer seulement la profondeur dynamique pour garder le fond statique n’est pas suffisant si le masque dynamique n’est pas exact pixel-par-pixel. À défaut, on change les occlusions : précisément le rejet demandé.

**Cause de rejet : copie couleur+Z non prouvée.**
- La source montre `gpu_v1_copy` pour copier le dégradé de ciel d’un buffer de fond vers la cible (`render.c:339`, `background`), mais les sources fournies ne prouvent pas qu’il copie la profondeur, ni que le pilote expose une copie couleur+Z atomique.  
- Les sources ne prouvent pas non plus un registre de masque dynamique ou une opération de restore Z dans le DRM/Pilote.  
- Lire la VRAM pour comparer est explicitement interdit (« No CPU reads of noncacheable VRAM for comparisons »). Écrire sans preuve d’équivalence ne serait pas un audit probant.

**Cause de rejet : coût de validation.**
- Pour prouver l’équivalence, il faudrait une capture pixel complète et une différence bit-à-bit, ce qui dépasse le budget mémoire de console et les contraintes du paquet (pas de lecture VRAM comparative).  
- La modification toucherait l’occlusion, donc elle n’est pas dans la contrainte « préserve pixels/occlusion/logique ».

**Décision :** on **rejette** le fond couleur+Z statique comme piste minimale now. On ne le maintient pas comme réserve sauf si un futur paquet démontre une copie profondeur documentée, une cible profondeur doublement tamponnée et une différence pixel avec capture certifiée.

## 6. Causes non prouvées : ce qu’il faut dire explicitement

1. **« submit = pure attente GPU »** n’est pas vrai. `submit` contient validation, double `cache_sync`, barrières, alimentation FIFO, attente completion et `usleep_range` (`prodock-gpu.c:127-188`).  
2. **« wait_us = preuve de fillrate »** n’est pas vrai. `wait_us` ne dit que le temps jusqu’à complétion d’un ensemble de commandes, avec granularité poll et absence de compteurs fragment/textures.  
3. **Le surcoût de 4,964 ms/image** de `submit` vs `feed+wait+cache` n’est pas expliqué dans le paquet. Hypothèse plausible : overhead d’ordonnancement/poll/cache et driver, mais non prouvée.  
4. **La géométrie cycles** est un compte modulo 32, pas un total. `cycles_mod32` ne permet donc pas de calculer une moyenne de coût par triangle.  
5. **L’exploration n’a pas de fenêtre contrôlée** : le paquet contient des fenêtres pour les modes `1,3,4,5,6`, pas pour le mode 0. Le vrai tour dit exploration `10,647 FPS`, mais pas `feed_us/wait_us/cache_us` par mode. Donc toute attribution précise de l’attente native à l’exploration est une conjecture.  
6. **Le vrai tour maison n’est pas la fenêtre contrôlée 360 images**. Les chiffres contrôlés (12,22 FPS) sont pour une fenêtre de 6 s simulées à 1 tick/image et ne couvrent pas tous les états denses tardifs de la démo.  
7. **Les zéros UI legacy du Solitaire/Simon mode natif ne signifient pas zéro travail CPU** (`COUNTER SCOPE`). Ne pas conclure d’un coût UI nul.

## 7. Tests discriminants à faire, sans lancer d’outil ici

### 7.1 Tests locaux host (avant hardware)

Objectif : prouver la conservation bit-à-bit des sorties logiques et l’absence de dépassement de lot.

1. **Capture commandes** avec `--host --frames 1 --capture prefix` (`main.c` accepte `--capture` seulement host, `main.c:45`) :
   - comparer le fichier `*.commands` et `*.json` baseline vs patched ;
   - CRC32 de l’état arcade en sortie (`state_crc32`) doit être identique aux valeurs connues (`probe_metrics.py` vérifie `re.fullmatch('[0-9a-f]{8]', state_crc32)` et `exited==0`).
2. **Temps de boundaries CPU** : mesurer `r->feed_seconds`, `r->present_seconds`, `r->commands`, `r->total_flushes` en host ; vérifier que le nombre de flush driver conceptuellement attendu baisse d’une unité par image dans les modes concernés, sans changement de `commands`.
3. **Test de saturation du lot** : générer artificiellement une image dont `r->batch.count` approche `PRODOCK_BATCH_MAX` ; l’auto-flush de `emit()` doit laisser reprendre exactement la même commande avec le même hash. Pas de réordonnancement.
4. **Adversaire mémoire** : forcer `r->failed=1` pendant un lot partiel ; vérifier que l’image rendue n’est pas présentée et que le CRC final d’état reste le même (`ok==0`, `exited==1` interdit).
5. **Comparaison d’artifacts** : `l3_render_dump()` écrit mémoire et JSON ; le CRC de capture doit rester stable après le patch dans toutes les phases `entry/rest/moving`.

### 7.2 Mesure future bornée sur Pro Dock

Paramètres proposés, sans nouvelle tolérance :
- Mode 4 maison, contrôlé, `--frames 360`, `--wall 0` impossible pour `probe` car il exige `fixed_frames` ; utiliser la fenêtre GM1 standard `360 images` exactement comme le paquet (`SCOPES`).
- Capturer `GPU_COUNTERS` : `feed_us`, `wait_us`, `cache_us`, `present_us`, `presents`, `vertices`, `triangles`, `culled`, `slivers`, `cycles_mod32`.
- Capturer `GPU_PHASE` : `simulation`, `preparation`, `submit`, `present`, `commands`, `batches`, `ui_bytes`, `rasters`, `state_crc32`, `max_frame`, p95/p99.
- Vérifier `GPU_DONE` : `ok=1`, `active=mode+1`, `showcase=1`, `hardware=1`, et l’état CRC d’encode dans la phase moving.
- Comparer baseline vs candidate sur **les mêmes métriques**, pas sur FPS seulement.
- Pour exploration : comme `gpu_motion_probe` n’accepte pas le mode 0 (`main` limitera `kind` à `1,3,4,5,6`), noter l’absence d’un probe mode 0 comme évidence manquante. Étendre le probe mode 0 serait hors du paquet actuel ; ne pas le présenter comme déjà possible.

### 7.3 Critères de rejet/arrêt de la piste

La piste consolidation flush doit être abandonnée si un de ces points apparaît :
- augmentation de `presents` ou apparition d’`underflows`/`errors`/`faulted` dans les compteurs Pro Dock ;
- augmentation de `wait_us` moyenne de plus du bruit `usleep_range(10,20)` sans compensation ;
- changement du `state_crc32` ou de `exited!=0` ;
- différence dans la capture `*.commands` au nom des tests host ;
- hausse de `max_frame` au-delà des pics fournis : maison contrôlée candidate déjà `0,127932 s` max ; toute dégradation majeure invalide.

## 8. Synthèse pour décision

La cause actuellement la mieux étayée par les mesures n’est pas l’attente GPU, mais la **préparation CPU** dans `maison`, avec une différence candidate/baseline de `-36,977 ms/image`. Le `submit` natif ne bouge presque pas (`-1,285 ms`). Le fond couleur+Z statique est à rejeter pour préserver les occlusions. La seule piste minimale et probalement testable sans violation des contraintes est la **fusion d’une soumission driver par image** dans les chemins qui aujourd’hui font une soumission géométrie plus une soumission UI/présentation, avec preuves host sur les CRC et preuves hardware sur les compteurs pilote. Elle ne promet aucun FPS.
