## Verdict synthèse

Le patch est **cohérent comme candidat expérimental à synthétiser/router**, pas comme preuve que la panne Neo est résolue. Les tests idéaux v2 ont prouvé le comportement RTL extrait sur 4 déphasages de référence (releases=15, `events.csv`), mais ils ne constituent ni une qualification physique, ni une preuve sur la cause black-screen/DMI. Aucun contre-exemple purement logique certain n’est visible dans le banc figé fourni, mais il existe une incertitude physique réelle sur le reset asynchrone et sur les limites GoaWin/PLL documentées.

## Faits établis par le paquet

1. **Anomalie parente confirmée seulement en simulation idéale** : `real50MHz/80MHz`, la chaîne extraite reproduisait (a) qualification de délai stale après perte de `LOCK` entre fronts clk50, (b) release POR d’un cycle avec `delay_done=0` après une perte échantillonnée. Preuve de simulation, pas preuve causale du matériel R21.  
2. **Patch RTL candidate** dans `neo_reset_trial.v` : ajout de `MIN_LOCK_CYCLES = 104000` (2,08 ms), `MAX_WAIT_CYCLES`, invalidation asynchrone des deux bits `ready_meta` via `negedge available`, exigence d’une nouvelle qualification, effacement de `wait_count`/`delay_done` pendant hold/command, permission `release_request = available && ready_meta[1] && !holding && delay_done`. Voir lignes candidate `neo_reset_trial.v:5,7,16-17,27,75-78,102-114`.  
3. **AHB** : `console_neo.v` candidate passe `rst_key_n(ae350_por_n && trial_request)` à `ae350_soc` au lieu du seul `ae350_por_n`. Voir diff hunk lignes SDL/V verilog correspondantes et `exact_chain.sv:30`.  
4. **Validations idéales** : `root_phase_sweep_01/result.json` passe sur 4 phases (`9000, 9500, 10000, 10001`) ; logs montrent `INVARIANTS_PASS ... releases=15`. Le bench `invariants_tb.sv:17-28` impose : pas de release zero-delta, pas de release si `!available || !done || holding`, pas de release sous 2 ms après montée `LOCK`, et intervalle 50 ms ou 2,08 ms selon mode.  
5. **Contraintes existantes** : SDC inherited, aucune nouvelle exception ajoutée. Existant :
   - `set_max_delay 8 -from [clk50] -to [bus80_clk]` et inverse, lignes SDC 30-33 ;
   - `set_false_path -to [get_pins {ae350_rst_sync_*/PRESET}]`, SDC ligne 37 ;
   - max delay 8 entre clk50/bus80 et plusieurs autres domaines.

## Ce que le patch prouve réellement

- En simulation idéale, le bistable de qualification n’est plus “stale” sur perte `available` : `ready_meta` revient à `2'b00` immédiatement sur `negedge available` (`neo_reset_trial.v:75-78`), donc `release_request` tombe sans attendre le prochain front clk50.  
- Un intervalle complet est exigé après hold ou commande : `wait_count <= 0` sur `holding || command_valid`, avec cible selon `delay_mode ? WAIT_CYCLES : MIN_LOCK_CYCLES` (`neo_reset_trial.v:102-111`).  
- En mode0, la durée minimale observée est ~2,08 ms au lieu d’un bypass (`events.csv`, `MODE0 no longer short diagnostic interval`).  
- Les pertes de référence sont aussi couvertes en simulation `case_id=14` (`invariants_tb.sv:88-89`) avec clock arrêtée, par le reset async.  
- Les deux étages AHB sont invalidés quand permission tombe : `rst_key_n = ae350_por_n && trial_request` force `init_sync` à 0 (`exact_chain.sv:30`, `ae350_soc` reset async).  

## Anomalies certaines ou tensions contractuelles

### 1. Le reset asynchrone est redéfini sans synchroniseur dédié de désassertion

Parent : `ready_meta <= {ready_meta[0], ddr_ready && pll_ready};` synchronisé sur front clk50 (`neo_reset_trial.v` parent lignes 70-71). Candidate : `always @(posedge clk_ref or negedge available)` avec reset `ready_meta <= 2'b00` même entre fronts clk50 (`candidate neo_reset_trial.v:75-78`). C’est volontaire au titre du défaut parent, mais cela fait d’un signal combinatoire `available = ddr_ready && pll_ready` un reset asynchrone des flops qui constituent précisément la synchronisation. L’assertion est immédiate ; la **désassertion** attend le prochain front clk50, comme prévu. Cependant, toute transition de `available` à l’envers du clock interne ou tout glitch court plusieurs fois respecte le modèle idéal, pas la physique.

### 2. `available` est déjà un signal susceptible de glitch

Le paquet rappelle UG306 p.40/table 5-2 : surveiller `LOCK` continuellement ≥2 ms, `LOCK` peut glitcher pendant verrouillage. Le patch clarifie “loss invalidates authorization even between reference-clock edges”, mais un glitch d’`available` asynchronous va réinitialiser `ready_meta`, puis exiger 2,08 ms ou 50 ms. C’est conservateur, mais la sensibilité asynchrone convertit toute instabilité brève en reset long. Ce n’est pas une erreur logique idéale, c’est une limite physique non bornée par les tests.

### 3. La constrained chain AHB n’a pas été mise à jour pour le nouveau sens de `rst_key_n`

La false path existante SDC ligne 37 cible uniquement `ae350_rst_sync_*/PRESET`, i.e. premier étage `ae350_rst_sync` qui se reset uniquement sur `negedge pll_ae350_lock`. Le candidate rend aussi `init_sync` resettable par `trial_request` via `ae350_por_n && trial_request` (diff `console_neo.v`, `exact_chain.sv:30`). Or `trial_request` est issu de clk50, alors que `init_sync` est clocké par `bus80_clk`. En candidate, la dz assertion de `rst_key_n` n’est plus unique à un registre déjà disjoint, et la désassertion n’est pas synchronisée au domaine 80 MHz. Les tests idéaux ne détectent pas cela. C’est une **tension contractuelle avec la contrainte SDC existante**, pas une proposition automatique d’exception supplémentaire. La juste position est : ne pas ajouter de `false_path` large sans synchroniseur nommé, et faire analyser le chemin de reset après synthèse.

### 4. La contrainte `bus80/clk50` borne le propagation delay, pas une largeur minimale de pulse physique

SDC fournit max delay 8 ns et clock 50/80 MHz. Le paquet rappelle correctement que DS1239 RSTMIN-PULSE 10 ns est une spécification PLL, pas une largeur minimale fabric. Donc le test idéal 1 ns ne prouve pas capture physique d’un pulse de 1 ns. Aucun contre-exemple logique ici ; c’est une limite analogique.

### 5. Mode 0 à 2,08 ms reste un choix diagnostic, pas une provenance vendor

`MIN_LOCK_CYCLES = 104000` correspond à la consigne UG306 de monitoring LOCK ≥2 ms, pas à une durée minimale prouvée d’AE350 POR/HW, car aucune donnée quantitative n’a été trouvée dans MUG1031. Le mode1 conserve 50 ms selon décision utilisateur. Le paquet dit bien que le précédent 20 ms est un exemple Sipeed fondé sur `DDRready`, pas une preuve vendeur. C’est un choix de marge, non une cure.

## Contre-exemple idéal identifié ?

Aucun contre-exemple **certain** à l’invariant testé dans le frozen bench :
- pas de `RELEASE` unqualified,
- case 9 : commande invalide et préfixe expiré n’incrémentent pas l’époque,
- case 13 : AHB stoppé conserve warm-reset puis qualification,
- case 14 : clock référence arrêtée avec perte `LOCK` reste reset,
- case 15 : perte DDR restores puis qualifie.

Cependant, un point logique mérite une vérification plus fine : au moment d’un `command_valid` concurrent avec un état déjà actif, `holding` et `delay_done` sont mis à jour dans des always concurrents. Dans le même cycle, `release_request` combinatoire peut encore lire l’ancienne valeur de `holding`/`delay_done` dans le modèle d’événements delta, même si `command_valid` force déjà la qualif à zéro dans le second bloc (`neo_reset_trial.v:75-78`, `83-98`, `102-111`). Le banc n’excite pas ce case en publication, et le downstream AE350 a déjà un retard de deux flops. Je ne le qualifie pas de contre-exemple établi, mais c’est le seul point à tester par une extension discrimante.

## Evidence manquante à ne pas présenter comme acquise

1. **Trois phases ordinaires et mapping primitif** explicitement “pas encore complétés” selon le paquet. Aucune preuve de comportement dans FPGA map/route.  
2. **Timing post-route** Gowin, recovery/removal du reset asynchrone, propagation réelle du `trial_request`, jitter de phase.  
3. **Analog** : durée effective des glitchs `LOCK`, réponse de `ddr_ready`, capture physique d’un pulse ≤10 ns.  
4. **Causalité réelle** : absence de preuve qu’une perte `LOCK` est la cause du black-screen/DMI R21. R19 reste le fallback physique.  
5. **AE350** : pas de durée POR/HW quantitative trouvée dans MUG1031 ; la décision 50 ms/2,08 ms reste une marge, pas une exigence prouvée.

## Jugement pour synthèse/route

Oui, le patch est suffisamment cohérent comme **candidate isolate**, à condition de le garder strictement expérimental et de ne pas le présenter comme qualification physique. Modifications fonctionnelles à respecter avant envoi :
- conserver le contrat : mode0 exige un intervalle complet, mode1 50 ms, commandes conserve tramage et hold ;
- ne pas ajouter de `false_path` global pour `ready_meta` ou `init_sync` sans identifier le synchroniseur exact ;
- faire analyseer les chemins `clk50 -> bus80_clk` et le reset `trial_request` avec le max delay 8 ns existant ;
- mettre à jour le commentaire de reset (`console_neo.v:147-152`) pour expliquer que `rst_key_n = ae350_por_n && trial_request`, et donc le premier étage reste `LOCK`, tandis que le second est la permission de release candidate.

## Test discriminant recommandé

Créer un seul cas idéal : pendant une release active valide, envoyer une commande valide sans arrêter AHB, et asserer dans le même front que `command_valid=1`, `holding_old=0`, `delay_done_old=1`, puis vérifier que `rst_key_n` et `por_n` baissent dans la fenêtre correspondant au chemin de reset async, sans release supplémentaire. Si ce cas échoue, la correction minimale serait d’ajouter directement `!command_valid` à la permission, non d’un nouveau domaine d’horloge. Ce test restera cependant un test idéal, pas une qualification Gowin.
