Je n’ai exécuté aucun test, aucune simulation et aucun accès carte. Analyse strictement fondée sur le packet fourni.

## 1. Faits établis

- R19, premier ARM :
  - commande `ARM` = `1`, séquence attendue `1`, écriture à `1793137186650` : `r19_usb_video.log:41`.
  - statut après ACK : `0x55544e41 0x0 0x1` → `busy=0`, `seq=1` : `r19_usb_video.log:42,44,46`.
  - banque lue deux fois, identique, premiers mots `0x55544e41 0x0 0x1` : `r19_usb_video.log:43,45`.
  - échec sur le header : `UTNA captured header differs` : `r19_usb_video.log:47`, avec pile `r19_usb_video.tcl:63,71`.
- Le contrat Tcl exige `[ID, 1, command]`, donc pour ARM `[ID, 1, 1]` : `utna_protocol.tcl:41`. La banque est relue deux fois et doit être stable : `utna_protocol.tcl:31-40`.
- RTL : le vecteur `live` place bien :
  - mot 0 = `0x55544e41`,
  - mot 1 = `32'd1`,
  - mot 2 = `command` : `usb_idle_trace.v:155-159`.
- Netlist exacte R19 : `snapshot_64` a `D=command[0]`, `snapshot_32` a `D=VCC`, avec le même enable `n1170_3` : `console_neo.vg:70126-70139`. Un étage du cône de mux de données de `u_replies` utilise bien `snapshot[32]` : `console_neo.vg:61491-61498`.
- Le FIFO de réponses est instancié dans `usb_idle_trace` : `usb_idle_trace.v:49-54`, netlist `console_neo.vg:82042-82088`. Le côté lecture a `rd_ready(!hreset)`, donc il est toujours prêt : `usb_idle_trace.v:54`.
- L’écriture banque se fait sur chaque `reply_valid`, avec `receive_index` incrémenté dans le même `if` : `usb_idle_trace.v:69-72`. `busy` est remis à 0 quand `receive_index==31` : `usb_idle_trace.v:71`.
- Les modules `usb_idle_trace` et `ddr_dcfifo` sont identiques entre R19 et R21r2 d’après le packet. R21r2 n’a pas été observé.

## 3. Latence snapshot → reply FIFO → head → bank

Séquence RTL attendue :

1. `cmd_pop` charge `snapshot <= live`, met `sending=1`, `send_index=0` : `usb_idle_trace.v:160-165`. Aucune écriture FIFO ce cycle-là, car `sending` ancien vaut 0.
2. Cycles suivants : 32 écritures dans `u_replies`, `send_index=0..31`, puis `sending<=0` : `usb_idle_trace.v:49-52,166-168`.
3. Côté `hclk`, le FIFO synchronise les pointeurs, charge la tête, et `reply_valid` est présenté : `ddr_dcfifo.v:103-135`. Le consommateur écrit `bank[receive_index] <= reply` sur `reply_valid` : `usb_idle_trace.v:69-72`.
4. L’ACK `busy=0` n’apparaît qu’après `receive_index==31` : `usb_idle_trace.v:71`.

Conséquences :

- Le mot 1 est écrit **tôt** dans la rafale, bien avant l’ACK. Une simple “latence pas encore arrivée” pour le mot 1 est peu compatible avec deux lectures identiques après ACK.
- Un décalage global d’un mot donnerait plutôt `[ID,1,1,...]` ou `[ID,1,0,...]`, pas `[ID,0,1,0,...]`.
- Une perte pure du mot 1 donnerait `[ID,1,0,...]`. Une insertion d’un zéro avant le mot 1 donnerait `[ID,0,1,1,...]`.
- L’observation `[ID,0,1,0,...]` est donc surtout compatible avec un **remplacement isolé du mot 1 par 0**, ou avec une lecture de `bank[1]` qui ne renvoie pas le mot écrit. Ce n’est pas une preuve, mais c’est le motif le plus parcimonieux.

## 4. Hypothèses et absence de démonstration

### H1 — Le mot 1 vaut 0 à l’écriture FIFO / banque

C’est l’hypothèse la plus simple : `bank[1]` reçoit `0` au lieu de `1`.

- Pour : le motif `[ID,0,1,0,...]` correspond à un mot 1 remplacé par 0, avec le mot 2 = commande = 1.
- Contre : `snapshot[32]` est un DFFRE à `D=VCC` dans la netlist exacte (`console_neo.vg:70133-70139`), avec le même enable que `snapshot[64]` (`:70126-70132`). Si `snapshot[64]` a bien chargé `command=1`, `snapshot[32]` devrait valoir 1.
- Point non couvert : le packet ne montre pas le cône complet de sélection `send_index=1` jusqu’à la donnée d’écriture du FIFO. Un **contre-exemple RTL possible** est donc : le mux de write-data de `u_replies` sélectionne, pour `send_index=1`, un mot nul (par exemple `ticks`) au lieu de `snapshot[63:32]`. Le LUT `n181_s53` avec `snapshot[32]` (`console_neo.vg:61491-61498`) est un indice contraire, mais pas une démonstration du cône complet.

### H2 — `bank[1]` n’a jamais été écrit et vaut 0

- Pour : la valeur est stable et identique sur deux lectures.
- Contre : en RTL, `receive_index` n’est incrémenté que dans le même `if(reply_valid)` que l’écriture banque (`usb_idle_trace.v:69-72`). Il faudrait une différence netlist sur le write-enable RAM, ou un défaut de lecture, pour “sauter” l’index 1.
- Aucune preuve dans le packet.

### H3 — La lecture `+44` ne renvoie pas `bank[1]`

- Le packet ne fournit pas le mux final `bank[bank_index]` ni la sélection `bank_0`/`bank_1`.
- Les RAM banque sont visibles : `bank_bank_0_*` avec `WAD(receive_index[3:0])`, `RAD(address[5:2])` (`console_neo.vg:77015-77021`), et `bank_bank_1_*` (`:77079-77085`). Le cône de sélection lecture n’est pas fourni.
- Deux lectures identiques ne distinguent pas “banque fausse” de “lecture fausse”.

### H4 — Impulsion `reply_valid` en trop ou en moins

- Le côté lecture du FIFO est en libre écoulement (`rd_ready = !hreset`, `usb_idle_trace.v:54`) et le consommateur écrit banque sur `reply_valid` sans compteur de réception ni garde `busy/receiving` (`:69-72`). `busy` est cleared à `receive_index==31`, mais l’écriture banque reste enabled.
- Une impulsion en trop après les 32 mots peut réécrire `bank[0]`, `bank[1]`, etc. ; une impulsion manquante peut laisser un trou.
- Toutefois, le motif observé n’est pas expliqué à lui seul par cette faiblesse : une impulsion en trop réécrirait avec les mots 0/1, pas nécessairement avec 0. Il faut un compteur de `reply_valid` pour discriminer.

### Ce qui n’est pas soutenu par le packet

- **ARM pré/post** : le snapshot est explicitement pré-clear (`usb_idle_trace.v:6,163-165`), et la branche `clear` (`:172-183`) ne remet pas `snapshot[32]` à 0. Le 0 du mot 1 n’est pas expliqué par le pré/post ARM.
- **Défaut silicium** : aucune preuve. La netlist montre `D=VCC` et la banque est stable ; cela ne prouve pas l’absence de défaut, mais ne l’établit pas.
- **USB HS/fréquence** : le packet ne qualifie ni le timing ni une énumération HS ; `comparison.md:3` le rappelle explicitement.
- **R21r2** : non testé. Les modules USB/FIFO étant identiques, un défaut interne à ces modules serait *a priori* reproductible sur R21r2 ; mais un effet top-level/reset reste possible. Aucune conclusion R21r2.

## 5. Tests locaux discriminants

### Test 1 — Simulation RTL avec assertions sur le chemin exact

Sans modifier le RTL, instrumenter un testbench :

- après `cmd_pop` avec `command=1`, vérifier que la donnée d’écriture de `u_replies` vaut `32'h00000001` quand `send_index==1` ;
- vérifier exactement 32 écritures FIFO et 32 impulsions `reply_valid` ;
- vérifier que `receive_index` prend chaque valeur `0..31` exactement une fois ;
- vérifier `bank[1]==32'h1`, `bank[2]==32'h1`.

Si l’assertion `wr_data==1` échoue, on a un **contre-exemple RTL démontré**. Si elle passe mais `bank[1]!=1`, le défaut est dans la capture/lecture banque.

### Test 2 — Même test en gate-level avec la netlist exacte

Comparer RTL et netlist :

- RTL passe, gate-level échoue → suspect mux post-synthèse, RAM, ou CDC.
- Les deux échouent → contrat RTL.
- Les deux passent → problème de harness/lecture carte ou de séquence de reset réelle.

### Test 3 — Deux commandes sur carte, sans relâcher le header

Faire exécuter par le propriétaire de la carte un diagnostic séparé :

1. restaurer, lire `snapshot_count` (`0xe9002008`) ;
2. ARM, logger la banque brute ;
3. DISARM (`command=6`), logger la banque brute ;
4. comparer.

Interprétation :

- ARM `[ID,0,1]` puis DISARM `[ID,0,6]` → défaut systématique du mot 1, pas un démarrage.
- ARM `[ID,0,1]` puis DISARM `[ID,1,6]` → problème de première capture / état initial.
- Le header doit rester `[ID,1,command]` ; ce test est diagnostique, pas une acceptance.

### Test 4 — Lecture individuelle vs rafale

Lire séparément :

- `0xe9002044` seul ;
- puis `0xe9002040` puis `0xe9002044` ;
- puis la rafale 32 mots actuelle.

Si `+44` seul vaut 1 mais la rafale vaut 0, le problème est dans l’adressage/rafale/`video_bus_stage` (`video_bus_stage.v:15-35`), pas dans la capture. Lire aussi `+80`/`+84` pour tester la seconde moitié de banque et la sélection `bank_0`/`bank_1`.

### Test 5 — Rendre le mot 3 non nul

Laisser la fenêtre ARM tourner pour obtenir `ticks != 0`, puis vérifier :

- `bank[2] == command` ;
- `bank[3] == ticks` non nul ;
- `bank[1]` toujours 0.

Si `bank[3]` est correct et `bank[1]` reste 0, le défaut est isolé au mot 1, pas un décalage global ni une latence générale.

### Test 6 — Compter les impulsions de réponse

Si un compteur de debug peut être ajouté temporairement, compter `reply_valid` entre `cmd_pop` et `busy=0`. Le contrat attend 32. Un compte de 31, 33 ou plus orienterait vers H4 ; un compte de 32 avec `bank[1]=0` orienterait vers H1/H2/H3.

## 6. Patch minimal proposé — non appliqué

### P1 — Testbench, pas de patch RTL

Ajouter les assertions du test 1. C’est le moyen le moins intrusif de prouver ou d’exclure un contre-exemple RTL.

### P2 — Durcissement du contrat de capture banque

Dans `usb_idle_trace`, autour de `:69-72`, ajouter un compteur explicite et interdire le wrap silencieux :

```verilog
reg [5:0] reply_words;
...
if(cmd_pop) reply_words <= 0;
if(reply_valid) begin
  if(reply_words < 32) begin
    bank[reply_words[4:0]] <= reply;
    reply_words <= reply_words + 1'b1;
    if(reply_words == 31) begin
      snapshot_count <= snapshot_count + 1'b1;
      busy <= 0;
    end
  end else begin
    rejected <= 1; // impulsion en trop : rendre le défaut observable
  end
end
```

Ce n’est **pas un correctif du header** : cela rend seulement visible une impulsion en trop et empêche une réécriture de `bank[0..]` après l’ACK. À ne pas présenter comme la cause tant que le test 1 n’a pas parlé.

### P3 — Tcl diagnostique, sans relaxation

Ajouter des lectures brutes de `snapshot_count` et de `+44` seul, et poursuivre vers DISARM dans un script **diagnostique séparé**. Le contrôle d’acceptation doit rester `utna_protocol.tcl:41` tel quel.

## 7. Conclusion

Le packet établit une **violation de contrat réelle et stable dans la fenêtre lue** : header `[ID,0,1]` au lieu de `[ID,1,1]` pour ARM. Il ne démontre pas :

- que `snapshot[32]` vaut 0 au moment de l’écriture FIFO ;
- que `bank[1]` a reçu 0 plutôt que d’avoir été mal lu ;
- que le FIFO a perdu, dupliqué ou décalé un mot ;
- un défaut silicium ;
- un effet ARM pré/post ;
- un comportement R21r2.

Le test le plus discriminant est la simulation avec assertion sur la donnée d’écriture de `u_replies` à `send_index=1`, puis la comparaison RTL/gate-level. Ensuite seulement, un diagnostic carte avec une seconde commande DISARM permettra de distinguer un défaut systématique du mot 1 d’un problème de première capture. Le header ne doit pas être relâché.
