# Revue technique — `l3_simon_light` (code exact)

## 1. Faits établis par lecture du paquet

- `simon_light.c` est une couche de présentation : aucune extension de l'état moteur ni de la sauvegarde; les champs temporels sont `double start[4]`, `last_time`, `pause_time` (`l3_simon.h`/`l3_simon_light.h`, `l3_simon_light.h` lignes 6-13).
- La politique annoncée est temps monotone en secondes, indépendant du `dt` moteur, sans clamage de temps écoulé (`l3_simon_light.h` commentaire lignes 4-7).
- `view_ok()` valide `phase`, `active_color` (≤4), `phase_ms` (≤600), `feedback_ms` (≤240), longueur de séquence, index, statut (`simon_light.c` lignes 7-15).
- `trigger()` pose `start[color]=now-elapsed/1000` (`simon_light.c` lignes 17-20), donc un `elapsed` négatif n'est pas concevable et un déclenchement reste ancré dans le passé.
- `observe()` :
  - vérifie `c`, `b`, finitude/microtonie de `now` (`simon_light.c` lignes 21-22) ;
  - reconstruit un état neuf si `fresh` (epoch différent, état invalide, `a` invalid) (`simon_light.c` lignes 23-25) ;
  - retourne `0` si pause (`simon_light.c` ligne 26) ;
  - gère `SHOW` et `INPUT` feedback (`simon_light.c` lignes 27-36) ;
  - récupère la dernière réponse acceptée sur transition `INPUT -> ROUND_OK/COMPLETE` via `pressed` (`simon_light.c` lignes 38-46) ;
  - déclenche `ERROR` (`simon_light.c` ligne 47) ;
  - force `duration[active]=0` à la sortie de `SHOW`, pour éviter la fuite dans le décalage de 250 ms (`simon_light.c` ligne 49).
- `sample()` utilise `pause_time` si pause, calcule l'enveloppe attack/plateau/release (`simon_light.c` lignes 61-82), et avance `last_time` (`simon_light.c` ligne 82).
- `pause()` décale tous les `start[i]` lors de la reprise (`simon_light.c` lignes 87-92).
- Le moteur `l3_simon` impose réellement le contrat utilisé : phases, durées 600/250/240, `demo_input` ignore `held` (`l3_simon.c`/`.h`).

## 2. Hypothèses et limites

- Je n'ai pas exécuté le banc ; les résultats attendus ci-dessous sont déduits du code exact et des constantes du moteur.
- Les tests proposés sont au niveau présentation : ils pilotent soit le moteur, soit des `L3SimonView` synthétisés de manière cohérente avec `view_ok()`. Aucune simulation d'absence inventée n'est nécessaire.
- Je n'ai pas trouvé de contre-exemple fonctionnel prouvé dans les six classes demandées (`pause/reprise`, `monotonie`, entrée sauvegarde, deux mêmes couleurs consécutives, erreur/fin, démonstration `held` ignoré). Les tests ci-dessous sont donc des tests discriminants : ils passent avec l'implémentation actuelle et casseraient les régressions classiques (clamp 250 ms, ancrage erroné, NULL/non-reprise, smear inter-couleurs).

## 3. Ce que les tests discriminants protègent exactement

1. **Pause/reprise réelle** : gel pendant 50 s, reprise avec avance de 50 ms, niveau inchangé pendant la pause, puis reprise de l'enveloppe sans "saut".
2. **Monotonie stricte** : tout `now < last_time` doit rejeter et laisser l'état byte-à-byte inchangé.
3. **Sauvegarde milieu de `SHOW`/feedback** : entrée par vue sauvegardée et temps arbitraire doit reconstruire correctement l'élaspsé (`start=now-elapsed`), y compris avec deux mêmes couleurs.
4. **Zéro de queue à la sortie de `SHOW`** : même couleur ensuite, pas de smear dans l'interruption de 250 ms.
5. **Erreur/fin** : gain 220/durée 360 pour l'erreur ; réponse finale acceptée allume même à la transition immédiate vers `COMPLETE`.
6. **`held` démonstration** : la couche lumière ne reçoit pas `held`, donc l'API doit continuer à déclencher sur le seul `pressed` lors de la transition finale ; le moteur lui-même ignore bien `held` (`l3_simon.c`, `l3_simon_step`, branche `PRESSED` fondée sur `pressed`, et `l3_simon_demo_input` avec `*held=0`).
