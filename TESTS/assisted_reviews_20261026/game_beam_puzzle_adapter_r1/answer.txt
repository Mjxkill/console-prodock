Faits constatés : `L3PuzzleChromeKey` inclut `lives` (`l3_puzzle_presentation.h`, struct), et `puzzle_key` propage `v->lives` (`l3_puzzle_ui.inc`). Dans `l3_puzzle_ui_chrome`, la comparaison globale `memcmp(&key,&old,...)` rend donc le cache invalide si les vies changent, et la révision de page s’incrémente. Mais le rafraîchissement du panneau n’est prévu que pour `key.status` ; sinon seuls `score/progress/target` sont réédités. Il n’y a pas de branche pour `lives`. L’importance du champ vies dans la clé est donc désynchronisée avec l’invalidation réelle. Fait aussi : les deux pages sont réellement séparées par `page_revision[2]`, avec chargement différentiel dans `puzzle_upload_rect`.

Hypothèse à vérifier : `sidebar()` affiche les vies. Le code source complet de `sidebar` n’est pas fourni, donc je marque cette dépendance comme hypothèse, pas comme fait. Si ce n’est pas le cas, le champ `lives` dans la clé n’a qu’un coût d’invalidation inutile.

Contre-exemple exact 1 : lors d’un événement dont le résultat visible est une perte de vie mais sans changement de `status/score/progress/target`, `l3_puzzle_presentation_observe` puis `l3_puzzle_motion_prepare` appellent `l3_puzzle_ui_chrome`. La comparaison globale détecte `lives`, donc `cache->key` est mis à jour et `revision++`, mais aucune portion du canvas n’est repeinte. Le canvas partagé garde les anciennes vies. Comme `compare` compare `r->mini_pixels` avec le mini UI de référence, la différence apparaît immédiatement au premier `prepare`, avant même d’interroger l’upload par page.

Contre-exemple exact 2, scénario A/B/A : si la répainture ne se fait pas, la page inactive garde son ombre `mini_shadow[page]` avec l’ancienne valeur. Quand elle devient active, `page_revision[page]` est déjà à la révision courante, donc `puzzle_upload_rect` n’envoie rien d’utile pour cette modification. L’ancienne vie reste présente dans la copie page A, et la rotation A/B/A ne répare pas l’état.

Différence effective : le panneau latéral est reconstruit et ré-uploadé sur la page courante dès qu’une variation de vies est détectée, alignant l’invalidation de cache avec la révision déjà incrémentée. J’ai volontairement limité la portée à la branche side panel : `status` reste géré d’abord, les variations purement numériques restent optimisées via `number_back`, et `lives` cesse d’être un fantôme de clé.
