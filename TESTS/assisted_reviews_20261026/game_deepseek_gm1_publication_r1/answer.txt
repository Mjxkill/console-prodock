## 6. Preuves manquantes / instrumentation nécessaire

1. **Timing par sous-étape dans `preparation`.** `gpu_motion_probe.c`, `run_phase` calcule seulement `f.preparation=end-before-f.submit-f.present`. Il faut ajouter des compteurs pour `mini_ui` raster/upload (`r->mini_raster_seconds`, `r->mini_publish_seconds`, `r->mini_scan_bytes`, `r->mini_restore_bytes`, `r->mini_chrome_rebuilds` existent déjà dans `render.h:54-55,62-63` mais ne sont pas imprimés par le probe), pour `maze_geometry` (autour de `geometry()`), et pour `mesh_seal_copy` (déjà mesuré par `l3_probe_mesh_publish`). Sans cela, `preparation` reste une boîte noire.
2. **Compteurs natifs non imprimés.** `COUNTER SCOPE` le dit : `l3_puzzle_ui.inc` enregistre `cache->rasterized_pixels` et `cache->published_bytes`, mais seulement `r->mini_bytes/mini_uploads` sont transmis ; `simon_presentation.c` enregistre `p->ui_raster_pixels` et `p->ui_published_bytes`, mais seulement `r->mini_bytes/mini_uploads` sont transmis. Les zéros UI des modes 2/4/6 ne sont **pas** une absence de travail CPU.
3. **Contradiction d’étiquettes/compteurs.** `FULL TOUR COSTS`, `name=Fusion1024` : `triangles=0`, `max_draws=0`, `commands=228147`, `batches=4421`. Or `VARIANTE baseline/candidate MODE 4`, `top moving` : `draws=11-14`, `triangles=1194-1664`. Si `MODE 4` est bien Fusion1024, les deux paquets ne décrivent pas le même chemin. De même, `name=Maison` au tour complet a `triangles=181504`, `max_draws=14`, tandis que `VARIANTE candidate MODE 5` a `draws=0`, `triangles=0`. Soit les compteurs `draws/triangles` ne sont pas alimentés pour ces chemins, soit les étiquettes ne correspondent pas. **Bloquant pour tout patch basé sur le mode 4 ou 5.**
4. **Hit-rate des caches natifs.** `puzzle_presentation.c:52` et `simon_presentation.c:122` incrémentent `skipped`, mais le probe ne l’imprime pas. Sans taux de succès, on ne peut pas comparer le gain d’un cache natif à un cache RAM.
5. **Page réellement scannée.** Le code utilise `frame&1` ; `simon_presentation.c:38-41` affirme ne pas toucher la page affichée, mais aucun compteur runtime de scanout n’est fourni. Toute nouvelle cache doit prouver qu’elle n’écrit que la page arrière.
6. **Entrée/préchargement.** Le paquet dit que `render_open` et le préchargement global des assets ont lieu **avant** `entry`. Il faut séparer : build statique, premier upload pleine page, bake natif, asset preload. Le pic d’entrée de 1,236 s du candidat avec `rasters=0` et `ui_bytes=768000` n’est pas attribuable sans cela.
7. **Microbenchmark d’écriture GPU.** Les débits apparents sont très faibles : `59 709 B / 0,05495 s ≈ 1,09 Mo/s` (mode 4), `19 456 B / 0,00322 s ≈ 6,0 Mo/s` (Maison). Il faut mesurer sur cible `memcpy` vs boucle 4 octets `volatile` pour 384 Kio vers `r->memory`, sans submit. Si `memcpy` est >2× plus rapide, le patch UI est un remplacement de boucle, pas un cache.
8. **Mémoire console.** `candidate_maze_render.c`, `l3_activity_art_open` utilise `PRODOCK_GPU_BASE+(18U<<20)` et affirme « above the complete console bank ». Le paquet donne le début du framebuffer console à `absolute 0x01700000`, soit `15 MiB` relatifs à `PRODOCK_GPU_BASE=0x00800000`. La taille de la banque console n’est pas fournie ; si elle dépasse 3 MiB, `18 MiB` chevauche. C’est une preuve manquante à lever avant tout patch mémoire. De même, `render.c:63-64` parle de pages HUD 20/21 MiB, alors que `mini_ui.c:15-16` utilise 22/23 MiB : commentaire obsolète ou incohérence à vérifier.

## 7. Patch minimal proposé

### 7.1 Priorité 1 : instrumentation, pas de changement de comportement

Preuve suffisante : le paquet ne permet pas d’attribuer `preparation`. Le patch suivant ne change ni pixels, ni commandes, ni sauvegardes ; il expose seulement l’existant.

Dans `gpu_motion_probe.c`, ajouter à `Phase` :

```c
double ui_raster, ui_publish;
unsigned long long ui_scan, ui_restore;
unsigned ui_chrome;
```

Dans `run_phase`, avant `l3_render_frame` :

```c
double ur0=r->mini_raster_seconds, up0=r->mini_publish_seconds;
unsigned long long us0=r->mini_scan_bytes, ub0=r->mini_restore_bytes;
unsigned uc0=r->mini_chrome_rebuilds;
```

Après `l3_render_frame` :

```c
p->ui_raster  += r->mini_raster_seconds  - ur0;
p->ui_publish += r->mini_publish_seconds - up0;
p->ui_scan    += r->mini_scan_bytes      - us0;
p->ui_restore += r->mini_restore_bytes   - ub0;
p->ui_chrome  += r->mini_chrome_rebuilds - uc0;
```

Dans `print_phase`, ajouter :

```c
printf("GPU_UI name=%s raster_s=%.9f publish_s=%.9f scan_bytes=%llu restore_bytes=%llu chrome=%u\n",
       p->name, p->ui_raster, p->ui_publish,
       (unsigned long long)p->ui_scan, (unsigned long long)p->ui_restore, p->ui_chrome);
```

Pour les modes natifs, inclure `l3_puzzle_presentation.h` et `l3_simon_presentation.h` et imprimer `p->ui.rasterized_pixels`, `p->ui.published_bytes`, `p->skipped`, `p->quads` (puzzle) et `p->ui_raster_pixels`, `p->ui_published_bytes`, `p->ui_scan_bytes`, `p->skipped`, `p->base_bytes`, `p->asset_bytes` (Simon). Ce sont exactement les champs cités par `COUNTER SCOPE`.

Pour `maze_render`, ajouter un timer autour de `geometry()` :

```c
double g0=l3_probe_time();
if(!l3_mini_motion_sample(...) || !geometry(r,&v,&actors))return 0;
l3_probe_stage_add(ST_MAZE_GEOM, l3_probe_time()-g0);
```

`seal()` mesure déjà la copie via `l3_probe_mesh_publish`. On obtient alors `maze_geom` vs `mesh_copy` vs `ui_raster` vs `ui_publish`.

### 7.2 Priorité 2 : dédup du mesh dynamique — **seulement comme test contrôlé**

Preuve insuffisante pour le fusionner : gain maximal 5,0 % en baseline Maison, 0 dans le candidat, et le pic n’est pas là. Si on veut quand même tester, le patch minimal est une ombre RAM de 2 Mio (deux pages de 1 Mio) et une comparaison exacte avant `memcpy` :

```c
#define DYN_PAGE (1u<<20)
static uint8_t dyn_shadow[2][DYN_PAGE];
static unsigned dyn_valid[2];

static int seal(Builder *b){
    if(!b->nv) return 1;
    unsigned vbytes=b->nv*32, fbytes=b->nf*32, bytes=vbytes+fbytes;
    if(b->n>=24 || b->offset>(28U<<20) || bytes>(28U<<20)-b->offset) return 0;
    unsigned start=b->offset, page=(start>>20)&1u;
    unsigned rel=start-((26u+page)<<20);
    if(rel+bytes>DYN_PAGE) return 0;
    uint8_t *sh=dyn_shadow[page]+rel;
    double t0=l3_probe_time();
    if(!(dyn_valid[page] &&
         !memcmp(sh,b->v,vbytes) &&
         !memcmp(sh+vbytes,b->f,fbytes))){
        memcpy(b->r->memory+start,b->v,vbytes);
        memcpy(b->r->memory+start+vbytes,b->f,fbytes);
        memcpy(sh,b->v,vbytes);
        memcpy(sh+vbytes,b->f,fbytes);
        dyn_valid[page]=1;
    }
    b->offset+=bytes;
    b->meshes[b->n++]=(gpu_geom_mesh){PRODOCK_GPU_BASE+start,
                                     PRODOCK_GPU_BASE+b->offset,
                                     (uint16_t)b->nv,(uint16_t)b->nf};
    l3_probe_mesh_publish(start,bytes,l3_probe_time()-t0);
    b->nv=b->nf=0;
    return 1;
}
```

Points obligatoires :

- Invalider `dyn_valid[0..1]` à `l3_render_open`, au changement `activity_mode`/`activity_stage`, et si `gpu_v1_invalidate` est appelé. Sinon le cache peut sauter une écriture alors que la VRAM a été réutilisée par un autre renderer.
- Ne jamais lire `r->memory` pour comparer.
- Écrire uniquement la page `frame&1` (26/27 MiB), qui n’est pas la page affichée.
- 2 Mio de RAM ordinaire ; pas de changement de pixels ni de commandes.

Gain attendu : au mieux `1,12 s` sur `22,48 s` en Maison baseline `moving` (5,0 %), `0` dans le candidat, et `~2,8 s` sur `29,46 s` en mode 4 candidate **si** 251/360 images sont identiques — ce qui reste à prouver.

### 7.3 Ce que je ne propose pas

Je ne propose pas de patch de raster UI dans `mini_ui.c` sur la base des seuls pics Maison : `preparation` n’est pas décomposée, et `raster+compare_publish` ne fait que `1,836 s` sur `13,189 s` du tour complet Maison. Un patch UI pourrait réduire cette part, mais pas le pic d’entrée de 0,581 s sans instrumentation. De même, je ne propose pas de patch `maze_render` pour le pic : le pic baseline est `preparation` à 80 %, et `mesh_publish` à 1,1 %.

## 8. Tests d’équivalence et de réfutation

1. **Équivalence des commandes, host/fixture.** Le probe n’autorise `--capture` qu’avec `--host --fixture` (`gpu_motion_probe.c`, validation `(capture&&(!host||!fixture))`). Lancer le **même binaire candidat**, cache activé/désactivé, `--host --fixture --kind 5 --frames 63 --capture /tmp/m5_off` et `/tmp/m5_on`, puis comparer le SHA-256 des fichiers `.commands`. Si la cache ne saute que des écritures de données identiques, le flux de commandes doit être **byte-identique**. Vérifier aussi `probe_metrics.py` : `assert b'LUMA3D_SAVE ' not in raw`, `assert p['queue_overflows']==0 and p['exited']==0`, `state_crc32` au format `[0-9a-f]{8}`.
2. **Équivalence pixels.** Ne pas utiliser la baseline comme référence pixel : le paquet dit que le candidat ajoute des glissements/halos et une nouvelle présentation maison. La référence doit être **le même binaire candidat sans cache**. Si le paquet ne fournit pas d’outil de capture framebuffer hardware, cette preuve manque ; le `--capture` host/fixture ne prouve que les commandes, pas les pixels.
3. **Équivalence sauvegarde/logique.** Les couples baseline/candidat des fenêtres contrôlées ont des `state_crc32` identiques par phase : M1 `80daff21,80daff21,28871f45` ; M3 `88fcab15,88fcab15,b033437e` ; M4 `7162ad9c,7162ad9c,c5384401` ; M5 `c21d7530,c21d7530,40bc87d5` ; M6 `61c8fa22,61c8fa22,bec2b0a2`. C’est un témoin fort, pas une preuve exhaustive des règles. Le probe imprime `saves=disabled` ; `gpu_motion_probe.c` dit « No save file is opened ».
4. **Test de la dédup mesh.** Logger un hash FNV-1a de `v[]` et `f[]` à chaque `seal`. Compter les images consécutives identiques dans `--kind 4 --frames 360` et `--kind 5 --frames 360`. Si <10 %, abandonner la dédup. Si >50 %, relancer cache on/off et comparer `wall`, `preparation`, `mesh_publish`, `p99`, `max`.
5. **Test du premier upload.** Instrumenter `entry` séparément : première publication page 0, page 1, bake natif, build statique. Microbenchmark `memcpy` 384 Kio vs boucle 4 octets volatile vers `r->memory`. Si `memcpy` est >2× plus rapide, remplacer la boucle dans `upload()`/`puzzle_upload_rect()` par des plages contiguës `memcpy` en conservant l’ombre ; sinon, ne pas toucher.
6. **Test de page affichée.** Ajouter un compteur de page scannée (ou une preuve pilote) et vérifier que `frame&1` n’écrit jamais la page active. Sans cela, toute cache multi-page reste risquée.
7. **Test mémoire 18 MiB.** Vérifier la taille réelle de la banque console entre `0x01700000` et l’usage `PRODOCK_GPU_BASE+(18<<20)`. Si la banque dépasse 3 MiB, le candidat `l3_activity_art_open` chevauche la console ; c’est un défaut séparé, mais bloquant pour « no reuse of console ».

## 9. Contre-exemples explicites

- **Contre-exemple à « 60 Ko explique Maison »** : `VARIANTE baseline MODE 5`, `top index=241`, `mesh_publish=0,003220713 s` sur `0,288018687 s` (1,1 %) ; `VARIANTE candidate MODE 5` a `dynamic_bytes=0`. Le pic est `preparation=0,231018725 s` (80,2 %). La copie n’est pas le coût.
- **Contre-exemple à « le cache natif est toujours gagnant »** : le mode 1 gagne 0,35 s de wall mais ajoute 1,40 s de `submit` ; le mode 3 gagne 1,40 s de wall mais ajoute 3,77 s de `submit` ; l’entrée se dégrade dans les cinq modes, avec `overflow=1` en modes 3 et 5. Le tour complet inclut l’entrée, donc le gain `moving` n’est pas le gain utilisateur.
- **Contre-exemple à « SUBMIT = raster »** : le pic Maison baseline `index=241` a `submit=31 ms` sur `288 ms`, alors que `preparation=231 ms`. Le `submit` du tour complet Maison (6,08 s) inclut le pilote et la synchronisation, pas seulement le dessin.
- **Contre-exemple à « les zéros UI natifs signifient zéro travail »** : `COUNTER SCOPE` dit explicitement que les champs legacy ne sont pas instrumentés pour les modes natifs ; `l3_puzzle_ui.inc` et `simon_presentation.c` ont leurs propres compteurs non imprimés.

## 10. Ce qui doit rester inchangé

- **Règles, pixels, art, sauvegardes** : le paquet exige les mêmes pixels/art, la même logique, la même sauvegarde, le même FPGA G22r0 et le même noyau. Toute cache doit être testée avec le **même binaire candidat**, cache on/off, pas contre la baseline si le candidat change volontairement le rendu (glissements/halos/nouvelle présentation maison).
- **Commandes légales** : `prodock_command` valide chaque commande avant FIFO (`prodock-gpu.c:136-139`) ; `submit` vérifie `batch->count`, `reserved`, la signature géométrie (`prodock-gpu.c:134,143-144`). Un patch qui ne saute que des écritures de données identiques ne change pas le flux de commandes ; le test `.commands` doit le confirmer.
- **Pas de lecture VRAM** : utiliser `mini_shadow[page]` ou une ombre RAM équivalente, jamais `memcmp(r->memory+...)`.
- **Pas d’écriture de la page affichée** : écrire la page `frame&1` et prouver le scanout, ou réutiliser `base_ready/page_valid` de `simon_presentation.c`.
- **Mémoire bornée** : 2 Mio pour une ombre de mesh dynamique, à comparer aux 2 Mio déjà utilisés par `mini_shadow[2]` et aux pages HUD. Vérifier le 18 MiB de `l3_activity_art_open` avant tout nouveau placement.

**En résumé :** le paquet ne soutient pas l’explication par la copie de 60 Ko/image pour Maison ; il soutient que les buffers RAM sont déjà le bon patron, que le cache natif a des gains réels mais déplace le coût vers `submit` et l’entrée, et que l’instrumentation par sous-étape est le prochain pas indispensable avant tout patch de performance.
