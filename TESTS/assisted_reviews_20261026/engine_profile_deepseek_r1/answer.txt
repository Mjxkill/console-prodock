## 1. Périmètre, faits et hypothèses

Je n’ai exécuté aucun test, aucun build et aucune modification. Le paquet ne contient pas `src/main.c` (seulement son SHA-256), ni `linux/drivers/prodock-uapi.h`, ni le code de `upload()`, ni le contenu de `prodock_info`.

Faits directement établis par le paquet :

- `luma3d_render.h` définit `L3_MAP_BYTES = 32 MiB` et `L3_ASSET_OFFSET = 8 MiB`, et `L3Render` porte `width`, `height`, `pitch`, `page_bytes`, `memory`.
- `render.c:73-85` : dimensions 800×480 ou 1280×720 ; sur carte, `w/h` viennent de `PRODOCK_INFO` (`render.c:82`) ; la cible 3D vaut `w/2 × h/2`, le pitch `w*2`, la page `1 MiB` ou `2 MiB`.
- `render.c:84` : seules les paires 800×480 et 1280×720 sont acceptées.
- `render.c:86` : fenêtre de 32 MiB, `mmap` sur carte ou `calloc` en hôte.
- `render.c:92` : les ressources commencent à 8 MiB ; `render.c:96` publie des blocs de 32 octets.
- `render.c:311` : page couleur alternée `(frame&1)*page_bytes`.
- `render.c:326-327` : profondeur à `2*page_bytes`, ciel à `6 MiB`.
- `render.c:460` et `478` : dump et `munmap` portent sur exactement 32 MiB.
- Le document d’architecture fixe les profils 400×240/640×360, les pages 1/2 MiB, les pitches 1600/2560, la limite V1 1024×512, et les plages mémoire 8–14, 14–15, 15–17, 18/19, 20–24, 24–28, 28–32 MiB.

Hypothèses à ne pas transformer en faits : la valeur de `PRODOCK_GPU_BASE` n’est pas dans le paquet ; les plages 8–14, 15–17, 18/19, 20–24, 24–28 et 28–32 sont déclarées par le document mais leur provenance noyau n’est citée que pour 14–15 MiB. Le profil 1280×720 n’est pas une validation matérielle Neo.

## 2. Interface C minimale proposée

Le module reste sans I/O, sans allocation, sans type GPU et sans `prodock-uapi.h`. Les offsets sont **relatifs à la fenêtre de 32 MiB**, jamais des adresses physiques.

```c
/* l3_profile.h — contrat pur, commun Pro Dock / Neo */
#ifndef L3_PROFILE_H
#define L3_PROFILE_H
#include <stdint.h>

enum { L3_PROFILE_NONE = -1,
       L3_PROFILE_800x480 = 0,
       L3_PROFILE_1280x720 = 1 };

typedef struct { uint32_t start, end; } L3Range; /* [start,end), relatif */

typedef enum {
    L3_MEM_COLOR0 = 0,
    L3_MEM_COLOR1,
    L3_MEM_WORLD,          /* 8 .. 14 MiB  */
    L3_MEM_PUZZLE_SIMON,   /* 14 .. 15 MiB, exclusif */
    L3_MEM_CONSOLE,        /* 15 .. 17 MiB, interdit au jeu */
    L3_MEM_HUD,            /* 20 .. 24 MiB  */
    L3_MEM_ACTIVITY_POOL,  /* 24 .. 28 MiB, agrégat */
    L3_MEM_SHOOTER,        /* 28 .. 32 MiB  */
    L3_MEM_COUNT
} L3MemId;

typedef struct {
    uint32_t screen_w, screen_h; /* sortie / UI */
    uint32_t render_w, render_h; /* cible 3D = screen/2 */
    uint32_t pitch;              /* RGB565, octets/ligne */
    uint32_t page_bytes;
    uint32_t map_bytes;          /* 32 MiB */
    uint32_t asset_offset;       /* 8 MiB */
    uint32_t sky_offset;         /* 6 MiB */
    uint32_t v1_max_w, v1_max_h; /* 1024 x 512 */
    uint32_t publish_block;      /* 32, blocs de publication */
} L3Profile;

int l3_profile_find(uint32_t w, uint32_t h);          /* id ou NONE */
const L3Profile *l3_profile_get(int id);               /* NULL si inconnu */
int l3_profile_valid(const L3Profile *p);              /* 0/1, sans effet */
L3Range l3_profile_range(const L3Profile *p, L3MemId id);
uint32_t l3_profile_depth_offset(const L3Profile *p);  /* 2*page, 0 si invalide */
#endif
```

`l3_profile_range` ne renvoie que des plages dont début et fin sont connus. Le ciel (6 MiB), la profondeur, les atlas 18/19 et les banques 26/27 ne sont pas des `L3Range` complets : leurs tailles ne sont pas établies. La profondeur est seulement un offset ; la taille minimale requise est calculée par le validateur.

## 3. Invariants et cas limites

1. **Sélection fermée** : seules `(800,480)` et `(1280,720)` sont valides, comme `render.c:84`. Toute autre dimension retourne `L3_PROFILE_NONE` ; aucun profil « par défaut ».
2. **Dérivations exactes** : `render_w == screen_w/2`, `render_h == screen_h/2`, `pitch == screen_w*2`, `page_bytes == 1 MiB` pour 800×480, `2 MiB` pour 1280×720.
3. **Page couleur** : `page_bytes >= pitch*render_h`, calculé en `uint64_t`. Cela couvre 400×240×1600 et 640×360×2560.
4. **Profondeur** : `depth = 2*page_bytes`, et `depth + pitch*render_h <= sky_offset`. La taille exacte réservée pour la profondeur n’est pas affirmée ; on vérifie seulement que l’étendue minimale ne touche pas le ciel.
5. **Fenêtre** : `map_bytes == 32 MiB`; toutes les plages connues sont incluses dans `[0,map_bytes)`, avec `start < end`.
6. **Non-recouvrement supérieur** : les plages `WORLD`, `PUZZLE_SIMON`, `CONSOLE`, `HUD`, `ACTIVITY_POOL`, `SHOOTER` sont disjointes. `ACTIVITY_POOL` reste volontairement un agrégat : les banques 26/27 ne doivent pas être extraites comme deux ranges de taille 1 MiB, car le paquet ne donne pas leur étendue exacte.
7. **Console** : `CONSOLE` vaut `[15 MiB,17 MiB)`. Aucune autre plage inscriptible ne doit la recouvrir. Attention : la provenance citée dans le document porte sur l’absence de chevauchement de 14–15 MiB avec la console ; la preuve kernel de 15–17 MiB n’est pas fournie dans ce paquet.
8. **V1 720p** : on valide `render_w <= 1024 && render_h <= 512`. On ne valide **pas** `screen_w <= 1024` : en 1280×720 la cible est 640×360, dans une page de pitch 2560, conformément au document. Confondre les deux est le faux rejet à éviter.
9. **Overflow** : tous les produits (`pitch*render_h`, `2*page_bytes`, `start+taille`) passent par `uint64_t` ; tout dépassement de `UINT32_MAX` ou de `map_bytes` invalide le profil.
10. **Alignement** : seul l’alignement RGB565 `pitch % 2 == 0` est certain. Les offsets actuels sont des multiples de MiB, mais aucune exigence ABI d’alignement de page ou de région n’est fournie : ne pas inventer un `align(4096/32)` universel. Le bloc de 32 octets concerne la publication/MC1, pas les pages.
11. **Exclusivité** : `PUZZLE_SIMON` est mutuellement exclusif ; le module le documente par son identifiant, mais ne prétend pas déduire l’état d’occupation. Un simple tableau de plages ne suffit pas à exprimer cette règle.
12. **Couches console** : la réserve 12–15 du terminal est un contrat distinct. Le paquet ne donne pas le nombre de couches réellement utilisables par l’application ; ne pas exposer `12` comme capacité disponible.

## 4. Valeurs connues et manquantes

Connues et encodables : 32 MiB de fenêtre ; 8 MiB de début des ressources ; 6 MiB de ciel ; profils 800×480 et 1280×720 ; rendus 400×240 et 640×360 ; pitches 1600/2560 ; pages 1/2 MiB ; limite V1 1024×512 ; plages 8–14, 14–15, 15–17, 20–24, 24–28, 28–32 MiB ; blocs de 32 octets ; couches console 12–15.

Manquantes ou non prouvées dans le paquet : valeur de `PRODOCK_GPU_BASE` ; tailles exactes du ciel, de la profondeur, des atlas 18/19 et des banques 26/27 ; sous-découpage de 8–14 et 20–24 ; alignement exigé par l’ABI ; champs et bits de capacité de `prodock_info` ; nombre de couches application ; validité matérielle Neo ; hash d’un dump GM1 de 32 MiB. Ce dernier point est une preuve de non-régression à établir avant tout raccord.

## 5. Plan de raccord minimal

**Patch A — nouveaux fichiers uniquement.** Ajouter `include/l3_profile.h` et `src/l3_profile.c` avec deux tables `static const L3Profile` et les fonctions pures. Aucun fichier actif modifié. Tests hôtes purs à prévoir : égalité stricte des deux profils avec les littéraux de `render.c:73-85` ; validité des plages ; refus d’un profil synthétique avec pitch impair, page trop petite, profondeur franchissant le ciel, console recouvrant une plage inscriptible, `map_bytes` différent de 32 MiB, et cible 1280×720 présentée comme cible V1.

**Patch B — un seul point de raccord.** Dans `l3_render_open`, après la fixation de `w/h` (`render.c:82`) et le test d’acceptation (`render.c:84`), remplacer uniquement l’affectation de `r->width`, `r->height`, `r->pitch`, `r->page_bytes` (`render.c:85`) par les champs du profil sélectionné. Garder `w` et `h` locaux, conserver `L3_MAP_BYTES` pour le `mmap` initial, et retourner 0 si `l3_profile_find` échoue. Les valeurs étant identiques, le flux GM1 doit rester identique.

**Patch C — optionnel, un littéral à la fois.** Remplacer `L3_MAP_BYTES` aux lignes 86/460/478 et les offsets 6/8 MiB aux lignes 92/327, puis `2*page_bytes` ligne 326, sans changer l’ordre des opérations ni les types. Ne pas toucher `PRODOCK_GPU_BASE`, ni la construction des commandes, ni l’ABI.

Preuve discriminante proposée, non exécutée ici : conserver pour GM1 un dump `.memory` de 32 MiB (`render.c:460`) et son JSON, puis comparer les SHA-256 avant/après chaque patch sur une séquence fixe. Le dump couvre exactement la fenêtre mémoire, donc il détecte un déplacement de page, de profondeur ou de ressource ; il ne prouve pas à lui seul l’identité du flux de commandes, d’où la comparaison séparée des captures hôtes et des compteurs. Pour le 720p, le test doit vérifier 640×360 ≤ 1024×512 et jamais 1280×720 ≤ 1024×512.
