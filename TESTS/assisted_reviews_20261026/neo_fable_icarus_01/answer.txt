- **Le patron CSR suffit à bloquer Icarus.** Le reproducteur `original_shared_vector/tb.sv:12-20` reproduit mot pour mot `gpu_accel.v:154-162`. ## Mécanisme : dépendance événementielle entre always, pas boucle matérielle

**Hypothèse principale, cohérente avec toutes les observations.** Chaque bloc `always @*` de `gpu_accel.v:156` lit `response_data[b*8+:8]` en partie droite de `gpu_accel.v:159`. Sa liste de sensibilité implicite contient donc `response_data`. Icarus abonne le bloc au vecteur entier, pas à la tranche. Chaque exécution écrit d'abord `8'd0` puis la valeur finale. Si la valeur finale est non nulle, cela génère deux changements sur le vecteur. Ces changements réveillent les trois autres blocs, qui en font autant et réveillent le premier. Un bloc seul ne se réveille pas lui-même, car il n'attend pas pendant qu'il écrit. La chaîne existe seulement avec au moins deux blocs dont l'octet final est non nul.

**Ce que cela implique dans `gpu_accel.v` sans aucune lecture CSR.** Le reset de `gpu_accel.v:114` met `read_select` à un-chaud sur l'index 0 pour chaque octet. `register_value[0]` vaut `424c5432` à `gpu_accel.v:123`, quatre octets non nuls. Le premier front `hclk` sous reset lance donc la boucle. La boucle ne dépend pas d'une lecture AHB du banc. C'est un fait, pas une généralisation.

**Pourquoi ce n'est pas une boucle combinatoire matérielle.** Le bloc `b` écrit uniquement l'octet `b` et ne lit que l'octet `b`. L'auto-référence de `gpu_accel.v:159` est une accumulation bloquante déroulée en arbre d'OR par la synthèse. Les tranches sont disjointes entre blocs. Il n'y a aucun chemin de rebouclage. Verilator, qui ordonne par dépendance de données et non par événement, converge. La variante `tmp` confirme que la valeur finale est stable au premier calcul.

**Ce qui reste hypothèse.** La granularité « vecteur entier » d'Icarus n'est pas démontrée par le paquet, seulement cohérente avec 263 740 événements. Deux variantes du reproducteur la discriminent, sans toucher au RTL commun :

1. Garder le vecteur partagé, ne générer qu'un seul bloc. Prédiction : convergence.
2. Garder les quatre blocs, remplacer le vecteur par quatre `reg [7:0]` distincts. Prédiction : convergence.
3. Garder le reproducteur original, mettre `register_value[0]` à `32'h0000001f`, un seul octet non nul. Prédiction : convergence. Avec `32'h000001ff`, deux octets non nuls, prédiction : blocage.

Si ces trois prédictions tiennent, le mécanisme est établi. Si la variante 1 boucle, mon modèle du réveil propre est faux et il faut revoir l'analyse.

## Autres explications et preuve de non-interférence

**Autre explication non exclue par le paquet.** Le cas `accel` est le seul à instancier `ddr_dcfifo`, `cdc_word`, `font_ram`, `blitter` et `gpu_blit_dma`. Les cas `geometry`, `pixels`, `raster`, `copy` ne les exercent pas forcément. Le reproducteur prouve que le patron CSR est suffisant pour bloquer, pas qu'il est l'unique cause dans `gpu_accel`. Le force sur `read_select` est justement le test qui ferme cette lacune : si le temps avance avec `read_select` forcé à 0, le patron est aussi nécessaire dans cette configuration.

**Cône d'influence de `read_select`, d'après le fichier fourni.** Le seul lecteur de `read_select` est `gpu_accel.v:160`. Le seul écrivain de `response_data` est le bloc `gpu_accel.v:156-161`. Le seul lecteur de `response_data` est `gpu_accel.v:152`, qui produit `hrdata`. Rien dans le module ne relit `hrdata`. `hready` à `gpu_accel.v:44` dépend de `bus_command`, `queue_full`, `read_wait`. `read_wait` à `gpu_accel.v:47-51` dépend de `hsel`, `htrans`, `hwrite`, `hready`. Le FIFO `gpu_accel.v:71-75`, `command_word`, le slot `v1_pending` et le mux DDR `gpu_accel.v:235-239` sont dans le domaine `mem_clk` et ne voient pas `read_select`. Forcer `read_select` à 0 ne modifie donc que `response_data` et `hrdata`. Avec tous les octets à 0, les quatre blocs écrivent 0 sur 0 et ne génèrent aucun événement, même quand `busy_sync` ou `queue_full` les réveillent.

**Contrôles additionnels, banc seulement.**

Garde de périmètre, pour que le force n'ait jamais à masquer une lecture :

```verilog
always @(posedge hclk)
  if (hresetn && hsel && htrans[1] && !hwrite && hready)
    $fatal(1, "lecture CSR dans un banc qui force read_select");
always @(posedge hclk)
  if (dut.read_select !== 104'd0 || dut.read_wait !== 1'b0)
    $fatal(1, "force read_select inefficace a %t", $time);
```

Détecteur de boucle delta, portable Icarus et Verilator, à placer dans un banc sans force pour obtenir l'heure exacte du blocage qui manque au paquet :

```verilog
integer deltas = 0; time last_t = 0;
always @(dut.response_data) begin
  if ($time == last_t) deltas = deltas + 1;
  else begin deltas = 0; last_t = $time; end
  if (deltas > 64) $fatal(1, "boucle delta sur response_data a %t", $time);
```
